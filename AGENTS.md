# Rebreya Main: инструкции для агента

Этот файл — короткая обязательная точка входа. Не читай весь репозиторий или большие документы целиком: сначала выбери слой и владельца изменения.

## Когда читать паспорт функций

Если для задачи нужны конкретные функции, методы, владельцы данных, маршруты вызовов, точки расширения или профильные тесты, открой `docs/function-passport.md` и прочитай только относящийся к задаче раздел.

- Для поиска раздела сначала используй `rg -n "термин|метод|файл" docs/function-passport.md`.
- Не загружай паспорт целиком без прямой необходимости.
- Любые новые или изменённые методы записывай в соответствующий раздел паспорта в том же commit.
- Обновляй сигнатуры, назначение, владельца, data flow, ограничения и профильные тесты. Удалённую функцию удаляй или заменяй в паспорте.
- Паспорт описывает текущее состояние проекта, а не историю изменений.

## Обязательный Git-процесс

- Репозиторий общий: код параллельно изменяют несколько человек.
- Перед правками выполни `git status --short --branch`, `git branch --show-current` и `git fetch origin`.
- Основная ветка — `main`; если remote использует `master`, проверяй её аналогично.
- Все изменения вноси только в `lich_branch`. Никогда не коммить и не пушь напрямую в `main` или `master`.
- После fetch выполни `git rev-list --left-right --count HEAD...origin/main` и `git log --oneline HEAD..origin/main`.
- Если есть чужие незакоммиченные изменения, remote `lich_branch` ушла вперёд или актуальная основная ветка конфликтует с работой — остановись и сообщи пользователю.
- Не используй `git add -A` в смешанной рабочей копии; добавляй только файлы текущей задачи.
- Перед commit проверь `git diff --check`, `git diff --stat` и содержательный `git diff`.
- После проверок сделай осмысленный commit и `git push -u origin lich_branch`.
- Force push запрещён без отдельного разрешения.

## Быстрый вход

- Среда: Foundry VTT 13, система dnd5e, обязательный модуль `statuscounter >= 3.0.4`.
- Источник версии и runtime-entrypoint — `module.json`.
- Versioned forwarder `scripts/main-<version>.js` должен только импортировать `scripts/main.js`.
- `scripts/main.js` — единственный composition root; он собирает сервисы, hooks и socket routes и публикует `game.rebreyaMain` и `game.modules.get("rebreya-main")?.api`.
- Обзор пользовательского API находится в `README.md`; открывай нужный раздел по заголовку.
- `docs/rebreya-module-architecture.html` — generated snapshot. Перед использованием сверяй `sourceCommit`; для обновления запускай `node tools/generate-architecture-map.mjs`.

## Версионирование и клиентский кэш

- При любом изменении кода, стилей, шаблонов, локализации или других файлов, которые получают игроки, ОБЯЗАТЕЛЬНО повышай `version` в `module.json` в рамках той же задачи. Не оставляй такие изменения на старой версии даже при локальном развёртывании.
- Модуль раздаётся через локальный Cloudflare Tunnel и кэшируется на клиентах игроков; без новой версии они могут продолжить получать устаревшие файлы.
- При повышении версии синхронно создай или переименуй `scripts/main-<version>.js`, обнови путь в `esmodules` и проверь, что в runtime-конфигурации не осталось ссылок на предыдущую версию.

## Архитектурные слои

|---|---|---|
| Composition | `scripts/main.js` | lifecycle, зависимости, API, socket dispatch |

| Infrastructure | `scripts/infrastructure/` | repositories, active GM, typed sockets, UI refresh |

| UI | `scripts/ui/`, `templates/`, `styles/` | ApplicationV2, Handlebars, оформление |

Направляй зависимости к domain/application и инфраструктурным интерфейсам. UI не должен напрямую писать world settings или исполнять привилегированные мутации.

## Контекст, завершение задачи и модель

- Выполни всю порученную задачу: реализацию, нужную проверку, обновление документации и Git-процесс. Не останавливайся после плана или первой рабочей версии, если пользователь поручил дальнейшие шаги.
- Новый чат предлагай для следующей самостоятельной задачи, когда история перегружена завершённым исследованием, устаревшими гипотезами или повторными compaction. Не прерывай текущую задачу ради переноса; сначала сохрани подтверждённые решения.
- Для следующего чата дай короткий самодостаточный handoff: результат и границы, путь к готовой спецификации (если есть), владелец поведения, ограничения, необходимые проверки и открытые вопросы. Не копируй историю и логи.
- При рекомендации модели сверяй её доступность в текущем продукте. Ориентир OpenAI: `GPT-6 Luna` с low/medium для чётко ограниченных правок и классификации, `GPT-6 Sol` с medium для повседневной разработки, `GPT-6 Astra` с medium/high для сложной архитектуры, world-state, sockets, recovery и рискованных изменений. Повышай effort только при необходимости и не откладывай уже порученную работу ради смены модели.

## Как переходить к реализации

1. Сформулируй наблюдаемое поведение и владельца; через `rg` найди связанные вызовы, flags, commands и hooks и читай только нужные диапазоны.
2. Расширяй существующий канонический сервис, API-метод или socket command, не создавая второго владельца, app или hook.
3. World-state изменяй через repository/coordinator, не из UI; player-операции с правами GM направляй через валидируемую typed command с авторизацией отправителя.
4. Для изменения поведения добавь или измени focused-тест владельца, затем внеси минимальную реализацию. При изменении публичного контракта обнови нужный раздел `README.md`.
5. Общий рекурсивный scan одного asset-root выполняй не более одного раза за startup/reload batch. Composition owner инвалидирует кэш один раз перед batch, сервисы переиспользуют результат. Принудительный scan допустим для отдельного явного refresh; все importers владельца кэша используют один canonical ESM URL/cache key.

## Снижение расхода контекста и токенов

- Не используй subagents ради мелкой параллельности: каждый агент получает отдельный контекст. Применяй их только для крупных действительно независимых работ.
- В Code Mode объединяй независимые вызовы инструментов в один `functions.exec`, проверяя каждый результат; зависимые действия выполняй последовательно.
- Передавай агрегированные результаты команд: тесты — passed/failed и реальные ошибки; git — shortstat или ограниченный diff; поиск — только релевантные совпадения и узкие диапазоны. Полные успешные логи не передавай.
- При изменении поведения запускай focused-тесты. Полную проверку runtime-кода выполняй один раз перед commit; повторяй затронутые проверки после новых изменений или ошибок. Для правки только инструкций или документации достаточно проверки diff и связанных ссылок.
- В handoff фиксируй commit и уже выполненные проверки.
- Не читай большие файлы целиком: сначала используй `rg`, затем открывай узкий диапазон.
- Используй паспорт функций как индекс. Если профильные разделы существенно разрастаются, разделяй их по доменам, оставляя `docs/function-passport.md` точкой маршрутизации.
- Массовые операции выполняй независимыми batch-задачами с manifest или другим компактным состоянием вместо одной длинной сессии.
- Пересматривай постоянные инструкции при изменении моделей и процесса; убирай устаревшие, противоречивые и дублирующие правила.
- По возможности используй только инструменты, plugins и skills, необходимые текущей задаче.
- Не жертвуй обязательными проверками и корректностью ради экономии токенов.

## Проверки

Focused-тест выбирай по владельцу из паспорта. Для изменений runtime-кода выполни полную проверку перед commit:

```powershell
node --test tests/*.test.mjs
git diff --check

$files = git ls-files '*.js' '*.mjs'
foreach ($file in $files) { node --check $file }

$json = git ls-files '*.json'
foreach ($file in $json) { Get-Content -Raw -Encoding UTF8 $file | ConvertFrom-Json | Out-Null }
```

В отчёте укажи команды, число passed/failed и реальные ошибки; полный успешный вывод не вставляй.
