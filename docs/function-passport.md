# Rebreya Main: паспорт функций и подсистем

Этот документ содержит подробные точки реализации, владельцев, data flow и профильные тесты. Начинай с корневого `AGENTS.md`, находи нужный раздел через `rg` и не загружай паспорт целиком без прямой необходимости.

## Контракт актуальности паспорта

`docs/function-passport.md` — обязательная часть реализации, а не историческая заметка. Любое изменение поведения должно в том же commit обновлять соответствующий паспорт ниже.

Обновление обязательно, если изменение:

- добавляет, удаляет, переименовывает или меняет контракт публичного метода `game.rebreyaMain`;
- добавляет или меняет service/repository, владельца данных, world setting, Actor/Item flag или managed pack;
- добавляет или меняет typed socket command, payload, `validate`, `authorize`, active-GM route или mutation journal;
- добавляет hook, ApplicationV2-окно, integration с dnd5e/сторонним модулем или новый refresh scope;
- переносит ответственность между файлами либо меняет последовательность чтения, мутации, компенсации или UI refresh;
- добавляет функциональную область или focused-тест, который становится основным доказательством поведения.

В затронутом паспорте укажи новые методы с сигнатурами, назначение, владельца, путь данных, ограничения и тесты. При удалении функции удали или замени её запись. Внутренний helper документируй только тогда, когда он становится архитектурной точкой входа или меняет границу ответственности. Хронологический changelog здесь не ведётся: документ всегда описывает текущее состояние.

Definition of Done: код, тесты, `README.md` при изменении публичного контракта и затронутые разделы `docs/function-passport.md` согласованы между собой. Изменение без актуализации паспорта считается незавершённым.

Перед commit выполни `git diff --name-only` и `git diff --cached --name-only`. Если изменён функциональный файл в `scripts/`, `data/`, `templates/`, `styles/` или `module.json`, соответствующее изменение `docs/function-passport.md` должно быть в том же staged scope. Исключение — чисто внутренний refactor без изменения контракта, владельца, data flow и точки реализации; это исключение должно быть очевидно из diff.

## Паспорт функций и подсистем

### 1. Composition root и публичный API

- **Зачем:** собрать зависимости один раз, провести Foundry lifecycle и дать макросам стабильную точку входа.
- **Владелец:** `scripts/main.js`; manifest и версия — `module.json`; versioned `scripts/main-<version>.js` является только forwarder к `main.js`.
- **Внешняя поверхность:** `game.rebreyaMain` и `game.modules.get("rebreya-main")?.api` ссылаются на один экземпляр `RebreyaMainModule`.
- **Lifecycle:** `init` регистрирует settings/helpers/types/ранние patches; `setup` подключает socket listener; `ready` создаёт API, hooks, managed packs и runtime-сервисы; `initialize()` выполняет фактическую загрузку.
- **Порядок privileged-mutation composition:** constructor создаёт один `WorldMutationCoordinator` → один `SocketCommandBus` → один `PrivilegedMutationGateway` → один `WorldSettingMutationRepository` → существующие repositories/services. Gateway доступен как `RebreyaMainModule.privilegedMutationGateway`; composition injects queued setting repository в `GlobalEventsService` и `EconomyRepository`.
- **Координационные методы:** `getModel(options)`, `reloadData({ notify, rerender })`, `resetWorldData({ notify })`, `refreshOpenApps()`. `initialize()`, `handleSocketMessage()`, `runInventoryMutation()` и профильные `refresh*Views()` внутренние и не являются обычным macro API.
- **Inventory organization routes:** private `RebreyaMainModule.#runInventoryOrganizationMutation(command, payload, validate, methodName)` обслуживает folder/item-membership и ingress-rule wrappers одним local/typed маршрутом: active GM вызывает `InventoryService` внутри `runInventoryMutation()`, прочие клиенты делают один `SocketCommandBus.request()` и только после success запрашивают scoped inventory refresh. Публичные class methods `getInventoryIngressRuleState(payload)`, `createInventoryIngressRule(payload)`, `updateInventoryIngressRule(payload)` и `deleteInventoryIngressRule(payload)` не владеют Actor state и не пишут его напрямую.
- **Inventory ingress dispatch:** private `RebreyaMainModule.#dispatchInventoryIngress({ command, payload, validate, execute })` локально проверяет exact serialized payload, клонирует его, извлекает точный Group Actor из `groupActorId` либо `target.groupActorId` и выполняет batch либо один раз через `runInventoryMutation()` на active GM, либо одной typed-командой с одним requester refresh. `#dispatchLootgenInventoryIngress()`, `#dispatchDirectInventoryIngress()`, партийные `claimStorageRow()`/`claimStorageAll()` и storage drag-import используют этот helper; non-party Storage сохраняет прежний маршрут. Active-GM handlers Storage и direct Lootgen/model оборачивают весь party batch одним `runInventoryMutation()`, а не каждую строку.
- **Куда править:** новую доменную операцию сначала реализуй в профильном сервисе; в `main.js` оставь валидацию входа, выбор local/socket route, вызов сервиса и точечный refresh.
- **Нельзя:** создавать второй composition root, помещать расчёты в hooks, регистрировать один hook в нескольких местах или добавлять новую привилегированную операцию в legacy socket switch.
- **Тесты:** `tests/main-composition-root.test.mjs`, `tests/module-manifest.test.mjs`, `tests/main-notifications.test.mjs`.

### 2. Active GM, typed sockets и надёжные мутации

- **Зачем:** сериализовать world-state, исключить двойное исполнение и безопасно выполнять player-инициированные операции на GM.
- **Владельцы:** application route и operation identity — `scripts/application/privileged-mutation-gateway.js`; active-GM election и typed transport — `scripts/infrastructure/foundry/active-gm.js` и `socket-command-bus.js`; очереди/replay — `scripts/application/world-mutation-coordinator.js`; durable multi-step recovery — `durable-mutation-journal.js`.
- **Gateway API:** `new PrivilegedMutationGateway({ commandBus, coordinator, gameProvider, getActiveGm, isActiveGmClient, operationIdFactory, maxTimeoutRetries = 1 })`; `registerCommand(command, { validate, authorize, execute })`; `mutate(command, payload, { operationId = "" } = {})`; `commit(queueKey, operation)`. `registerCommand` требует все три callback и запрещает пустые/повторные команды; `execute` получает frozen `{ command, operationId, requestId, sender, source, assertActiveGm }`. Если elected active GM отсутствует, `mutate` сразу отклоняется с `active-gm-unavailable` и не создаёт socket request/timer.
- **Typed outbound API:** `SocketCommandBus.request(command, payload, { requestId = "" } = {})`; непустой explicit string ID используется после trim, non-string ID отклоняется как `invalid-request`, а прежние двухаргументные callers продолжают получать ID из factory. Pending correlation остаётся уникальной по `requestId + command + userId`.
- **Протокол:** `rebreya.command` / `rebreya.command.result`; лимит envelope — 65 536 байт, timeout одной попытки — 10 секунд. Inbound bus сопоставляет envelope sender с authenticated transport sender, находит реального Foundry User, выполняет `validate → authorize → execute` только на elected active GM и сериализует intent на outer key `world`.
- **Gateway data flow:** `mutate` один раз клонирует payload и выбирает stable operation ID → выполняет client-side validation → elected active GM вызывает тот же registered executor напрямую через `runIdempotent("world", senderId + "\\0" + command + "\\0" + operationId, ...)` → любой другой GM/player вызывает typed `request(..., { requestId: operationId })` → authoritative boundary повторяет validation/authorization и передаёт только authenticated `sender` → domain result возвращается caller. Typed adapter не входит в outer `world` повторно.
- **No-active-GM route:** после client-side validation inactive client сначала проверяет наличие elected GM; при его отсутствии возвращает `active-gm-unavailable`, не вызывает typed transport и не создаёт timeout. Socket retry разрешён только когда initial elected-GM ID непустой.
- **Repository boundary:** `commit(queueKey, operation)` принимает только inner key (не `world`), проверяет election до входа и в начале setting queue, передаёт frozen `{ assertActiveGm }` и проверяет authority после operation. Inactive client не начинает operation; отказ первого operation guard до write сохраняет `active-gm-changed`, а потеря authority после успешного pre-write guard или потенциальной записи становится `PrivilegedMutationError` с code `ambiguous-outcome`.
- **Generic world-setting repository:** `new WorldSettingMutationRepository({ mutationGateway, gameProvider })` из `scripts/infrastructure/foundry/world-setting-mutation-repository.js`; composition создаёт ровно один экземпляр как `RebreyaMainModule.worldSettingMutationRepository` и injects его в writers global events и economy.
- **Object-setting API и data flow:** `readObject(settingKey, { normalize } = {})` возвращает detached normalized plain object (иначе `{}`). `mutateObject(settingKey, mutator, { normalize, afterCommit = null, shouldCommit = null } = {})` вызывает только `mutationGateway.commit("setting:<settingKey>", ...)`: внутри inner queue fresh читает Foundry setting, передаёт mutator только detached draft и нормализует detached committed object. Если optional `shouldCommit(result, detachedCommitted)` возвращает false, метод возвращает mutator result без `settings.set` и `afterCommit`; иначе делает один write, проверяет `assertActiveGm()` непосредственно до и после него и только затем вызывает `afterCommit(result, detachedCommitted)`. Ошибка mutator, write или post-write guard не вызывает `afterCommit` и не обновляет cache/model. `replaceObject(settingKey, value, options = {})` делегирует `mutateObject`, очищает все own keys fresh draft и присваивает detached normalized replacement, не вызывая `settings.set` напрямую.
- **Global-events commands:** `global-events.create { data }`, `global-events.update { eventId, patch }`, `global-events.delete { eventId }`, `global-events.duplicate { eventId }`, `global-events.import-defaults {}` определены в `global-events-mutation-commands.js`, принимают только exact serializable plain payload и авторизуют только authenticated GM. Они регистрируются через gateway: active GM выполняет их direct на outer `world`, остальные клиенты используют typed request; executor rebuilds economy model только после durable event-state commit.
- **Economy commands:** `economy.city-presentation.update { cityId, patch }`, `economy.connection.set-active { connectionId, isActive }`, `economy.reference.update-description { entryType, entryId, description }`, `economy.trade-route.update-metadata { connectionId, patch }`, `economy.state-policy.update { stateId, patch }`, `economy.world-data.reset {}` определены в `economy-mutation-commands.js`. Все принимают только exact safe-serializable plain payload; city/route/policy patch ограничены документированным non-empty whitelist, числа конечны, а `null` city field сбрасывает override. Каждый command авторизует только authenticated GM, выполняется gateway на outer `world`; inactive GM только запрашивает typed result и локально не пишет settings.
- **Trader public commands:** `trader.audit.record { operation }` и `trader.metadata.update { cityId, traderKey, patch }` определены в `trader-public-mutation-commands.js`. Audit принимает safe plain operation с Actor ID, авторизует GM либо OWNER этого Actor и executor передаёт в `TraderService.recordTradeAudit` только authenticated `context.sender.id`, игнорируя identity из payload. Metadata patch ограничен non-empty whitelist `portrait|description` и доступен только GM. Оба command выполняются gateway на outer `world`; legacy raw socket `trader-audit` не является mutation route.
- **Group registry commands:** `group.registry.register { groupActorId }`, `group.registry.activate { groupActorId }` и `group.inventory.merge-legacy { groupActorId }` определены в `group-registry-mutation-commands.js`. Каждый принимает exact один trimmed non-empty Actor ID и авторизует только authenticated GM. Gateway выполняет command на outer `world`; registry executor проверяет dnd5e group Actor и передаёт `context.assertActiveGm` в `GroupContextService`, а merge сохраняет прежний `runInventoryMutation()` path. Inactive GM и player всегда получают typed result, не начиная local Actor/setting write.
- **Downtime commands:** `downtime.weeks.grant { groupId, actorIds, weeks, reason, fromIsoDate }`, `downtime.weeks.revoke { groupId, actorIds, weeks, reason }`, `downtime.history.clear { groupId }`, `downtime.request.create { groupId, actorId, actionId, title, description, weeks, craftProject, targetActionSelections }`, `downtime.request.update { groupId, actorId, requestId, actionId, title, description, weeks, craftProject, targetActionSelections }`, `downtime.request.set-status { groupId, requestId, status, result }`, `downtime.request.set-checks { groupId, requestId, checks }`, `downtime.request.record-check { groupId, actorId, requestId, checkId, result }`, `downtime.project.continue { groupId, actorId, requestId, checkId, result }` и `downtime.project.close { groupId, actorId, requestId }` определены в `downtime-mutation-commands.js`. Grant/revoke/history/status/check assignment доступны только GM; остальные — GM либо OWNER exact character-member зарегистрированной managed-группы. Все используют gateway outer `world`, а `DowntimeService` — только inner `setting:groupState` queue; sender attribution добавляет executor, а не payload.
- **Идемпотентность и retry:** direct и typed используют один ключ `${sender.id}\u0000${command}\u0000${operationId}` на общем coordinator active-инстанса. Gateway допускает ноль или один automatic retry исключительно после `SocketCommandError.code === "request-timeout"`, повторяет тот же payload/ID и только при неизменном elected-GM ID. Второй timeout, election change либо post-write authority loss возвращает `ambiguous-outcome`; остальные ошибки не повторяются. Replay ограничен 256 completed results и lifetime текущего active-GM module instance.
- **Ingress-rule commands:** exact `inventory.ingress-rule.create|update|delete` принимают `groupActorId`, stable `operationId`, nonnegative safe `expectedRevision` и canonical exact rule либо `ruleId`; `normalizeInventoryIngressRule()` используется только для проверки каноничности payload, authoritative conflict/folder/revision validation остаётся в `InventoryService`. Все три команды используют ту же `#canSenderManageGroup()` матрицу (GM либо владелец character-member зарегистрированной целевой группы), transport sender binding и один refresh результата, что folder organization.
- **Куда править:** общую корреляцию — `socket-command-bus.js`; правила доступа — рядом с регистрацией команды; конкурирующую запись — в repository/coordinator; фазы восстановления — в journal/workflow.
- **Нельзя:** доверять `senderId` из payload, делать UI `get setting -> mutate -> set`, выполнять команду на неактивном GM, вызывать `mutate()`/outer key `world` из executor/repository, повторять timeout с новым ID или делать retry после election change. Batch 0 не мигрирует существующие domain writers.
- **Тесты:** `tests/world-setting-mutation-repository.test.mjs` (fresh inner-queue read, detached drafts/replacement, normalization, conditional no-write, write/guard ordering, failed mutation/write cache isolation и independent edits), `tests/privileged-mutation-gateway.test.mjs` (direct/typed route, authenticated authorization, no-active-GM fail-fast, stable retry ID, election refusal, commit guard), `tests/world-mutation-infrastructure.test.mjs` (coordinator, active GM, typed transport и explicit request ID), `tests/group-command-dispatch.test.mjs` (включая exact downtime schemas, GM/OWNER matrix, sender attribution, inactive no-local-write и ignored raw downtime request), `tests/main-composition-root.test.mjs`, `tests/durable-mutation-journal.test.mjs` и `tests/security.test.mjs`.

### 3. Экономика, города, товары и торговые маршруты

- **Зачем:** загрузить каноническую модель мира и рассчитать снабжение, спрос, цены, связи и аналитические snapshots без UI-зависимостей.
- **Владельцы:** чтение/кэш — `scripts/data/repository.js` (`EconomyRepository`); presentation overrides — `scripts/data/city-presentation-overrides.js` и тот же repository; расчёты — `scripts/engine/economy-engine.js`; представления — `scripts/engine/selectors.js`.
- **Источники:** `data/goods.json`, `regions.json`, `cities.json`, `reference.json`, `materials.json`, `gear.json`; 300 базовых city panoramas — tracked WebP в `assets/cities/`. `cities.json` и `tools/import-xlsx.ps1` используют только runtime-путь `modules/rebreya-main/assets/cities/<имя города>.webp`, поэтому public City view не зависит от Foundry Data/assets вне модуля. `normalizeCities()` принимает source-поля `image`/`img` и сохраняет канонический путь в city model вместе с `description`; presentation read model получает оба поля уже из нормализованной модели. Runtime overrides живут в world settings, а не переписывают source JSON. Hidden world setting `cityPresentationOverrides` хранит только непустые отличия `description`/`image` известных городов и возвращается detached после нормализации.
- **Внешние методы:** `getCitySnapshot(cityId)`, `getPublicCitySnapshot(cityId)`, `getPublicEconomySnapshot()`, `getCityPresentation(cityId)`, `updateCityPresentation(cityId, patch = {})`, `resetCityPresentation(cityId, fields = ["description", "image"])`, `getTradeRouteSnapshot(connectionId)`, `getTradeRouteBaseSnapshot(connectionId)`, `getTradeRoutes()`, `hasTradeRouteAnalytics()`, `prepareTradeRouteAnalytics({ rerender })`, `setConnectionActive(connectionId, isActive)`, `updateTradeRouteMetadata(connectionId, patch)`, `getReferenceEntrySnapshot(entryType, entryId)`, `updateReferenceDescription(entryType, entryId, description)`, `updateStatePolicy(stateId, patch)`, `resetWorldData({ notify })`.
- **Presentation repository:** `new EconomyRepository({ worldSettingMutationRepository })` получает единственный writer; private `#mutateObjectSetting(key, mutator, options)` делегирует только `WorldSettingMutationRepository.mutateObject`. `getCityPresentationOverrides()`, `getCityPresentations()`, `getCityPresentation(cityId)` остаются detached reads. `updateCityPresentation(cityId, patch = {})` применяет patch к fresh normalized `cityPresentationOverrides` draft; `null` и пустая строка удаляют override поля и восстанавливают source value, неизвестный `cityId` отклоняется. `setConnectionActive`, `setReferenceNote`, `setTradeRouteOverride` и `setStatePolicy` аналогично меняют только fresh draft соответствующего object setting и rebuild model/cache только через successful `afterCommit`. `resetWorldData()` последовательно вызывает `replaceObject(key, {})` для пяти economy settings и только после всех successful writes rebuilds model.
- **Public read models:** `buildPublicCitySnapshot({ model, city, presentation, traders, tradersError })`, `buildPublicEconomySnapshot(model, cityPresentations = {})`, `selectPublicCityRows(cities, filters)`, `buildPublicFilterOptions(cities, selectedState = "all")` из `scripts/application/public-economy-read-model.js`. Городской `materialRows` включает только материалы с непустым `linkedGoodId`, то есть связанные с обычным товаром городской экономики; material price/weight для оставшихся строк делегирует `getMaterialPriceModifier()` и `applyMarketPrice()` Trader Engine. Общий public economy snapshot остаётся полным и берёт base price/weight из materials и мировой deficit из `model.overview.deficitGoods`. Player projections не содержат production/demand/balance/surplus, процентные modifiers, routes, policies, events или audit.
- **UI:** `scripts/ui/economy-app.js`, `city-app.js`, `trade-routes-app.js`, `trade-route-app.js`, `reference-info-app.js` и одноимённые templates.
- **Куда править:** формулу — engine; нормализацию исходников — repository/data importer; shape карточки — selector/UI; persisted override — composition method + setting/repository.
- **Composition flow:** public reads получают модель/repository presentation и возвращают detached safe read model; ошибка trader summaries локализуется в `tradersError`. `updateCityPresentation` и `resetCityPresentation` используют один `economy.city-presentation.update` command; после authoritative результата вызывают только `refreshCityViews({ cityIds: [cityId] })`, а reset с пустым списком разрешённых полей не пишет setting. Остальные economy writers route через свои exact gateway commands, затем сохраняют прежний scoped refresh/return shape. `resetWorldData` использует `economy.world-data.reset`: outer `world` intent сначала reset trader state, затем sequentially resets five economy settings; atomic rollback между settings не обещается.
- **Нельзя:** считать цену в template/UI, мутировать snapshot или смешивать source data с world override.
- **Тесты:** `tests/city-normalizer.test.mjs` фиксирует перенос source panorama в нормализованную city model; `tests/city-public-assets.test.mjs` проверяет 300 путей и точное множество module-owned WebP без внешней папки Data/assets; `tests/city-presentation-overrides.test.mjs` проверяет city patch normalization и exact economy command validators; `tests/group-command-dispatch.test.mjs` проверяет GM authorization, inactive-GM typed route without local setting write, independent economy patches и sequential reset; `tests/economy-city-connections.test.mjs`, `tests/public-economy-read-model.test.mjs`, профильные tests сервисов/окон, `tests/main-composition-root.test.mjs` для composition wiring и `tests/ui-refresh-coordinator.test.mjs` для scoped city refresh.

### 4. Глобальные события и политики государств

- **Зачем:** накладывать датированные модификаторы на города, товары, маршруты, государства и категории торговцев.
- **Владелец:** `scripts/data/global-events-service.js` (`GlobalEventsService`); persisted state — `globalEventsState`, draft — `globalEventsDraft`, политики — `statePolicies`.
- **Чтение:** `getAllGlobalEvents()`, `getActiveGlobalEvents(currentDate)`, `getEventsAffectingCity(cityId, currentDate)`, `getEventsAffectingCityGood(cityId, goodId, currentDate)`, `getEventsAffectingRoute(fromCityId, toCityId, currentDate, connectionId)`, `getEventsAffectingState(stateId, currentDate)`, `getStatePolicies()`, `getEffectiveStatePolicy(stateId, targetStateId, currentDate)`.
- **Мутации:** `createGlobalEvent(data)`, `updateGlobalEvent(id, patch)`, `deleteGlobalEvent(id)`, `duplicateGlobalEvent(id)`, `importDefaultGlobalEventTemplates()`, `updateStatePolicy(stateId, patch)`. Первые пять route через exact gateway-команды; `GlobalEventsService` применяет create/update/delete/duplicate/import и calendar activation как patch к fresh `globalEventsState` в `WorldSettingMutationRepository` queue `setting:globalEventsState`. Private `#mutateGlobalEvents(mutator, { commitWhenChanged = false } = {})` включает conditional commit для calendar activation: unchanged result не обновляет state/event timestamps и не пишет setting. `refreshEventActivationByDate(currentDate, previousDate)` на non-active client возвращает unchanged result до repository queue. Дубликат не вызывает create внутри той же очереди. Cache invalidates/обновляется только через `afterCommit`; ошибка domain/write/authority не меняет cache.
- **UI:** `scripts/ui/global-events-app.js`, `states-app.js`; composition handler `handleGlobalEventsConfigChange()` инвалидирует кэш/обновляет нужные окна.
- **Куда править:** фильтры/эффекты/видимость — `GlobalEventsService`; форму и GM controls — UI/template; настройку — `scripts/main.js` registration и config-change handler.

### 7. Партийный инвентарь, валюты и припасы

- **Зачем:** управлять предметами/валютой/припасами активной группы и переносами к персонажам с recovery после частичной записи.
- **Владелец:** `scripts/data/inventory-service.js`; чистая логика папок без собственного состояния — `scripts/data/inventory-folder-tree.js`; hook reconciliation — `scripts/integrations/inventory-sync.js`; UI — `scripts/ui/inventory-app.js`.

- **Чистая модель ingress-правил:** `scripts/data/inventory-ingress-rules.js` публикует `INVENTORY_INGRESS_RULES_VERSION = 1`, frozen `INVENTORY_INGRESS_RULE_FIELD_DEFINITIONS` и `InventoryIngressRuleError(code, details)`. `createEmptyInventoryIngressRuleState()`, `normalizeInventoryIngressRule(rule)`, `normalizeInventoryIngressRuleState(rawState)` и `describeInventoryIngressRule(rule)` принимают только exact plain-data schema, канонизируют typed enum/identity/number/boolean operands и folder/skip/dismantle actions, не мутируют input и возвращают deeply frozen detached data; отсутствующий flag означает revision `0`. `findInventoryIngressRuleConflicts(rules)` консервативно пересекает constraints и считает потенциальное пересечение конфликтом, причём dismantle семантически добавляет `dismantlable is true`. `compileInventoryIngressRules(state)` отвергает конфликтное состояние и возвращает immutable `candidateRuleIds(descriptor)`/`evaluateMany(descriptors)` с максимум одним detached решением; missing descriptor field не удовлетворяет даже отрицательному условию. `InventoryIngressRuleCompilerCache.get(groupActorId, state)` кэширует compiled engine по точной паре group Actor/revision, а `clear(groupActorId = "")` сбрасывает одну группу либо весь cache. Индекс exact `sourceType + sourceId` и положительных discrete constraints ограничивает candidate union до numeric/negative evaluation без полного `rules × rows` прохода; helper не читает Foundry globals, sockets или world-state. Focused owner test: `tests/inventory-ingress-rules.test.mjs`.
- **Canonical ingress descriptor и dismantle:** `scripts/data/inventory-ingress-descriptor.js` без Foundry globals публикует `buildInventoryIngressDescriptor(itemData, { model, dismantlable? } = {})`, `captureInventoryIngressIdentity(descriptor, quantity)`, `canResolveInventoryDismantle(itemData, { model } = {})` и `resolveInventoryDismantleOutputs(itemData, quantity, { model } = {})`. Проекция возвращает deeply frozen plain data с `ordinary|magic|material`, стабильной identity только из managed source flags/model ID, D&D5e type/subtype, category/rarity/rank, durability state, integer copper и unit pounds; source origin и presentation name в identity не входят. Cheap eligibility проверяет positive unit weight, non-container/non-material source и stable material profile без расчёта quantity; full resolver отдельно применяет текущую формулу `floor(unitWeight × quantity × 50% × 100) / 100` и возвращает frozen material outputs. `InventoryService.breakItemToMaterial(itemId, quantity)` остаётся явной операцией над старым Item, но делегирует тому же full resolver, материализует output через существующие `#buildMaterialItemData()`/`#upsertInventoryItem()` и больше не разрешает материал по имени. Focused tests: `tests/inventory-ingress-descriptor.test.mjs`, `tests/inventory-mutation-recovery.test.mjs`.
- **Application ingress planner:** `INVENTORY_INGRESS_PLAN_VERSION = 1`, `InventoryIngressPlanError(code, details)`, pure `isValidSerializedInventoryIngressPlan(plan)` и `InventoryIngressPlanner({ readRules, buildDescriptor, resolveDismantleOutputs, compilerCache, confirm })` находятся в `scripts/application/inventory-ingress-planner.js`. Валидатор принимает только exact wire-shape, canonical IDs/actions/identity, unique source/override keys и quantity parity; его совместно используют inventory, Lootgen и Storage typed payloads. Async `preview({ groupActorId, requestedFolderId = null, rows, batch = false })` принимает только exact detached rows `{ sourceKey, quantity, itemData, legacyFolderId, container }`, один раз читает rule state/cache/evaluateMany, асинхронно дожидается ровно одного descriptor на Item row и вызывает async-capable full dismantle adapter только для matched dismantle; результат deeply frozen и содержит captured identity, action `legacy|folder|skip|dismantle`, rule ID и non-authoritative presentation. `collectChoices(preview)` не открывает UI для folder/no-match/batch-skip, делегирует ровно один confirmation для single skip либо всех dismantle rows и возвращает только validated root override keys. `serialize(preview, { rootOverrideSourceKeys = [] } = {})` удаляет ItemData/material preview и сохраняет exact identity/match/action expectations; `assertParity(serializedPlan, authoritativePreview)` требует их полного совпадения и возвращает `plan-stale` при revision/source/quantity/target/rule/action drift. Planner не пишет state, не вызывает socket/render и не доверяет material output из serialized plan. Terminal retry возвращает сохранённый outcome до source resolve; новый/nonterminal commit вызывает `resolveRows({...request,recovering:Boolean(record)})`, один раз строит authoritative preview и требует `assertParity()`, существующую derived folder и неизменный dismantle output. - **Личное раскрытие:** `getInventoryFolderUiState(groupActorId, folderIds = []) -> { version: 1, groupActorId, expandedFolderIds }` читает только `game.user.flags["rebreya-main"].inventoryFolderUi` и фильтрует отсутствующие папки. `setInventoryFolderExpanded(groupActorId, folderId, expanded)` сериализует по `inventory-folder-ui:<userId>`, внутри очереди повторно читает live Actor folders и свежий User flag, сливает один toggle, удаляет stale ID и делает одну `User.setFlag()`; Actor, world settings и sockets не затрагиваются. `RebreyaMainModule` проксирует оба метода локально без active-GM route.
- **Надёжность:** canonical ingress record отклоняет повтор batch ID с другим plan/origin/group fingerprint. Target receipt записывается до Item mutation; write-then-throw create обнаруживается по ingress marker, merge — по exact before/after quantity. Folder flag пишется после всех targets и до первого source debit; lost flag acknowledgement сверяется с normalized live state. Ошибка source adapter оставляет target/folder receipts nonterminal, поэтому повтор продолжает debit без второго target delta; terminal retry не вызывает resolver/planner/debit. При drift rules/source/folder/material nonterminal record возвращает `reconciliation-required`, а не применяет новую ценность. Старые craft/manual dismantle/material recovery paths не вызывают ingress planner.
- **Storage target flow:** `claimStorageRow(..., request)` и `claimStorageAll(..., request)` для `destination:"party"` получают fresh storage snapshot, проецируют только unclaimed Item/container rows через private `#buildStorageInventoryIngressRows()`, один раз вызывают `#prepareStorageInventoryIngress()`/choice dialog и добавляют exact `ingressPlan`; cancel возвращает `null` без direct/socket dispatch. Затем общий `#dispatchInventoryIngress()` выполняет ровно один local batch либо одну typed-команду и один scoped refresh. Typed authorize сохраняет прежнюю GM/member permission matrix. Coins и Journal rows в planner не входят. `StorageApp.#onClick()` не закрывает popover и не refresh-ит snapshot при cancel/stale error, поэтому следующий action строит fresh plan.
- **Exact storage currency target:** `InventoryService.addCurrencyToInventoryOnce(coins, mutationId, { groupActorId = "" } = {})` при непустом ID live-разрешает именно этот managed group Actor и передаёт его в `#executeAddCurrencyOnce(coins, mutationId, { actor?, groupActorId? })`; fallback на current group остаётся только для вызовов без exact target. Новый глобальный hook, coordinator или refresh entrypoint не создаётся.

- **Filtered party claim:** `LootClaimService({ ..., grantBatch })` публикует `claimBatch({ messageId, lootId, claimId, rowIds, includeCoins, ingressPlan })`; `claimRow()`/`claimCoins()` — compatibility delegates к тому же batch state machine. Сервис один раз читает trusted ChatMessage state под `loot-claim:<messageId>`, durably связывает fingerprint `lootId+rowIds+includeCoins+plan`, вызывает один idempotent `grantBatch`, сохраняет receipt и помечает claimed только returned `acceptedRowIds`; filtered skip остаётся доступным. Lost ChatMessage acknowledgement сверяется повторным read, terminal retry возвращает compact result, другой request с тем же claim ID блокируется. Composition grant один раз вызывает `InventoryService.commitInventoryIngressBatch()` для Item rows, отдельно выдаёт coins stable mutation ID без descriptor и затем одним ChatMessage update фиксирует принятые строки/coins.
- **Typed batch routes:** `inventory.ingress.lootgen` принимает exact `{ batchMutationId, groupActorId, lootId, rowIds, includeCoins, ingressPlan }`, не принимает message ID/ItemData/material outputs и требует полного совпадения plan source keys с unique row IDs. `inventory.ingress.direct` принимает exact `{batchMutationId,coins,groupActorId,ingressPlan,sourceOrigin,sources}` с origin `lootgen|public-model`; source содержит только stable IDs, quantity и broken marker. Sender должен быть GM либо владельцем character-member зарегистрированной target group. Chat route повторно находит GM-authored trusted Lootgen ChatMessage; direct route на active GM заново строит ItemData по source IDs и выполняет authoritative plan parity. `claimLootgenChatRowToInventory()`, `claimLootgenChatAllToInventory()` и прямая выдача Lootgen/model собирают decisions один раз и выполняют один local active-GM commit либо один typed request. `runInventoryMutation()`/requester refresh вызывается один раз на batch, per-row public sockets/renders отсутствуют. Монеты прямого Lootgen добавляются в той же command execution с отдельным idempotent currency receipt и никогда не входят в matcher. Cancel не отправляет команду; stale error не меняет источник и следующий click строит новый preview.

### 14. Прочность, разрушение и upgrades

- **Зачем:** нормализовать durability, применить повреждение/поломку/уничтожение и устанавливать upgrades в пределах capacity.
- **Владельцы:** legacy/item durability — `scripts/data/durability-service.js`; native dnd5e objects — `native-object-durability-service.js`; rules — `durability-rules.js`; derived Item name — `durability-item-presentation.js`; upgrades — `item-upgrade-service.js`.
- **Внешние методы:** `initializeItem()`, `getOrBuildDurability(item, { sourceType?, sourceId? })`, `getOrBuildBrokenDurability(item, { sourceType?, sourceId? })`, `damageItem()`, `damageDurabilityTarget()`, `resolveDurabilityOutcome()`, `breakItem()`, `destroyItem()`, `getDurability()`, `isBroken()`, `installItemUpgrade(hostItem, upgradeItem, options)`, `removeItemUpgrade()`, `setItemUpgradeCapacity()`.
- **Data flow durability:** `getOrBuildDurability()` сначала проверяет eligibility, затем возвращает plain clone существующего flag (включая damage/broken state и timestamp) либо строит initial flag из model gear, material, construction и size. `getOrBuildBrokenDurability()` применяет к этому clone существующий `markDurabilityBroken()` и service timestamp и возвращает canonical `state:"broken"`, `breakStage:1`, `hp.value:0` без commit. Оба метода — чистые derive-paths: не вызывают `item.update`, delete, hooks, journals и не меняют source document; corpse materializer использует broken derive только для canonical body armor clone. `initializeItem()` для normal path использует тот же результат и делает один update только для отсутствующего flag; `force: true` строит initial flag заново private builder. `StorageCommandService.#prepareGroundRow()` — consumer чистого derive-path: перед расходованием world/compendium/embedded Item либо перед scene-transfer storage row он переносит clone результата только в cloned ground row, не обновляя исходный Item/row; existing damaged flag сохраняется точно, а `null` очищает stale durability в clone, чтобы ineligible ground row не попала в native HP/AC projection. Только точный `storageCoinTemplate:{version:1,denomination}` с canonical `pp/gp/sp/cp` исключает managed Coin Items из durability; `sourceType` сам по себе, другая версия и malformed/unknown denomination не исключают ordinary loot.
- **Broken name projection:** `formatDurabilityItemName(name, durability)` — чистый идемпотентный formatter: только canonical `state:"broken"|"destroyed"` при `eligible !== false` добавляет один suffix ` (сломан)`, intact снимает managed suffix, отсутствие flag не меняет имя. `CorpseStorageMaterializer`, `applyLootgenBrokenDurability()`, `StorageApp._prepareContext()` и persisted `InventoryService.buildLootgenItemData()` используют его без изменения source Item; поэтому уже сохранённая corpse row видна как сломанная и создаёт у персонажа Foundry Item с тем же flag и suffix. `DurabilityService.#commitUpdate()` добавляет `name` в тот же Item update только при реальном изменении derived имени, поэтому `breakItem()` синхронизирует предмет персонажа без второго broken-флага.
- **Corpse projection recovery:** `reconcileNativeObjectDurability()` на active GM сначала удаляет ошибочную legacy object projection только у Scene Token с complete corpse marker и `objectDurability`: снимает object flag/AC/max/DT override, возвращает corpse HP к `0`, восстанавливает bar1 из Actor prototype и сохраняет storage rows/marker; затем штатно reconciles только настоящие chests/piles. Player не выполняет эту world-state migration.
- **Typed command:** `durability.target.damage`; mutation journal — hidden setting durability journal, зарегистрированный composition root.
- **Integrations/UI:** `scripts/integrations/durability-hooks.js`, `item-upgrade-sheet.js`, `scripts/ui/durability-outcome-dialog.js`.
- **Куда править:** формулы/thresholds — rules; routing native/legacy — integrations; Actor/Item mutation — соответствующий service; sheet controls — integration/UI.
- **Нельзя:** одновременно маршрутизировать Item в native и legacy service, уничтожать без outcome/recovery path или считать UI capacity authoritative.
- **Тесты:** `tests/durability-*.test.mjs` (включая non-mutating derivation, existing-flag precedence и Coin exclusion), `native-object-durability-service.test.mjs`, `native-durability-*.test.mjs`, `item-upgrade-service.test.mjs`.

- **Economy view flow:** `EconomyApp._prepareContext()` для player сразу вызывает `getPublicEconomySnapshot()`, фильтрует только через `selectPublicCityRows`/`buildPublicFilterOptions` и не запрашивает mechanical model, summaries, events или audit; GM сохраняет прежний analytics context. Existing Economy tool в группе Scene Controls видим всем ролям при `showEconomyButton`, тогда как Groups/Cosmology/Lootgen остаются GM-only; карточки вызывают канонический `openCityApp(cityId)`.
- **Travel entrypoints:** кнопки исходного и конечного города в сводке маршрута используют существующий `travel-open-city` handler и вызывают тот же `openCityApp(cityId)`; отдельный listener, City app или проверка текущего местоположения не создаются.
- **Presentation UI adapters:** `resolveCityViewMode({ isGM = false, requestedMode = "admin" } = {})`, `promptCityDescription({ city, dialogClass } = {})`, `openCityImagePicker({ current = "", pickerClass, onSelected, onError } = {})` из `scripts/ui/city-presentation-ui.js`. Они собирают/нормализуют пользовательский ввод, но не пишут setting; GM mutation выполняют composition API `updateCityPresentation`/`resetCityPresentation`.
- **Refresh:** private `#appRefreshTask(app, { refreshInventorySnapshot, ...renderOptions })` пропускает закрытые/свёрнутые приложения и для inventory вызывает cache-invalidating `refreshInventorySnapshot()` внутри прежнего `UiRefreshCoordinator`; остальные окна продолжают идти через `rerenderApp(..., { focus: false })`. `#flushInventoryViews()` выбирает main и composition-owned folder popouts по `inventoryActorId`/explicit group fallback, дедуплицирует instances, добавляет только Actor sheets из затронутых Actor IDs и сохраняет `preserveScroll: true`. `refreshInventoryViews({ actorIds })` остаётся единственным inventory refresh-route и объединяет IDs/waiters с `runInventoryMutation()` hold boundary; background refresh не поднимает окно и не крадёт focus.
- **Внутренние refresh entrypoints:** `refreshInventoryViews({ actorIds })`, `refreshDowntimeViews({ actorIds })`, `refreshCosmologyViews()`, `refreshCityViews({ cityIds = [] } = {})`, `refreshOpenApps()`. `refreshCityViews` выбирает только канонические instances из единственного `cityApps` cache, пропускает закрытые/свёрнутые окна и рендерит без focus. Entry points вызываются после authoritative mutation result и не являются доменными командами.
- **Куда править:** context shape — UI adapter/selector; markup — HBS; theme/layout — CSS; cross-window scheduling — refresh coordinator/composition helper.
- **Нельзя:** писать world settings из UI, хранить единственную копию state в app instance, вызывать массовый `render()` или создавать parallel app для compatibility entrypoint.
- **Тесты:** `tests/ui-refresh-coordinator.test.mjs` (включая scoped city selection), `tests/main-composition-root.test.mjs`, `tests/city-public-ui.test.mjs`, `tests/economy-public-ui.test.mjs`, `tests/bg3-hotbar-compat.test.mjs`, `background-refresh-focus.test.mjs`, `style-theme.test.mjs` и профильные `*-app-context.test.mjs`/`*-ui.test.mjs`.

### 20. Диагностика и выбор точки реализации

- **Нет API:** проверь manifest entrypoint, ошибки `ready`, `game.modules.get("rebreya-main")?.api` и `tests/main-composition-root.test.mjs`.
- **Не записалось состояние:** найди owner setting/repository, active GM, command validation/authorization, operation ID и journal phase. `reconciliation-required` требует ручной сверки.
- **Не обновился UI:** найди authoritative mutation result и соответствующий `refresh*Views`; не лечи это глобальным render.
- **Не сработала automation:** проверь identifier/sourceType/runtime flags, recipe/version, Actor ownership, dnd5e/MIDI hook и registry diagnostics через `getSpellAutomationDiagnostics()`.
- **Не синхронизировался pack:** проверь active GM, managed/source/signature flags, stable ID collision и dependency order.
- **Как выбрать тест:** owner service → `<owner>.test.mjs`; typed command → `*-socket`/`*-command-dispatch`; recovery → `*-recovery`/transaction; UI → `*-app-context`/`*-ui`; compatibility → одноимённый integration test.
