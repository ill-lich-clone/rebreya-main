# Синхронизация снаряжения и покрытие расходов припасов

Дата: 2026-07-26
Статус: дизайн подтверждён

## Цели этапа

1. Сделать `Общий компендиум снаряжения V0.1` источником истины для готовых предметов.
2. Обогащать готовые предметы механикой из профильных листов, не создавая параллельные документы.
3. Сохранить материалы как отдельный физический слой и связать готовые предметы с материалами стабильными идентификаторами.
4. Удалять дубли только внутри управляемого компендиума снаряжения.
5. Добавить для группового инвентаря независимое покрытие расходов еды и воды.

## Границы этапа

В этап не входят:

- изменение предметов, уже находящихся у персонажей;
- транспорт;
- изменение формулы крафта;
- автоматизация прочих перечисленных игровых механик.

Для будущей переработки крафта зафиксировано правило: количество порций материала рассчитывается как цена готового продукта, делённая на цену порции материала, с округлением вверх. На этом этапе применяется только корректная связь продукта с материалом.

## Два слоя предметных данных

### Материалы

`Энциклопедия материалов` описывает физические порции сырья:

- название;
- тип и подтип;
- цена порции;
- вес порции;
- ранг;
- описание и области применения.

Материалы синхронизируются в отдельный управляемый компендиум материалов.

### Готовые продукты

`Общий компендиум снаряжения V0.1` определяет существование и базовую идентичность готового продукта:

- название;
- тип снаряжения;
- магазинный подтип;
- цена;
- вес;
- ранг;
- краткое описание;
- связанный инструмент;
- преобладающий материал.

Только строка общего листа может создать готовый продукт. Строка профильного листа без соответствующего базового продукта считается ошибкой данных и не создаёт самостоятельный документ.

## Обогащение механикой

Профильные листы дополняют базовый продукт типизированными блоками:

- `Оружие V0.36` → `weapon`;
- `Огнестрел V0.36` → данные огнестрела внутри механики оружия;
- `Усовершенствования V0.21` → `upgrade`;
- `Импланты V0.1` → `implant`.

Импорт строит единый нормализованный объект готового продукта. Базовые поля всегда берутся из общего листа; профильный лист не должен перезаписывать базовую цену, описание или идентичность предмета.

## Сопоставление строк

Сопоставление выполняется в следующем порядке:

1. явный канонический ключ из справочника;
2. стабильный идентификатор ранее известного продукта;
3. нормализованное имя готового продукта;
4. специально определённая связь профильной строки с материалом — только для форматов, где профильный лист называет исходный материал вместо готового продукта.

Резервное сопоставление допускается только при единственном кандидате. Неоднозначные, потерянные и осиротевшие строки попадают в отчёт импорта и не объединяются молча.

Пример:

- материал `Сухожилие чудовища` остаётся отдельной порцией сырья за 125 зм;
- продукт `Сухожилие чудовища` остаётся готовым усовершенствованием за 250 зм;
- строка листа усовершенствований добавляет механику к готовому продукту;
- одинаковые отображаемые названия в разных компендиумах не являются дублем.

## Синхронизация компендиума

Управляемый синк использует стабильный идентификатор готового продукта:

- один базовый продукт создаёт не более одного документа в `world.rebreya-gear`;
- изменившиеся управляемые документы обновляются;
- отсутствующие в актуальном источнике управляемые документы удаляются;
- неуправляемые документы не затрагиваются;
- документы Actor/owned Items не сканируются, не обновляются и не удаляются.

В Quick Insert одинаковые названия материала и продукта должны различаться контекстом компендиума и типом, а не удалением одного из объектов.

## Покрытие расходов еды и воды

В групповом инвентаре добавляются два независимых переключателя:

- `Покрыть расходы еды`;
- `Покрыть расходы воды`.

Пока переключатель активен:

- соответствующий суточный расход равен нулю;
- запас не списывается при смене дня;
- прогноз оставшихся дней не показывает ложное истощение;
- предварительный просмотр перехода календаря использует нулевой расход;
- итоговое сообщение отражает фактически нулевое списание.

Переключатели сохраняются в данных группы. Изменять их могут GM и владельцы группового склада через существующий авторизованный путь мутаций и сокетов.

## Проверки и ошибки

Синхронизация должна проверять:

- уникальность идентификаторов базовых продуктов;
- отсутствие дублей канонических ключей;
- существование связанных материалов;
- однозначность сопоставления профильных строк;
- отсутствие профильных строк-сирот;
- сохранение базовых полей после обогащения.

Ошибки данных должны завершать генерацию понятным отчётом до изменения управляемого компендиума.
