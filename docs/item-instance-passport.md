# Частичные переносы и экземпляры предметов

Канонический индекс: [паспорт функций](function-passport.md), разделы inventory, UI и application infrastructure. Runtime: Foundry 13, dnd5e; изменения доступны с 1.4.249.

## Правила и журнал

- `planItemInstanceMutation({source,quantity,sameActor,sameFolder,forHeroSlot})` (`scripts/data/item-instance-rules.js`) возвращает `{kind,quantity,sourceRemaining,preserveSourceId}`. `source` содержит quantity, step и признаки индивидуального состояния. Расчёт целыми единицами с масштабом 100000; обычные вещи step=1, материалы step=0.00001. Same-folder/no-op и whole membership сохраняют ID. Partial split запрещён для содержимого, установленных upgrades, charges/effects (включая формулы max и activity uses), attuned, повреждённой прочности, equipped/held. `ItemInstanceError(code,message)` несёт объяснимый код отказа. Тест: `item-instance-rules.test.mjs`.
- `DurableMutationJournal.listPending()` возвращает detached nonterminal records под существующей journal queue; новых world settings нет. Retention прежний: ограничиваются terminal records, незавершённые сохраняются.
- `itemInstanceFingerprint(value)` (`scripts/application/item-instance-workflow.js`) канонизирует JSON-like intent, сортируя ключи объектов; порядок массивов значим.
- `ItemInstanceWorkflow({journal,coordinator,documents}).run(intent,context)` сериализует затронутые Actors по отсортированным `inventory-organization:<actorId>`. Operation key включает authenticated sender, action/mode и operationId; fingerprint включает весь intent. Сначала journal lookup и Actor authorization, затем fresh source; terminal replay работает без удалённого source Item. Чужой fingerprint запрещён. Незавершённый item-instance record блокирует новые операции с теми же Actors.
- Intent: `{operationId,sourceActorUuid,sourceItemId,destinationActorUuid,quantity,targetFolderId,heroSlotId,expectedSourceQuantity}`. Folder и hero target не могут одновременно быть non-null. Внутренний hero intent добавляет `mode: assign|clear|normalize`. Для clear/normalize quantity=null в immutable intent; `context.planSource(source,intent)` вычисляет количество под очередью до первого write. Клиент не выбирает policy overrides.
- Context: `{sender,assertAuthority,authorize,preparePlacement,planSource?,prepareTargetData?,moveWhole?,verifyWhole?}`. `authorize(actors,intent)` проверяется при retry; при новой операции получает также fresh source. `planSource` может уточнить pure planner options. `prepareTargetData(data,source)` готовит только detached clone до journal.start. `preparePlacement(source)` возвращает список `{actor:source|target,itemId?,before,after}` с разрешёнными dotted field paths. Не пишет Documents.
- `#run` сохраняет prepared data до writes, затем target-created → source-debited → placement-written → committed. `#guarded(context,operation)` проверяет authority до/после каждого journal/Document write. При смене GM старый клиент не компенсирует. Terminal journal write находится после Document transaction: отказ сохранения terminal receipt не откатывает уже выполненную операцию.
- `#compensate(record,context,error)` сохраняет compensating, отменяет только доказанно принадлежащие операции изменения, записывает compensated/terminal failure. Конфликт переводится в nonterminal manual-review с failure/compensationFailure diagnostic, без повторной выдачи. Whole transfer rollback принадлежит делегированному владельцу; после неоднозначного whole outcome worker требует сверки.

## Foundry driver

`ItemInstanceDocuments({resolveActor=fromUuid})`, файл `scripts/infrastructure/foundry/item-instance-documents.js`, не хранит отдельного world state.

- `readActors(intent)` разрешает source/target заново. `readSource(intent,actors)` возвращает refs, detached ItemData, quantity/step/folder и complex-state policy DTO. Поддерживаются world Actor UUIDs; synthetic sheet не является новым самостоятельным маршрутом переноса.
- `prepare(intent,plan,source,context,operation)` очищает clone через внутренний `cleanClone(data)`: убирает document identity и прежние transfer receipts, сохраняет пользовательские flags/metadata. Назначает deterministic target ID, origin fingerprint, source quantity/marker snapshots и placement patches. Whole delegate использует placeholder `$target` до получения его receipt. Для cross-Actor split сбрасывает native container reference.
- `createTarget(record,context)` сверяет exact ID и `itemInstanceOrigin`, создаёт один Item с keepId либо вызывает whole owner. `debitSource` пишет quantity и replacement `itemInstanceDebit` одним Item update; повтор сверяет receipt. `#write` проверяет authority до/после write.
- `writePlacement` проверяет before/after только owned fields; повтор already-after не пишет. `#substitute` заменяет `$target` в IDs/paths/value после whole receipt; `#placementDocument` разрешает document; `#readFields` читает touched paths; `#update` переводит null в `-=`, объекты в `==` replacement, массивы/скаляры сохраняет. Hero slots не оставляют merge leftovers.
- `verifyCommitted` сверяет source/target quantity, debit marker и placement; для whole вызывает `verifyWhole`, одного отсутствия source недостаточно.
- `compensate` сначала сверяет все touched fields и target metadata. Чужие edits или missing target после debit требуют manual-review. Затем обратным порядком восстанавливает placement, source quantity/marker и удаляет только свой неизменённый target. Весь Actor snapshot не восстанавливается.

## Владельцы поведения и UI

- `InventoryService.moveInventoryItemToFolder({groupActorId,itemId,folderId=null,quantity?,operationId?,expectedSourceQuantity?},{sender=game.user}={})`: без quantity прежний whole membership reducer; с quantity — worker на существующих mutationJournal/coordinator. Повторно проверяет membership/OWNER, папку и optimistic quantity. Возвращает worker result плюс `{actorId,folderId}`. `isValidInventoryItemFolderMovePayload` в main оставляет exact legacy schema и расширенную exact schema с обязательным operationId. Registry executor передаёт authenticated sender вторым argument; структурированные recovery errors сохраняют code.
- `promptInventoryPartialTransfer({quantity,step=1,folders=[],folderId=null,chooseFolder=false})` в `inventory-app.js` возвращает `{quantity,folderId}` только после explicit confirm и проверки шага/папки; cancel/close → null. Cancel работает и при невалидном input. Shift+internal drop и «Перенести часть…» вызывают один диалог; обычный drop и external ingress сохраняют прежний путь.
- `InventoryApp.#transferInventoryPart(itemId,folderId,{chooseFolder,snapshot,groupActorId})` захватывает свежий group/item/target до await и создаёт operationId один раз. `#submitPartialTransfer(payload)` сохраняет pending intent до подтверждённого ответа; context menu предлагает повтор с тем же ID. Timeout/ambiguous/manual-review не разрешают тихо начать новую операцию. Pending UI живёт в экземпляре app; journal живёт в мире. `#openItemContextMenu` учитывает дробные материалы и доступность организации; drop handler фиксирует Shift до await.
- `HeroDollService.assignItemToSlot(actor,slotId,dropData)` возвращает Item через `#submitAssignment(actor,slotId,dropData,mode)`. `clearSlot(actor,slotId)` снимает предмет из всех занятых им hand slots, не сливает количество. `normalizeLegacyStack(actor,slotId)` явно выделяет остаток из ordinary legacy stack, оставляя исходный ID у экипированной единицы. `getActorSnapshot` добавляет `slot.legacyStack`; render ничего не мигрирует.
- `executeAssignItemToSlot(payload,{sender},mode=assign)` — authoritative use case. `#authorizeAssignment(source,intent,sender)` требует OWNER target, source того же Actor либо managed group с target среди членов и OWNER source; проверки повторяются внутри worker. `#assignmentHands(actor,item,slotId)` использует canonical held-items capacity/reservations и запрещает захват занятой чужим действием руки до create. `#prepareAssignment(source)` строит компенсационные patches через `buildHeldItemHandUpdate`/`buildHeldItemWornUpdate`; two-hand item остаётся одним ID в обоих hand slots, замена освобождает прежний экземпляр.
- Raw private clone/debit и unsetFlag→setFlag в hero service отсутствуют: все три операции проходят через worker и replacement patch. Normalize снимает equipped/held только с нового остатка; upgrades/contents/runtime state всё равно запрещают split. Повтор journal receipt не создаёт дополнительные CurseEater/CurseUpgrade hosts.
- Main API `assignHeroDollItem(payload)`, `normalizeHeroDollStack(payload)`, `clearHeroDollSlot(payload)` → существующий PrivilegedMutationGateway; commands `hero-doll.assign`, `hero-doll.normalize-stack`, `hero-doll.clear`. `isValidHeroDollAssignPayload(payload)` задаёт exact `{actorUuid,sourceItemUuid,slotId,operationId}`; world Actor/embedded Item UUID, известный slot, canonical operationId ≤128. Mode выбирает регистрация команды, не payload. Public service хранит operationId для retry в `pendingAssignments`.
- Whole ordinary group source делегируется `InventoryService.executeTakeMutation` со стабильным ID; success требует terminal `{ok:true,value.createdItemId}` существующего journal. Для сложного whole group source прямой equip пока отклоняется до write: нужен отдельный подтверждённый перенос графа. Same-Actor singleton с upgrades сохраняет ID и может экипироваться.
- `bindHeroDollClickDelegation`/`bindHeroDollDelegatedListeners` в sheet integration обрабатывают `normalize-slot-stack` через service и rerender. HBS показывает отдельную кнопку только при legacyStack; CSS `.rm-hero-doll-slot__normalize` не меняет размер 80×80 ячейки.
