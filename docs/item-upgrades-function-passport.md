# Усовершенствования: каталог, правила, стоимость

Размер собственного host, strict descriptor v4 и неизменность стоимости установленных компонентов: [паспорт размеров снаряжения](equipment-size-function-passport.md#стоимость-composition-и-перенос). Прежние v2/v3 descriptors и installation contracts сохраняются.

Входной индекс: [паспорт функций](function-passport.md), разделы 13–15. R4 — правила/value; R7 runtime — 1.4.255. [Паспорт простых усовершенствований](simple-item-upgrades-function-passport.md) описывает 35 подключённых профилей, native проекцию, броски, поглощение и lifecycle.

## Каталог

Владелец `scripts/data/upgrade-automation-manifest.js`, решения `data/upgrade-automation-manifest.json`.

- `buildUpgradeAutomationManifest(upgrades, gear, decisions)` → detached rows, сортировка по productId. Private `indexRows(rows, field)` проверяет уникальность; `fail(code,id)` бросает explicit catalog error. Join только `productId === gear.id`; нет name fallback. Отсутствующие/лишние решения, дубликаты и неизвестные статусы отклоняются. Row содержит профиль, gearId, тип, reason, effectKind, owner/test/capability mappings и `ruleSource {file,productId,sourceSheet,sourceSheetRow}`. Для доступного статуса обязательны owner и existing test evidence.
- `buildUpgradeAutomationManifest()` добавляет `normalizedGearId` через тот же `canonicalCatalogId()`, которым пользуется импорт снаряжения. При коллизии в полном каталоге снаряжения значение равно `null`. Исходные `productId` и `gearId` строки каталога сохраняются.
- `resolveUpgradeCatalogEntry(gearId, manifest=[])` за один проход возвращает `{entry,availability}`. Совпадение с исходным ID имеет приоритет над однозначным нормализованным ID. `getUpgradeAvailability(productId, manifest=[])` возвращает только `{decision,available,label,reason}` из того же поиска. Подтверждённая автоматизация использует `existing-curse`, `simple-implemented` или `event-implemented`; неизвестный ID → `unavailable-no-rule`. Все 124 строки имеют явное решение: 11 проклятий, 35 простых автоматизаций, 1 событийная, 2 кандидата, 40 сложных без автоматизации и 35 без проверенного правила. Новые строки полного синка добавляются fail-closed как unavailable-no-rule до отдельного аудита автоматизации. Planned-R7 tests не являются свидетельством реализации.
- `loadUpgradeAutomationManifest()` → cached Promise rows; параллельно читает три static JSON с version query и `cache:no-store`, не пишет документы/settings. Ошибка сбрасывает promise для следующей попытки. Runtime не извлекает эффекты из русской прозы.
- Focused: `tests/upgrade-automation-manifest.test.mjs`; историческая матрица в `docs/superpowers/specs/2026-09-07-module-development/upgrade-scope.md` описывает исходные 91 решение, а текущим полным источником для 124 строк служит JSON manifest.

## Pure правила

Владелец `scripts/data/item-upgrade-rules.js`, без Foundry globals.

- `UpgradeRuleError(code, details={})`: code/details плюс пользовательское объяснение; unavailable/incompatible/capacity/slot-conflict/invalid-quantity.
- `resolveUpgradeProfile(storedProfile,catalogProfile)` возвращает detached сохранённый object целиком; при его отсутствии — каталог. Не смешивает custom effect с каталогом.
- `validateUpgradeCapacity(host,installed,capacity)` проверяет singleton host, целое capacity 1–3, позиции всех слотов и их уникальность; возвращает capacity. Снижение ниже максимального занятого slotIndex запрещено, даже когда installed.length меньше.
- `validateUpgradeInstallation(host,installed,candidate,{allowManual=false}={})` → `{allowed:true,slotIndex}`. Host содержит `id,compatibilityTags,capacity,quantity,isEquipped,isHeld,isAttuned,isBroken`, candidate содержит `sourceId,slotIndex?,profile,availability`. По умолчанию требуется статус существующего проклятия, реализованного простого правила или реализованного события. `allowManual:true` разрешает проверку существующего ручного профиля. В обоих случаях проверяются singleton host, совместимость, вместимость и занятые слоты, выбирается первый свободный слот. Основные tags — альтернативы. Дополнительные qualifiers `melee`, `ranged`, `nonmetal`, `brass-knuckles-or-metal-gauntlet`, `spellcasting-focus`, `grip-change`, `metallic`, `bow-or-crossbow`, `closable-container` и `worn` обязательны. Неизвестный tag отклоняется. `outerwear,shield` допускает обе категории.
- `evaluateUpgradeActivation(host,actor,profile)` → `{supported,active,reason}`. Явная `profile.activation`: carried/equipped/held/attuned; неизвестная/отсутствующая policy не активна. `worksWhenBroken:false` отключает broken host. actor зарезервирован для расширения существующих predicates.
- Focused: `tests/item-upgrade-rules.test.mjs`.

## Foundry adapter и запись

Владелец остаётся `scripts/data/item-upgrade-service.js`. Actor owner permission и existing installed links сохранены.

- `ItemUpgradeService(moduleApi=null,{getManifest=loadUpgradeAutomationManifest}={})` принимает composition API; второй аргумент — dependency injection для тестов. Единственный runtime экземпляр создаёт `scripts/main.js`.
- `getUpgradeProjection(item)` → `{sourceId,profile,availability,legacyOverride,choices,choiceOptions,requiresChoice}`. Поиск по `flags.rebreya-main.gearId` возвращает каталожный `productId` как `sourceId`; неизвестные документы сохраняют свой ID. `profileSignature(profile)` сравнивает `flags.rebreya-main.upgrade` с найденным профилем независимо от порядка ключей. `availability.available` описывает автоматизацию. Каталожный профиль без неё получает пометку «Без автоматизации» и причину. Отличающийся пользовательский профиль сохраняется и помечается неподтверждённым для новой установки. Choices читает из child flag `upgradeChoices`, при отсутствующем или недействительном обязательном выборе возвращает `requiresChoice`. Профильный тест запускает штатный импорт для всех 124 позиций и установку «Шипастой отделки доспеха» с обеими формами ID.
- `getItemUpgradeCategory(item)` допускает оружие, лёгкую, среднюю и тяжёлую броню, щиты и одежду как `outerwear`, а также типы `wondrous/staff/rod/wand`, данные `flags.rebreya-main.itemType`, магические ёмкости и распознанные фокусировки как `wondrous`. Каталог снаряжения заранее создаёт распознанную носимую одежду как `equipment/clothing`. Старый Actor-owned `loot/gear` считается одеждой при сочетании `equipmentType:Снаряжение` и точного `gearId` из `isRebreyaWearableClothingGearId(gearId)`. Обычные контейнеры, инструменты и прочие предметы вне перечисленных категорий недоступны для установки.
- `buildUpgradeHostDescriptor(item,{material}={})` читает явно заданные `flags.rebreya-main.upgradeCompatibilityTags` и дополняет их распознанными признаками. Магическая фокусировка определяется свойством dnd5e `foc` или точным ID фокусировки Ребреи. Хват определяется `lchGrip`, лук и арбалет — native `system.type.baseItem` или точным ID снаряжения. Закрывающаяся ёмкость определяется точным идентификатором известного контейнера, например `bag-of-holding`, либо явным признаком. Носимый чудесный предмет определяется одеждой dnd5e, назначением в телесные слоты куклы героя, точным идентификатором известного носимого предмета SRD или явным признаком. Магическая одежда может соответствовать `outerwear` и `wondrous-item`. Определение опирается на свойства и идентификаторы предмета. Состояние рук и экипировки читает через `getItemHeldHands`/`isItemEquipped`, attuned — native boolean, broken — canonical durability state.
- Private `#readHostMaterial(item)` вызывается при установке подтверждённого каталожного профиля с требованием `metallic`, когда нет уже заданного признака металла и известен `predominantMaterialId`. Читает `getModel().materialById` по текущему или каноническому ID. Дескриптор принимает подтип «Металл» и точные ID основных материалов, включая сталь и железо, у которых в каталоге указан подтип источника. Для других улучшений материал не загружается.
- `installItemUpgrade(hostItem,upgradeItem,options={})` / alias `installUpgrade` читает проекцию, проверяет количество и прежний host, затем валидирует установку. Каталожному профилю разрешена ручная установка. Upgrade stack отделяет одну единицу, host stack требует R3 split. `options.capacity` при несовпадении отклоняется. New slotIndex — только целое допустимое значение. Проверка ручных «Костей Тролля» и сохранения профиля находится в `tests/item-upgrade-service.test.mjs`.
- `options.choices` либо сохранённые choices проверяются до любых create/update/split. Нормализованный object сохраняется в `flags.rebreya-main.upgradeChoices` только установленной единицы, не остатка исходного stack. Remove и повторная установка сохраняют выбор. API не вызывает UI; отсутствующий обязательный выбор даёт UpgradeRuleError invalid-choice с объяснением.
- `removeItemUpgrade(hostItem,upgradeItemOrId)` / `removeUpgrade`: private `resolveActorItem` разрешает только child того же Actor; validates remaining slots до первой записи. Unavailable/custom исторический child разрешено снять без удаления профиля.
- `setItemUpgradeCapacity(hostItem,capacity)` / `setUpgradeCapacity`: pure validation до Item.update, без clamp входного аргумента. Public сигнатуры в game.rebreyaMain сохранены.
- Прежняя многошаговая запись install/remove не стала durable workflow в R4. Этот этап не обещает recovery между create/update при сбое; R3 journal не подменяется.
- Focused: `tests/item-upgrade-service.test.mjs` и `tests/item-upgrade-rules.test.mjs` покрывают шесть квалификаторов на подходящих и неподходящих предметах и проверяют отсутствие записи при отказе. Смежные проверки: `curse-upgrade-automation-service`, `equipment-import-gear-profiles`, `gear-compendium`.

## Ответный урон шипастой отделки

- `SpikedTrimService` в `scripts/combat/spiked-trim-service.js` обрабатывает `onMidiRollComplete(workflow)` и `onNativeAttackCard(card)`. MIDI отправляет запрос после завершения атаки; нативный путь получает карточку атаки на active GM при выключенном MIDI. Источник должен иметь оружейную или заклинательную AttackActivity ближнего боя и записанную цель. Попадание и промах запускают эффект, метательный режим не запускает. Бросок без Activity или цели не даёт достаточных данных.
- `registerCommand(gateway)` регистрирует `item-upgrade.spiked-trim {cardUuid,targetUuid}`. `authorize(payload,{sender})` сверяет автора карточки, его право на атакующего, тип Activity, бросок и UUID цели; GM сверяется повторно в `execute(payload,{sender,assertActiveGm})`. Команда сериализуется по Actor атакующего. `equippedTrims(actor)` читает экипированный предмет, непротиворечивую пару записей host/child и каталожный ID. Урон возможен только при подтверждённом профиле `event-implemented`. Каждый атакованный носитель отвечает один раз, несколько отделок на одном носителе не складываются.
- `registerSpikedTrimHooks(hooks,service)` связывает эти события и `captureDamageReceipt(actor,updates,options)`. Исполнитель вызывает нативный `Actor.applyDamage` с 2 `piercing`. Последние 128 квитанций `flags.rebreya-main.spikedTrimReceipts` живут на Actor атакующего. Квитанция добавляется в ту же запись, что и урон, с серверным расписанием команды и стабильным ID карточки и цели. Focused: `tests/spiked-trim.test.mjs`, `tests/item-upgrade-service.test.mjs`, `tests/upgrade-automation-manifest.test.mjs`.

## UI

Владелец `scripts/integrations/item-upgrade-sheet.js`.

- `installItemUpgradeWithChoices(hostItem,upgradeItem,moduleApi)` используется обоими существующими drop handlers. Read-only projection → при необходимости DialogV2 с finite choiceOptions → canonical install API. Отмена/закрытие возвращает null до записи/анимации/уведомления об успехе; уже выбранный тип не спрашивает снова. `namedItem("damageType")` читает native dialog form. `createUpgradeAvailabilityHtml` также показывает необходимость выбора либо его сохранённый тип.

- `createItemUpgradePanelHtml(hostItem)`/`renderItemUpgradePanel(root,hostItem)` показывают обычную панель только допустимому host, но сохраняют removal-only панель для исторически запрещённого host с установленными links: без capacity и drop controls. `bindItemUpgradeSheet(root,app,moduleApi)` подключает install/drop только допустимой цели, а open/remove — также cleanup-панели; `removeItemUpgrade` остаётся canonical способом безопасно снять historical child.
- `renderItemUpgradeAvailability(root,item,service)` асинхронно проецирует один upgrade либо installed children. WeakMap token подавляет устаревший render; повтор заменяет только собственную status section. Ошибка каталога видна текстом, без unhandled rejection. Host показывает статус в mods, source upgrade — в native details/description. Документы не обновляет.
- `createUpgradeAvailabilityHtml(item,projection)` показывает экранированные имя, пометку и причину из проекции, а также статус пользовательского профиля. CSS ограничен `.rm-item-upgrades__availability`.
- Focused: `tests/item-upgrade-service.test.mjs`, native live Item sheets.

## Типы поглощения

`scripts/data/item-upgrade-choices.js`: `getUpgradeChoiceOptions(sourceId,damageTypes=systemTypes)` пересекает фиксированный полный каталог правила с типами системы. Чешуя монстра — fire/cold/acid/poison/lightning; Зачарование поглощения — 13 обычных типов dnd5e, без healing/tempHP/произвольных ключей. `validateUpgradeChoices(sourceId,choices,damageTypes)` принимает только `{damageType}` для этих двух профилей и только пустой object для остальных; возвращает detached normalized object либо invalid-choice. Для Node/не загруженного CONFIG fallback — тот же finite каталог. Эта функция общая для install, projection и R8 generation; не выполняет выбор случайно. Focused: `tests/item-upgrade-choices.test.mjs`, service split/reinstall и absorption projection tests.

## Полная стоимость

Владелец `scripts/data/item-value.js`.

- `ItemValueError(code,details={})` сохраняет code/details; unknown-price/overflow/invalid-descriptor/unsupported-container.
- `addItemValue(a,b)` и private `multiplyItemValue(value,quantity)` допускают только неотрицательные safe integer copper values; проверяют переполнение результата.
- `evaluateItemValue(descriptor,catalogReader)` → `{baseValue,upgradeValue,contentsValue,totalValue,diagnostics}`. Descriptor v2 с unique instanceKey, sourceType/sourceId, quantity, boolean isBroken, upgrades и container. Обычная quantity — positive safe integer; composed host — quantity1; upgrade slots 1–3 уникальны, choices — object. Private `readComponent` вызывает synchronous `catalogReader.resolveValueComponent` с detached input, проверяет явный priceKnown:true, цену и форму optional upgradeProfile/includedUpgradeSourceIds. Private `record/id/invalid` проверяют DTO.
- base = unitValue×quantity; upgradeValue — сумма отдельных installed components. includedUpgradeSourceIds — multiset: каждое включение исключает ровно один matching child. Даже included child должен иметь известную цену. Цены сломанного предмета определяет reader по isBroken; новой скидки R4 не вводит.
- R9: shared traversal считает canonical snapshot через reader.readContainerValueNodes; root depth0/max8, cap200 documents, unique host/upgrade/container identities, quantity1 для контейнера. contentsValue включает только оставшиеся children/currency. Без адаптера сохраняется unsupported-container. Подробный data flow/errors и тесты — [паспорт составного лута](lootgen-composite-function-passport.md). Расчёт не меняет источники и не пересчитывает world Items.
- `resolveLootgenItemValue(rawValue,fallbackGold=0)` — прежняя legacy money policy: positive floored raw value, иначе rounded gold×100 (включая explicit legacy 0). Export того же имени в `scripts/ui/lootgen-app.js` делегирует сюда. Генератор/старые шаблоны пока сохраняют прежнюю семантику; новый evaluator — контракт для R8/R9.
- Focused: `tests/item-value.test.mjs`, `tests/lootgen-app-context.test.mjs`.
