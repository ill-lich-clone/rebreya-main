# Вдохновение Laaru и надёжный доброс d20

Статус: утверждено пользователем 2026-10-31 («Утверждаю, реализуй»).

## Результат для игрока

1. Бард использует существующее «Дать вдохновение (расходует заряд)» из Laaru на выбранном другом существе. Получатель получает одну кость на 10 минут. Её размер определяется уровнем барда: d6 / d8 с 5-го / d10 с 10-го / d12 с 15-го уровня; существующая авторская scale-формула имеет приоритет.
2. Получатель добровольно применяет кость к своей атаке, проверке характеристики/навыка/инструмента либо спасброску. Отказ или закрытие диалога сохраняет кость. Применение удаляет только выбранную кость. Истёкшая кость недоступна даже без стороннего автоматического удаления эффектов.
3. Атаки сохраняют текущую политику общего сервиса: предложение появляется при промахе, который доступные источники способны исправить; натуральная 1 не исправляется. Это сознательное сохранение существующего поведения доброса, хотя текст PHB допускает решение до объявления результата.
4. Кости «Исполнителя», «Точная атака» и другие уже поддерживаемые источники продолжают работать. Вдохновение и кость «Исполнителя» могут существовать одновременно; они не заменяют друг друга. Разрешается выбрать оба источника для одного броска, как уже допускает общий диалог атак; каждый применяется/расходуется однократно. У существа одновременно не более одного бардовского вдохновения, независимо от барда-источника. Повторная выдача при действующей кости отклоняется до штатного расхода, с понятным сообщением.
5. Решение игрока завершается до продолжения зависимого расчёта. Итог броска, попадание MIDI и сохранённое сообщение согласованы; перезагрузка чата не теряет прибавку.

## Подтверждённое текущее состояние

- Чистая `lich_branch`, HEAD совпадает с `origin/lich_branch`; после fetch `HEAD...origin/main` = 133/0. Версия модуля 1.5.40; manifest поддерживает Foundry 13. Установлены dnd5e 5.2.5 и Laaru 3.99.0. Live-версии ещё не проверены.
- Источник: `Compendium.laaru-dnd5-hw.classfeatures.Item.hpLNiGq7y67d2EHA`, прочитан из временной копии LevelDB. Карточка описывает правила 2014 года. В ней есть отдельные activities выдачи (`jADU6PX5XlK4kOq8`, itemUses=1) и броска (`2Enk7AiD901iQmfz`, формула `1@scale.bard.inspiration`); второй activity не является выдачей. У карточки пустой список effects, хотя activity выдачи ссылается на эффект.
- `BardicInspirationCompatService` сейчас только восстанавливает ресурс барабаном; он не выдаёт кость. `AttackRollBoostService` читает item boosts и Actor ActiveEffects с `flags.rebreya-main.d20Bonus`. `PerformerAutomationService` использует тот же флаг для обычных d20-проверок.
- 34 focused-теста проходят: `node --test tests/attack-roll-boost-service.test.mjs tests/performer-automation-service.test.mjs tests/bardic-inspiration-compat-service.test.mjs`.
- Отдельное воспроизведение гонки: запустить native fallback, оставить его prompt незавершённым, обработать тот же Roll через MIDI, затем подтвердить кость. Получено: Roll=19, MIDI=15, промах против КД18, кость удалена. Текущие тесты ожидают fallback целиком и пропускают такой порядок.
- В установленном dnd5e `rollSkill`/`rollAttack` вызываются через синхронный `Hooks.callAll` после `buildPost`. Асинхронный диалог из этих hooks не задерживает публикацию результата. В проекте уже есть ожидаемая async-граница `CONFIG.Dice.D20Roll.buildPost` у curse-upgrade automation; её интеграция должна сохранить порядок обработки проклятий.

## Подходы и выбранное направление

- Рекомендованный и подтверждённый по поведению путь: расширить наш compatibility-сервис, хранить выданную кость в существующем формате `d20Bonus`, использовать существующих владельцев добросов. Сторонний пакет Laaru остаётся источником данных.
- Правка самого пакета Laaru терялась бы при обновлении и дублировала бы наш механизм доброса; исключена.
- Самостоятельная новая система вдохновения/диалогов дублировала бы существующие сервисы и расход ресурсов; исключена.

## Владельцы и границы

- `scripts/combat/bardic-inspiration-compat-service.js`: распознавание точного источника (включая современный `_stats.compendiumSource` и поддерживаемые legacy source flags), различение выдачи и самостоятельного броска, разрешение размера кости от барда, проверка получателя, выдача/истечение. Не распознавать произвольные черты только по имени.
- `scripts/combat/attack-roll-boost-service.js`: одна ожидаемая операция на Roll/workflow; объединение источников, расходование и конечные MIDI hit-состояния.
- `scripts/combat/performer-automation-service.js`: добровольные generic `d20Bonus` для обычных проверок, совместимость с прежним performer metadata и штрафной костью. Выбор среди совместно доступных эффектов должен позволять оставить невыбранные эффекты.
- `scripts/combat/hooks.js`, `scripts/main.js` и существующая native roll-граница: только композиция/однократная интеграция; без второго владельца и повторных prompts. Нельзя просто сделать обычный Foundry hook async и считать его ожидаемым.
- World effects на чужих Actors создаются через валидируемую typed-команду и active GM. GM заново разрешает source Item/activity и target, проверяет OWNER отправителя и допустимость операции, не доверяет переданному клиентом размеру кости. Повторная доставка не создаёт вторую кость. Применение на linked/unlinked Token сохраняет точную цель.
- Range 60 ft проверяется при наличии source/target Tokens на одной сцене; себя выбирать нельзя. Без source/target Tokens на одной сцене допускается выдача явно указанному Actor, а дистанцию и слышимость проверяют участники вручную; показать это ограничение в уведомлении. Без геометрии нельзя выдумывать позицию или выбирать случайный Token. Слышимость остаётся решением участников: автоматизация не определяет её по наличию walls/vision.

## Сохраняемые контракты

- Laaru files/compendium не изменяются. Не удалять вторую activity броска, пользовательские activities, эффекты, формулы, uses max/recovery и дополнительные способы расходования вдохновения подклассами.
- Ресурс расходует штатная consumption существующей activity ровно один раз при выдаче. Применение получателем не тратит ресурс барда повторно. Отмена до выдачи не расходует его. Не переносить resource из Item в Actor flags.
- Барабан продолжает восстанавливать одну потраченную кость без переполнения; короткий/долгий отдых сохраняет авторские recovery rules.
- Сохранить размеры/продолжительность кости и штрафа «Исполнителя», блокировку после двух провалов, расходование «Точной атаки», scale references, публичные методы и существующие flags/settings.
- Не менять crit/fumble, advantage/disadvantage, исходный d20, оружейные ограничения, боеприпасы, осечки, автоматическое применение урона, AC/reactive bonuses или политику доступности других источников.
- Бардовское вдохновение ограничено обычными перечисленными d20-тестами; произвольный Roll, урон, initiative и death saves в новую автоматизацию не включаются.

## Намеренные изменения поведения

Самостоятельные решения автора спецификации, вынесенные на утверждение: совместное применение разных источников разрешено; отсутствие общей token-геометрии не блокирует явно выбранного Actor, но требует ручной проверки условий. Builder review выявил эти две неоднозначности; обе уточнены здесь.

1. Появляется автоматическая выдача и применение вдохновения Laaru с указанными ограничениями.
2. MIDI ждёт начатое решение о добросе того же Roll; потраченная кость меняет реальное попадание.
3. Обычные d20 bonuses применяются на ожидаемой границе до сохранения/использования результата, а не позже из post-roll hook. Прибавка сохраняется в сериализуемой структуре Roll, а не только во временном `_total`.
4. Одновременно доступные generic bonuses корректно различаются; отказ/невыбор одного не расходует другой. Истёкшие эффекты исключаются.

## Проверки до реализации и критерии готовности

Сначала failing regressions: незавершённый fallback + MIDI на том же Roll; отмена/повторное событие без двойного расхода; сериализация/восстановление и исходный d20; native skill/save message создаётся после решения; оба порядка с существующей обработкой проклятий; performer add/subtract.

Тесты вдохновения: точный modern/legacy source, обе Laaru activities, уровни 1/5/10/15 и приоритет authored scale, одна кость на получателя/600 секунд, отказ и expiry без расхода, сохранение performer effect, native единственный расход ресурса и барабан, self/missing target, чужой Actor через typed command, поддельный sender/source/target, повторная доставка, linked/unlinked target. Подтверждённые правила фиксировать до product edits, не ослаблять существующие assertions.

После реализации: focused suites; весь `node --test tests/*.test.mjs`; `node --check` для tracked JS/MJS; JSON parsing; `git diff --check`. Live Foundry: actual grant, выбор/отказ на skill/save, промах→попадание MIDI, совместимость с «Исполнителем», reload и повторная инициализация; GM/player permissions. Недоступную live-проверку явно указать, не заменять её утверждением на основании mocks.
