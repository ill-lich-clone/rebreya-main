# Общие ссылки на предметы в инвентаре

Дата: 2026-10-14. Статус: подтверждено пользователем 2026-10-14.

## Наблюдаемый результат

Название любого реального Item в групповом инвентаре становится кликабельным: материалы, снаряжение, магические предметы, алхимические расходники, ручные и кастомные предметы, а также Item из сторонних компендиумов. Наличие ссылки не зависит от экономического `sourceType` или списка поддерживаемых торговых каталогов.

Клик открывает доступный исходный Item в компендиуме либо среди мировых предметов. Если источник отсутствует, удалён, недоступен или не определяется однозначно, открывается собственный Item из инвентаря. Карточки записей журнала сохраняют существующий специализированный просмотр.

Примеры: старый алхимический расходник с `alchemyProductId`, но без `sourceId`, открывает соответствующую запись; вручную созданная строка с единственным совпадающим мировым предметом открывает этот предмет; Item со ссылкой на конкретный источник открывает его даже после переименования строки.

## Причина и выбранный подход

`InventoryService.#buildInventoryEntry()` разрешает ссылки только для `material`, `gear` и `magicItem`. Шаблон использует это разрешение, а обработчик `open-compendium-entry` вызывает `openTradeEntry()`, который выбирает отдельные каталоги по типу. Алхимический каталог сохраняет `sourceType: alchemyProduct` и `alchemyProductId`, но не общий `sourceId`. При импорте `sanitizeEmbeddedItemData()` удаляет `_stats` и `_id`, поэтому часть сведений о происхождении теряется.

Выбран один общий resolver источника Item и существующее открытие native sheet. Расширение списка типов не решает задачу для сторонних и будущих Item. Открытие только вложенного Item не даёт пользователю требуемых ссылок на реальные источники. Общий resolver решает оба случая без новой формы просмотра или нового владельца инвентаря.

## Правила определения источника

Поиск читает текущий Item по его `itemId` у существующего inventory actor выбранной группы. Получение карточки не создаёт actor. Данные строки служат подсказками для поиска, а не разрешением на изменение документов.

Приоритеты:

1. Валидный сохранённый UUID исходного Item: новый display-only `flags.rebreya-main.itemSourceUuid`, существующие `flags.core.sourceId` / `flags.dnd5e.sourceId` и `_stats.compendiumSource`. Они принимаются только как ссылки на доступный standalone world Item или compendium Item. Внешние ссылки на embedded Item других actors игнорируются: их документы могут быть изменены или удалены переносом. UUID реально известного источника имеет приоритет перед совпадениями по имени, включая UUID мирового Item. Текущий embedded Item используется только как последний вариант.
2. Стабильная идентичность источника: пара типа и `sourceId`, либо существующий флаг вида `<sourceType>Id`, с согласованной нормализацией регистра типа и ключа. Например, это покрывает `materialId`, `gearId` и `alchemyProductId` одним правилом. Сравниваются именно идентификаторы источника, а не любые поля с окончанием `Id`. Идентичность может использовать уже вычисленные inventory snapshot hints, не меняя классификацию предмета.
3. Точное нормализованное имя: обрезка краёв, сведение пробелов и сравнение без учёта регистра. Поиск не использует подстроки или нечёткое сходство. Native subtype и экономический тип не служат ограничивающим списком: вручную добавленный `loot` может ссылаться на единственный мировой `weapon` с тем же именем.
4. Существующий embedded Item из инвентаря как последний вариант.

Для поиска по идентификатору и имени сначала рассматриваются доступные Item-компендиумы, затем мировые Item. Одно совпадение в старшем уровне выбирается; несколько совпадений в этом уровне считаются неоднозначными и приводят к открытию inventory Item, без выбора первого документа или перехода к более слабому совпадению. При отсутствии совпадений поиск продолжается на следующем уровне. Недоступные документы не участвуют в выборе. Если сохранённый UUID устарел, используются остальные правила.

Права проверяются средствами Foundry для текущего пользователя: видимость Item-компендиума и доступ к документу. Это относится и к fallback sheet: открытие embedded Item не повышает права на party actor и следует существующим разрешениям просмотра. Поиск не обращается к GM socket для просмотра закрытого источника. Карточка отсутствующего или недоступного embedded Item не создаётся заново: UI показывает сообщение о недоступности и обновляет строку обычным способом.

## Владельцы и совместимость

Resolver принадлежит infrastructure: он читает UUID, индексы Item-компендиумов и мировые Item, возвращает `Document | null` и не рендерит sheet. Composition root публикует read-only `resolveItemSource(itemOrData, hints)` в существующем module API. Inventory UI выбирает найденный документ либо live inventory Item и использует существующее native открытие sheet. JournalRecord продолжает прежний viewer/API.

`openTradeEntry()` и отдельные методы открытия торговых каталогов сохраняют существующие сигнатуры и поведение для их потребителей. Эта задача меняет ссылки в InventoryApp; отдельный интерфейс Storage не перерабатывается. Общий resolver допускает повторное использование без второй реализации поиска.

При обычном импорте и копировании Item в инвентарь до удаления `_stats` сохраняется маленькая необязательная metadata `itemSourceUuid`: известный оригинальный источник либо UUID standalone world/compendium Item. UUID перемещаемого actor Item, который может быть удалён после переноса, не подменяет известный исходный источник. Сведения добавляются в существующий ingress/serialization путь, без массовой миграции старых Item, восстановления полного `_stats` или изменения schema recovery.

Metadata используется только для открытия карточки. Она не предоставляет полномочий на импорт, удаление, выдачу или восстановление и не заменяет `nativeImportSource`. Она сохраняется при последующих копированиях, разделении и переносах, где прежние source flags сохранялись. Она не меняет существующие правила слияния стаков, расчёта identity, stock и recovery: display-only поле исключается из сравнений, где иначе изменило бы эти правила. При совместимом слиянии сохраняется уже имеющаяся ссылка целевого стака; клик не переписывает её.

Сохраняются классификация custom/manual, authored formulas, quantity rules, дробные материалы, масса, цена, бюджеты, история приобретения, продажа, разбор, крафт, переносы и права владения. Совпадение имени с каталогом ради открытия карточки не превращает ручной Item в каталожный и не подменяет его характеристики.

## Производительность и ошибки

Поиск выполняется по клику, а не для каждой строки snapshot/render. Для поиска по имени и идентичности используются индексы доступных Item-компендиумов: `getIndex({ fields })` явно запрашивает `name`, `type` и namespace `flags.rebreya-main`, включая нужные source identity flags; стандартного индекса без flags недостаточно. Полные Documents загружаются только для кандидатов, которым требуется проверка доступа, и выбранного источника. Холодный индекс загружается лениво средствами Foundry. Общий постоянный кэш и новые hooks для кэша не вводятся; повторные запросы переиспользуют индекс Foundry.

Ошибка одного pack, удалённый документ или повреждённый UUID не ломает окно инвентаря. Нельзя выбирать единственное совпадение, если поиск в другом подходящем доступном pack завершился ошибкой и уникальность не подтверждена: в таком случае открывается inventory Item. Native sheet открывается один раз на клик. Открытие ссылок не пишет документы, settings, stock или mutation journal.

## Намеренные изменения поведения

- Все Item-строки получают кнопку названия независимо от `sourceType`.
- Кнопка использует общий resolver вместо торгового dispatch; доступный мировой источник становится допустимой целью.
- Сохранённая идентичность имеет приоритет над именем; неоднозначное совпадение открывает собственный Item вместо случайной записи.
- Отсутствие внешнего источника открывает собственную карточку, вместо некликабельного имени или сообщения только про компендиум.
- Новые ingress copies сохраняют необязательную ссылку на исходный документ без изменения игровых характеристик.

## Регрессии до изменения product-кода

Focused-тесты должны закрепить:

- Алхимию с legacy `alchemyProductId` без `sourceId`, материал/gear без `sourceType` на документе каталога, произвольный новый тип и сторонний Item-компендиум.
- Кастомный и ручной Item с единственным мировым совпадением, включая различие native Item type; предпочтение компендиума при поиске без точного UUID.
- Приоритет конкретного UUID над совпадающим именем, известный мировой источник, переименованную inventory строку и отказ от внешнего actor-item UUID.
- Неоднозначные имена/идентификаторы в одном и нескольких packs, отсутствующий источник, ошибку pack, холодный/пустой индекс и удалённый источник.
- Закрытый pack и недоступный мировой Item: источник не открывается, используется разрешённый inventory Item.
- Сохранение происхождения через существующие import/copy paths при удалённом `_stats`, неизменность caller data, merge/recovery contracts и отсутствие полномочий от display metadata.
- Неизменность manual/custom экономики и классификации, количества и материала при открытии ссылки.
- UI открывает выбранный live Item через общий API один раз; JournalRecord сохраняет viewer; рендер строк не сканирует packs; чтение не создаёт actor и не выполняет привилегированных записей.

Базовый прогон до правок: `node --test tests/group-inventory-migration.test.mjs tests/inventory-app-context.test.mjs tests/storage-app.test.mjs` — 273 passed, 0 failed.
