# Полное покрытие предметов индивидуальными иконками

## Наблюдаемый результат

После синхронизации управляемых компендиумов ни один принадлежащий модулю предмет из текущего аудита не использует стандартную заглушку или чужую классовую иконку. Каждый транспорт и скакун также получает индивидуальное изображение вместо общего значка типа.

Итоговый аудит должен подтвердить:

- `0` документов `Item` на `background.svg`, `book.svg`, `city.svg`, generic `utility.svg` или другом fallback, если документ входит в manifest этой задачи;
- `0` базовых классов, использующих изображение другого класса;
- `0` транспортных `Actor`, использующих только `pawprint.svg`, `anchor.svg`, `wing.svg` или `clockwork.svg`;
- `443` уникальных целевых WebP-файла для `449` документов: повторяющиеся имена Ремесленника используют одну общую иконку в пределах своего lookup scope.

## Границы задачи

В задачу входят все записи из аудита `rebreya-items-without-icons`:

- 157 предысторий;
- 11 черт;
- 122 классовых предмета, дедуплицированные по имени и class scope;
- 12 архетипов Ремесленника;
- 9 расовых умений;
- 15 действий;
- 26 downtime-активностей;
- 32 государства и плана;
- 3 базовых класса без собственной картинки;
- 62 транспорта и скакуна.

Не заменяются уже существующие индивидуальные иконки снаряжения, материалов, магических предметов, рас, обычных подклассов, заклинаний и конструкта. Не меняются игровые правила, описания, document IDs, advancement, права доступа и world-state.

## Визуальная система

Все новые иконки продолжают существующий стиль модуля:

- тёмное эпическое фэнтези с живописной детализацией;
- чёрный и бронзовый фон, золото и тёплое оранжевое свечение;
- один центральный образ или действие, читаемый в размере 64–256 px;
- декоративная золотая рамка с одинаковыми безопасными отступами;
- высокий контраст и глубокие тени;
- без текста, букв, цифр, логотипов, водяных знаков и элементов интерфейса.

Для предысторий и классовых умений образ передаёт роль или действие, а не портрет конкретного именованного персонажа. Для государств и планов используется символическое место, гербовая композиция или ландшафт без читаемой надписи. Для транспорта показывается сам объект в узнаваемом ракурсе, а не только символ его типа.

## Пакетная генерация

Manifest содержит ровно один target на уникальный итоговый файл. Каждый target задаёт:

- стабильный `targetId`;
- отображаемое имя;
- категорию и дополнительный контекст для промпта;
- относительный итоговый путь;
- `batchId`, индекс ячейки, строку и колонку;
- статус применения и источник сгенерированной сетки.

Targets идут в детерминированном порядке и разбиваются сквозным потоком на 18 batch по 25 ячеек; последняя сетка использует только 18 ячеек. Порядок внутри сетки всегда слева направо и сверху вниз. Категории разрешено смешивать в одной сетке, потому что manifest, а не имя batch, определяет итоговую папку.

Первая сетка является пилотной. Перед продолжением проверяются строгая геометрия 5×5, отсутствие текста, единый стиль, соответствие всех 25 изображений manifest-порядку и читаемость центрального объекта. После успешной проверки оставшиеся 17 сеток генерируются тем же шаблоном без дополнительной смены визуальной системы.

## Adapter сеток

Канонический инструмент уже существует: `tools/icon-pipeline.py`. Он расширяется grid-командами и остаётся единственным общим владельцем manifest, промптов, FFmpeg-нарезки и итогового аудита. Новый adapter не создаётся. Специализированные `feats-sheet-batch.py` и `races-sheet-batch.py` сохраняются без удаления и продолжают обслуживать прежний локальный workflow.

Adapter предоставляет команды для:

- построения и проверки manifest из канонических source-каталогов;
- выбора следующего неприменённого batch;
- печати точного ImageGen-промпта с 25 именами в manifest-порядке;
- применения явно указанной сетки к явно указанному batch;
- повторного аудита оставшихся fallback-документов.

При применении adapter:

1. проверяет существование batch и входного изображения;
2. через FFprobe требует квадратное изображение ненулевого размера;
3. нормализует сетку до квадратного размера, кратного пяти;
4. одним вызовом FFmpeg `filter_complex` делает `split`, 25 операций `crop`, масштабирование и WebP-кодирование в `256x256`;
5. записывает только занятые ячейки в точные manifest-пути;
6. по умолчанию отказывается перезаписывать существующий файл;
7. проверяет число, формат и размеры результатов;
8. создаёт ignored preview/receipt в `tmp/imagegen/` и атомарно отмечает batch применённым.

Частичная ошибка не должна помечать batch завершённым. Повтор после ошибки допускается только для отсутствующих файлов либо с явным флагом перезаписи.

## Раскладка файлов

Итоговые module-owned WebP размещаются по существующей модели именного lookup:

- `templates/icons/Backgrounds/`;
- `templates/icons/Feats/`;
- `templates/icons/Classes/<owner>/`;
- `templates/icons/AbilitiesByRace/<race>/`;
- `templates/icons/Actions/`;
- `templates/icons/Downtime/`;
- `templates/icons/States/`;
- `templates/icons/Transport/`.

Имя файла сохраняет отображаемое имя после Windows-safe sanitation. Нормализованный stem обязан совпадать с ключом, который строит `compendium-utils.js`; коллизия разных targets с одним output path является ошибкой manifest до генерации.

## Runtime-подключение

Существующие владельцы предысторий, черт, классов, рас и действий уже используют `buildNamedIconLookup()` и `resolveNamedIcon()`. Для них достаточно правильного имени и папки файла.

Три владельца требуют расширения существующего потока:

- `downtime-compendium.js` разрешает имя активности через `templates/icons/Downtime` и затем общий icon root;
- `states-compendium.js` разрешает имя государства/плана через `templates/icons/States` и затем общий icon root;
- `transport-compendium.js` строит lookup `templates/icons/Transport`, а `transport-actor-builder.js` принимает разрешённое индивидуальное artwork; типовой значок остаётся только защитным fallback для неизвестной внешней записи.

Сигнатуры управляемых документов включают разрешённый путь изображения, а template version изменяется там, где это необходимо для обновления существующих документов. UI не пишет настройки мира, новые socket routes и privileged mutations не создаются.

## Проверка и критерии готовности

Focused-проверки должны покрывать:

- детерминированные 443 targets и 18 batch;
- отсутствие дубликатов `targetId`, output path и занятой ячейки;
- безопасные Windows-имена;
- отказ от не-квадратной/повреждённой сетки;
- точное сопоставление row-major ячейки итоговому пути;
- отказ от неявной перезаписи;
- успешную FFmpeg-нарезку тестовой 5×5-сетки в WebP `256x256`;
- именной icon lookup и signature invalidation для downtime, states и transport;
- итоговый аудит с нулём targets на fallback;
- наличие и декодируемость всех 443 WebP.

Перед завершением выполняются профильные тесты владельцев, полный `node --test tests/*.test.mjs`, `git diff --check`, syntax-check всех tracked JavaScript/ESM и JSON parsing. Новые или изменённые методы adapter и runtime-владельцев отражаются в соответствующем разделе `docs/function-passport.md`.

## Git и восстановимость

Работа выполняется только в `lich_branch`. Генерация идёт batch-задачами с ignored receipt в `tmp/imagegen`, поэтому уже проверенные сетки и иконки не теряются при прерывании. В commit добавляются только спецификация, adapter, профильные тесты, runtime-изменения, паспорт и проверенные конечные WebP; исходные сетки и временные previews не коммитятся. Force push запрещён.
