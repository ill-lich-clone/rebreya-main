# Пресеты куклы героя

Дата: 2026-10-09. Статус: спецификация для согласования перед планом реализации.

## Цель и согласованные решения

Владелец героя сохраняет текущую куклу как именованный комплект и переключает комплекты кнопкой «Применить». Если сохранённый предмет продан, передан или удалён, в соответствующей клетке появляется полупрозрачное изображение отсутствующего предмета. Эта подсказка не считается предметом на кукле, не занимает слот и не даёт эффектов. Её можно убрать или заменить настоящим предметом.

Удаление силуэта изменяет только текущую куклу. Сохранённый комплект меняется исключительно при явном сохранении; повторное применение несохранённого комплекта снова показывает силуэт. Пользователь согласовал это поведение в чате.

Пресеты относятся к конкретному Actor, доступны его владельцам с разных компьютеров и сохраняются после перезагрузки. Внешний вид сетки и расположение слотов не входят в пресет.

## Пользовательский интерфейс

Над существующей куклой: список комплектов, «Применить», «Сохранить» и меню управления. Меню содержит создание комплекта из текущей куклы, переименование и удаление. Создание требует непустого имени; пробелы по краям удаляются, повторяющиеся имена внутри Actor отклоняются с объяснением. Искусственного ограничения количества комплектов в первой версии нет.

Выбор названия сам по себе не переключает экипировку. «Применить» восстанавливает полный набор слотов выбранного комплекта, включая пустые клетки. «Сохранить» перезаписывает выбранный комплект текущим состоянием, включая оставшиеся силуэты. Новый комплект также может сохранить силуэты. Сохранение не экипирует, не клонирует и не перемещает предметы.

После ручного изменения текущей куклы относительно применённого комплекта показывается отметка «изменён». Простое исчезновение документа при неизменной сохранённой ссылке не является ручным редактированием комплекта. Сохранение или повторное применение снимает отметку. Выбор другого названия не переписывает комплект и не меняет текущую куклу.

Удаление комплекта не снимает текущую экипировку и не удаляет текущие силуэты; снимается только привязка текущей куклы к удалённому комплекту. Для удаления комплекта требуется обычное подтверждение в интерфейсе. Явная кнопка «Сохранить» является достаточным подтверждением перезаписи.

## Отсутствующий предмет

Запись комплекта хранит ID конкретного embedded Item и резервные название/изображение. При наличии Item используются его актуальные данные. При отсутствии показывается сохранённое изображение с пониженной непрозрачностью и подписью в tooltip «<название> — предмет отсутствует». При недоступном изображении используется штатная запасная иконка; имя остаётся доступным.

Силуэт не является Item и не создаёт документ, quantity, system.equipped, heldHands, эффекты или резервирование. В snapshot клетка с силуэтом имеет occupied=false; счётчики reservedCount/availableCount и фильтрация инвентаря учитывают только реальные назначения. Клетка может визуально содержать силуэт, но механически остаётся свободной.

ПКМ предлагает «Убрать силуэт» и существующий список совместимых предметов. Успешное назначение настоящего предмета через меню или drag-and-drop удаляет силуэт только из текущей клетки. Неуспешное назначение сохраняет силуэт. Клик по силуэту не пытается открыть отсутствующий Item.

Привязка строго к экземпляру: другой Item с тем же названием, типом или изображением не подставляется автоматически. Предмет вне actor.items этого героя считается отсутствующим; комплект ничего не забирает из группового инвентаря. Перемещение внутри инвентаря, сохраняющее embedded Item ID и доступность предмета, не превращает его в отсутствующий.

В первой версии силуэты восстанавливаются при явном применении комплекта; автоматическое применение или экипировка при возвращении предмета не выполняются. Существующее поведение удаления текущего предмета вне применения комплекта не расширяется этой задачей.

## Данные и владельцы

Канонический владелец — существующий scripts/data/hero-doll-service.js. Presentation остаётся в templates/hero-doll-tab.hbs и существующих sheet integration/bindings; composition/API/typed routes — в scripts/main.js.

Существующий контракт flags.rebreya-main.heroDoll.slots[slotId] = {itemId} сохраняется: здесь находятся только реальные назначения. Комплекты и текущее состояние отсутствующих ссылок хранятся в отдельных полях Actor flags; они не подмешиваются в slots. Предлагаемая структура: версия схемы, коллекция комплектов со стабильными ID и именами, выбранный/применённый ID, отдельная карта текущих силуэтов. Каждый комплект хранит карту slotId -> {itemId,name,img}; отсутствие записи означает пустой слот. Точные имена новых полей и методов фиксируются в плане после проверки всех писателей heroDoll state.

Все обновления должны сохранять соседние Actor flags, существующие slots и данные других подсистем. Render и чтение snapshot не записывают документы и не мигрируют состояние. Actor без новых полей продолжает работать как раньше. Новый сервис-владелец куклы, новое world setting и отдельное приложение не нужны.

## Применение и ошибки

Операция применения авторизует authenticated sender как GM либо OWNER Actor. UI не пишет Actor/Item напрямую: изменения проходят через валидируемую typed command и существующие authoritative coordinator/journal. Проверки повторяются под блокировкой Actor, а не только по UI snapshot.

До записи проверяются существование комплекта, актуальность его данных, известные слоты, уникальность экземпляров в комплекте, совместимость каждого существующего Item и отсутствие конфликтующей незавершённой операции. Отсутствующий Item даёт силуэт и не блокирует остальные назначения. Существующий, но несовместимый/недоступный для назначения Item вызывает объяснимый отказ всего переключения до изменений, а не маскируется отсутствующим.

Комплект применяется как одна согласованная операция. Нельзя ограничиться последовательным вызовом assignItemToSlot для каждой клетки без общей блокировки, receipts и recovery: игрок не должен получить молча сохранённый половинчатый комплект. При ошибке используются проверяемые компенсационные patches только затронутых полей; при конфликтующих чужих правках — существующий manual-review и запрет повторной выдачи. Полный Actor snapshot для отката не используется.

Повтор запроса после timeout использует тот же operationId и intent; подтверждённый повтор не создаёт предметы или остатки повторно. До завершения/разрешения неоднозначного исхода интерфейс не начинает второе применение как новую операцию. Изменение/удаление комплекта во время применения не допускает установки устаревшего состояния без проверки.

Применение меняет размещение и экипировку только предметов, затронутых прежними/новыми реальными слотами. Остальные предметы и их equipped flags не пересчитываются. Смена не меняет attunement, количество расходников, формулы, charges, upgrades, contents, прочность, настройки, денежные остатки или бюджеты.

## Сохранение текущих контрактов

- Doll hand slots независимы от flags.rebreya-main.heldHands: применение не берёт предметы в реальные руки, не освобождает руки и не проверяет их вместимость.
- Clear/replacement сохраняет system.equipped у реально удерживаемого предмета через существующий held-items adapter.
- Слоты ссылаются на конкретные Item экземпляры. Существующие quantity rules и authoritative worker остаются владельцами выделения единицы; запрещён самостоятельный clone/debit из UI или новой команды.
- Обычные legacy stacks обрабатываются существующим разрешённым instance flow. Сложные предметы с индивидуальным состоянием не делятся вопреки текущим ограничениям. Явная normalizeLegacyStack остаётся доступной.
- Кольца, спинные слоты, clothing и правила совместимости сохраняются. Один экземпляр нельзя назначить в несколько клеток одного комплекта.
- Ручное назначение, очистка, меню предметов, tooltips и временное скрытие sidebar продолжают работать.

Намеренные изменения поведения: добавление Actor-пресетов; полное переключение набора с восстановлением пустых слотов; отображение и удаление механически пустых силуэтов; сохранение текущих силуэтов в комплект только явной командой.

## Проверки, обязательные до изменения поведения

Focused regression tests фиксируют требования, а не только форму реализации:

1. Создание, переименование, удаление, явная перезапись; изоляция Actor; read/render без writes; прежнее состояние без пресетов.
2. Полное переключение, очистка слотов, сохранение независимых equipped/heldHands и индивидуального состояния Item; перестановка экземпляров между слотами без дублирования.
3. Отсутствующий/проданный/переданный Item -> fallback-силуэт, occupied=false, прежние механические счётчики, отсутствие Item/effects/quantity writes; одноимённый экземпляр не заменяет исходный.
4. Удаление силуэта -> комплект неизменен -> повторное применение возвращает силуэт. После удаления и явного сохранения повторное применение оставляет слот пустым.
5. Замена силуэта реальным предметом; ошибка назначения сохраняет силуэт; сохранение остальных силуэтов; отсутствие auto-equip при возврате Item.
6. Несовместимый слот, дубликат Item, не-владелец, устаревший комплект, pending operation: объяснимый отказ без частичных изменений.
7. Quantity-one/legacy-stack cases и ограничения сложных экземпляров; fault injection до/после writes, retry после timeout, restart/recovery и конфликт компенсации без двойной выдачи.
8. UI: translucent image/tooltip, ПКМ удаления и выбора, drag-and-drop, modified state, очистка listeners при rerender, отсутствие записи из UI.

Основные существующие tests: tests/hero-doll-service.test.mjs, tests/hero-doll-instances.test.mjs, tests/hero-doll-ui.test.mjs, tests/dnd5e-sheet-downtime-tab.test.mjs. Для общего применения дополнить профильные coordinator/journal/instance tests по фактическому пути реализации.

После реализации: полный Node test suite, node --check для tracked JS/MJS, проверка tracked JSON, git diff --check. Live Foundry 13/dnd5e: GM и владелец-player, несколько окон Actor, reload, реальные sold/missing items и отсутствие console errors. Runtime-версия dnd5e и Foundry build фиксируются по реально доступному миру.

## Документация и выпуск

При реализации обновить README.md (пользовательский API и поведение) и docs/function-passport.md / docs/item-instance-passport.md (новые/изменённые методы, владелец, data flow, ограничения и тесты). Повысить module.json version относительно актуальной на момент реализации, синхронизировать versioned forwarder и esmodules. Текущая версия при подготовке спецификации: 1.4.363.

Только эта спецификация не меняет runtime, поэтому bump версии и runtime-тесты на данном этапе не требуются. Все записи/commits/push выполняются в lich_branch.
