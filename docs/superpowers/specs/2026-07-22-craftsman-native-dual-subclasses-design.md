# Ремесленник V0.1: два нативных подкласса dnd5e — дизайн

## Цель

Переписать ограничение dnd5e «один подкласс на один класс» для Ремесленника V0.1. Персонаж должен независимо выбрать:

- Исследование на 2-м уровне;
- Специальность на 3-м уровне.

Оба выбора должны использовать настоящие Items типа `subclass`, нативный `SubclassFlow`, стандартный Compendium Browser и штатную уровневую связь dnd5e. В карточке класса на листе персонажа должны одновременно отображаться оба выбранных подкласса.

Источник правил: [D&D Ремесленник V0.1](https://docs.google.com/document/d/1txV83llt1cC6PEFQCUA5FB53HOquCPEIelxOdua9bf8).

Зафиксированная ревизия источника: `AIroW34SYHbxIEd8hfh8j8hzbnG0i0cRyrMv3r2tLosHyzGf2l4OIqoMC8xBU220H_tJnksnZGuBtol42YomSQ`.

## Выбранный подход

Модуль расширяет базовые правила dnd5e только для класса `craftsman-v01`:

1. Исследования и Специальности публикуются как обычные `subclass` Items.
2. Два специализированных Advancement наследуют штатный `SubclassAdvancement`, а их формы — штатный `SubclassFlow`.
3. `AdvancementManager` обрабатывает все связанные с Ремесленником подклассы при повышении и понижении уровня.
4. Связь Item класса с подклассами становится множественной для Ремесленника, но сохраняет совместимый одиночный `class.subclass` для кода dnd5e, ожидающего одно значение.
5. Нативная карточка класса отображает оба подкласса внутри того же блока, где dnd5e показывает обычный подкласс.

Другие классы и их стандартная связь «один класс — один подкласс» не меняются.

## Почему не используются комбинации и отдельные типы Item

Не создаются составные варианты вида «Исследование + Специальность». При семи Исследованиях и пяти Специальностях это породило бы 35 зависимых комбинаций, уничтожило бы раздельные уровни выбора и усложнило замену одной оси.

Типы `rebreya-main.research` и `rebreya-main.specialty` больше не используются для новых персонажей. Они оставались обходом системного ограничения, показывали `ItemChoice` с флажками и не участвовали в нативной связи класса с подклассом.

## Нативные Items и компендий

Все варианты хранятся в существующем стандартном компендии `world.rebreya-subclasses` как Items типа `subclass`.

Структура папок:

```text
Подклассы
└── Ремесленник V0.1
    ├── Исследования
    └── Специальности
```

Каждый Item получает:

- `system.classIdentifier: "craftsman-v01"`;
- уникальный `system.identifier`;
- `flags.rebreya-main.craftsmanTrack` со значением `research` или `specialty`;
- стабильный `flags.rebreya-main.archetypeId`;
- полный текст и вложенные Advancement;
- стабильный document ID, не меняющийся при повторной синхронизации.

Compendium Browser использует тип `subclass`, `system.classIdentifier` и флаг трека. Поэтому окно выбора выглядит и работает как выбор подкласса остальных классов, но каждый шаг показывает только варианты своей оси.

## Два нативных Advancement

Класс содержит два отдельных Advancement:

- `ResearchSubclass` на 2-м уровне;
- `SpecialtySubclass` на 3-м уровне.

Оба класса Advancement наследуют dnd5e `SubclassAdvancement`. Их Flow наследует `SubclassFlow` и сохраняет штатные:

- шаблон окна;
- кнопку открытия Compendium Browser;
- предпросмотр Item;
- drag-and-drop;
- `flags.dnd5e.sourceId`;
- `flags.dnd5e.advancementOrigin`;
- `flags.dnd5e.advancementRoot`;
- применение, откат и восстановление выбранного Item.

Расширение Flow добавляет только фильтр `craftsmanTrack` и проверку, что перетащенный подкласс принадлежит нужному треку Ремесленника. Произвольный подкласс или вариант другой оси отклоняется с уведомлением.

`summaryforLevel` каждого Advancement получает выбранный Item через собственное `value.document`, а не через одиночный `class.subclass`.

## Множественная связь класса с подклассами

Для Ремесленника вводится единый helper, возвращающий объект:

```js
{
  research: Item | null,
  specialty: Item | null
}
```

Связь определяется по следующим данным, а не по имени Item:

- Item имеет тип `subclass`;
- `system.classIdentifier === "craftsman-v01"`;
- `flags.rebreya-main.craftsmanTrack` содержит допустимый трек.

Для совместимости с API dnd5e геттер `class.subclass` у Ремесленника возвращает Исследование. Это важно для штатных вычислений заклинаний: магическое Исследование может переопределять базовую прогрессию класса. Специальность остаётся вторым полноценным подклассом и обрабатывается расширенным Advancement Manager.

У остальных классов геттер и системное поведение остаются без изменений.

## Уровневый жизненный цикл

Штатный dnd5e `AdvancementManager.createLevelChangeSteps` вызывает Advancement только одного `classItem.subclass`. Модуль заменяет этот участок для `craftsman-v01` эквивалентным алгоритмом, который перебирает оба связанных подкласса.

При повышении уровня порядок шагов сохраняется:

1. раса;
2. класс;
3. Исследование;
4. Специальность;
5. связанные feature Items;
6. итоговое изменение уровня класса.

При понижении порядок разворачивается безопасно: сначала отзываются зависимые выдачи, затем Advancement обоих подклассов и класса.

Новый алгоритм используется только для Ремесленника. Для любого другого класса вызывается оригинальная реализация dnd5e. Патч регистрируется один раз, имеет маркер версии и проверяет наличие ожидаемых API; несовместимая версия системы выдаёт явную ошибку вместо частично работающего класса.

## Отображение в карточке класса

Отдельная секция «Архетипы Ремесленника» удаляется.

Контекст штатной вкладки «Умения» получает для карточки Ремесленника два подкласса. Совместимый вариант системного partial `dnd5e.actor-classes` сохраняет прежнюю разметку для обычных классов, а для Ремесленника выводит:

- иконку класса;
- иконку выбранного Исследования либо нативную кнопку выбора;
- иконку выбранной Специальности либо нативную кнопку выбора;
- название класса;
- строки `Исследование — <название>` и `Специальность — <название>`;
- обычные действия открытия и удаления Item;
- уровень класса в прежнем месте.

Обе иконки и названия ссылаются на настоящие embedded `subclass` Items. Удаление одного трека не затрагивает другой.

Tidy5e получает те же два нативных Item через его официальный extension API. Старый самостоятельный блок не сохраняется ни на стандартном листе, ни в Tidy5e.

## Полный состав данных из документа

### Исследования

В компендий добавляются все семь вариантов:

1. Оружейник;
2. Бронник;
3. Алхимик;
4. Артефактор;
5. Оккультист;
6. Врачеватель;
7. Механик.

Документ содержит полные уровневые ветки для Оружейника, Бронника, Алхимика, Артефактора и Механика. Их умения становятся отдельными feature Items и выдаются вложенными `ItemGrant` на уровнях, указанных в документе.

Оккультист и Врачеватель в зафиксированной ревизии содержат только вводные заготовки без полной уровневой ветки. Они всё равно создаются как доступные `subclass` Items с дословным имеющимся текстом, но модуль не придумывает отсутствующие умения.

### Специальности

В компендий добавляются все пять вариантов:

1. Штурмовик;
2. Защитник;
3. Конструктор;
4. Артиллерист;
5. Тактик.

Полная уровневная ветка в документе есть у Конструктора. Его умения выдаются на уровнях 3, 3, 6, 10 и 15.

Штурмовик, Защитник, Артиллерист и Тактик содержат только вводные описания. Они создаются без выдуманных уровневых умений.

## Дословность и Markdown

Текст переносится из зафиксированной ревизии документа дословно. Нельзя:

- сокращать или пересказывать;
- исправлять авторские опечатки и терминологию;
- удалять повторяющиеся заголовки Алхимика;
- переставлять абзацы, варианты и таблицы;
- заменять отсутствующие правила предполагаемыми механиками.

Разрешена только невидимая Markdown-разметка: заголовки, курсив, полужирные метки, списки, таблицы и цитатные блоки. Канонический видимый текст до и после рендера должен совпадать с соответствующим диапазоном Google Docs.

Артефактор получает нативные поля spellcasting только в объёме, прямо определённом разделом «Использование заклинаний» и таблицей документа. Его список заклинаний переносится целиком. Для незавершённых вариантов магическая прогрессия не выдумывается.

## Граница автоматизации и зависимые подсистемы

В эту работу входят:

- два нативных выбора подкласса;
- хранение обоих подклассов на Actor;
- выдача и отзыв всех описанных уровневых feature Items;
- нативная прогрессия заклинаний там, где она полностью определена;
- владения и другие стандартные данные dnd5e, явно заданные текстом;
- отображение обоих подклассов в карточке класса.

Полная автоматизация следующих правил требует отдельных подсистем и не подменяется фиктивными эффектами:

- создание, улучшение и активация гаджетов;
- Объект исследования и очки модификации;
- расширенный крафт, ремонт, импланты и ранги мастерских;
- Actor/Token Конструкта и управление его сборками;
- транспорт, поломки и транспортные узлы;
- создание и расходование авторских зелий и разносторонних предметов.

Items содержат весь текст этих правил и выдаются на нужных уровнях, но их отдельная автоматизация проектируется после базовой subclass-механики.

## Миграция прежней реализации

Старые типы `research` и `specialty` временно остаются зарегистрированными только для чтения и безопасной миграции существующих Actor.

GM-миграция:

1. находит embedded Item класса `craftsman-v01` со старыми `ResearchChoice`/`SpecialtyChoice`;
2. сопоставляет выбранные Items по стабильному `archetypeId`;
3. создаёт соответствующие новые Items типа `subclass`;
4. переносит значения Advancement и перепривязывает выданные feature Items к новым корням;
5. проверяет наличие обоих новых документов и целостность ссылок;
6. только после успешной проверки удаляет старые embedded Items;
7. обновляет Advancement Item класса на два новых нативных типа.

Если источник нового подкласса или feature Item не найден, миграция прекращается до удаления старых данных и выводит идентификатор проблемы. Повторный запуск идемпотентен.

Из устаревшего компендия `world.rebreya-craftsman-archetypes` удаляются только документы, помеченные модулем как управляемые, и только после успешной публикации новых подклассов. Сторонние документы не затрагиваются.

## Ошибки и ограничения целостности

- Нельзя выбрать два Исследования или две Специальности для одного Ремесленника.
- Можно независимо заменить одну ось, сохранив вторую.
- Подкласс другого класса или другого трека не проходит проверку Flow и drag-and-drop.
- Класс не публикуется, если отсутствует UUID хотя бы одного заявленного подкласса.
- Пустая авторская заготовка допустима, но не маскируется под реализованную уровневую ветку.
- Синхронизация обновляет управляемые документы на месте и сохраняет стабильные UUID.
- Патчи dnd5e не применяются вне мира dnd5e и не меняют поведение других классов.

## Проверки

Автоматические тесты должны подтвердить:

- все 12 вариантов созданы как `subclass` и находятся в стандартном компендии;
- каждый вариант имеет правильный трек и `classIdentifier`;
- оба Advancement наследуют нативный `SubclassAdvancement` и используют нативный Flow/template;
- Compendium Browser каждого шага показывает только свой трек;
- неверный drag-and-drop отклоняется;
- уровень 2 создаёт Исследование, уровень 3 независимо создаёт Специальность;
- повышение и понижение обрабатывает вложенные Advancement обоих подклассов;
- замена одной оси не удаляет вторую;
- дубликат одного трека запрещён;
- `class.subclass` совместимо возвращает Исследование;
- карточка класса содержит обе иконки, оба названия и нативные действия;
- обычные классы по-прежнему имеют один подкласс и прежнюю разметку;
- миграция сохраняет выбор и выданные features, а при ошибке не удаляет старые Items;
- полный видимый текст каждой записи совпадает с зафиксированной ревизией Google Docs;
- все прежние тесты модуля проходят.

Ручная проверка выполняется в Foundry VTT 13 с установленной версией dnd5e:

1. добавить Ремесленника новому Actor;
2. на 2-м уровне открыть нативную библиотеку Исследований и выбрать вариант;
3. на 3-м уровне открыть нативную библиотеку Специальностей и выбрать вариант;
4. проверить обе записи внутри карточки класса;
5. повысить и понизить уровень через все точки выдачи обеих осей;
6. заменить только один трек;
7. проверить обычный класс с одним подклассом;
8. проверить миграцию Actor со старой реализацией.

## Критерий готовности

Работа завершена, когда Ремесленник использует два независимых настоящих `subclass` Item, выбирает их через нативный браузер dnd5e, показывает оба внутри карточки класса и корректно проводит Advancement каждого трека на всех уровнях. Все 12 вариантов из документа опубликованы с полным доступным текстом, а отсутствующая в источнике механика не выдумана.
