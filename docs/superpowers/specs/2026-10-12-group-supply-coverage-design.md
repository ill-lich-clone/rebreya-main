# Покрытие расходов еды и воды по группе

Дата: 2026-10-12. Статус: согласована пользователем, реализация ещё не начата.

## Наблюдаемый результат

Флажки «Покрыть расходы еды» и «Покрыть расходы воды» запоминаются отдельно
для каждой управляемой dnd5e-группы. При переключении групп пользователь
видит выбор соответствующей группы. Изменение одного флажка не меняет
другой флажок или настройки другой группы. После перезагрузки выбор сохраняется.

Календарь и ручное списание припасов используют настройки именно той группы,
для которой выполняется операция. Смена активной группы во время ожидания
операции не перенаправляет запись или списание.

## Причина и владелец

Сейчас `InventoryService.#getState()` читает оба флажка из мирового `PARTY_STATE`.
`updatePartyDefaults(patch)` записывает их туда же. `getPartySnapshot()` и
`#buildSupplyConsumptionSnapshot()` используют это общее состояние, даже
когда инвентарь и участники уже выбраны по конкретному Group Actor.

Владельцем расчёта и изменения остаётся `scripts/data/inventory-service.js`.
Настройки группы хранятся в существующем `GROUP_STATE.groupsById[groupActorId]`
и записываются через `GroupContextService` / `GroupStateRepository`.
`scripts/data/group-context-service.js` сохраняет и нормализует новые поля.
Окно передаёт идентификатор показанной группы; публичный API и транспорт
проверяют целевой scope до записи. UI не пишет settings напрямую.

## Совместимость и намеренные изменения

- Единственное изменение игрового поведения: покрытие еды и воды становится
  независимым для каждой группы вместо общего переключателя мира.
- При первом обновлении существующие зарегистрированные группы однократно
  получают текущие общие значения каждого флажка. Уже сохранённые отдельные
  значения, включая `false`, не перезаписываются. Последующие изменения старого
  мирового состояния не влияют на группы. Новые группы начинают с `false/false`.
- Старые ключи `PARTY_STATE`, названия полей, названия флажков и вызов
  `updatePartyDefaults(patch)` сохраняются. Вызов без явного scope выбирает
  группу при входе в операцию; legacy-инвентарь без native-группы сохраняет
  прежнее поведение. Явно неверная/удалённая группа даёт ошибку, без fallback
  на другую группу или мировую запись.
- `defaultCapMod`, настройки участников, авторские значения расхода,
  количества предметов, бюджет и прочие правила не меняются.
- Покрытая еда обнуляет только потребность в еде; покрытая вода — только
  потребность в воде. Покрытый ресурс не списывается и не вызывает штраф
  энергии. Нехватка непокрытого ресурса и её штрафы остаются прежними.
- Сохраняются действующие права управления группой. Привилегированная запись
  выполняется elected active GM через существующий валидируемый маршрут;
  идентификатор группы не расширяет права отправителя.
- Среда: Foundry VTT 13, dnd5e, `statuscounter >= 3.0.4`, существующая ESM-
  архитектура без новых зависимостей. Для клиентских изменений обязательны
  повышение версии `module.json` и синхронный versioned forwarder.

## Регрессионные проверки до изменения реализации

1. Две группы: A покрывает только еду, B — только воду. Снимки, переключение,
   независимые записи и повторное создание сервисов сохраняют эти значения.
2. Дневное и многодневное списание по явному `groupId` использует его флажки,
   даже если другая группа активна. Проверяются реальные количества еды/воды,
   авторские нормы участников, нехватка и энергия.
3. Начальный перенос общих `true/false` сохраняет поведение существующих групп;
   повторный перенос не перезаписывает отдельные `false/true`. Новая группа
   получает `false/false`; legacy-вызов сохраняет прежний контракт.
4. Смена группы во время асинхронного вызова не меняет захваченный scope.
   Неверная группа и отправитель без прав не создают записей.
5. UI передаёт показанную группу, API сохраняет старый вызов и направляет
   разрешённые удалённые записи через active GM.

## Проверка и граница согласования

После согласования этой спецификации составляется отдельный письменный план.
До изменения product-кода требуется согласование плана, согласно AGENTS.md.
Проверка реализации: focused-тесты, затем полный `node --test tests/*.test.mjs`,
syntax checks всех tracked JS/MJS, parsing всех tracked JSON и `git diff --check`.
При доступном Foundry — переключение двух групп, сохранение и перезагрузка,
проверка ошибок консоли; недоступная live-проверка указывается в отчёте.
