# Единое управление реакциями и сообщениями чата

Статус: согласовано пользователем 2026-10-23, включая общий чат и имена скрытых NPC.

## Результат для пользователя

Реакции всех Actor, включая персонажей игроков и NPC, а также стандартные реакции Midi-QOL, проходят через существующий `ReactionQueueService`. Во время реального выбора чат показывает «Имя выбирает реакцию». После успешного применения сервис удаляет именно это сообщение. При отказе, закрытии окна или таймауте заменяет его на «Имя не применил реакцию».

Имя берётся у реагирующего Actor; строка безопасно экранируется. Предлагаемое поведение: сообщение видно всем участникам чата, включая сообщения о NPC. Ошибка применения или отмена последующей формы расхода считается неприменённой реакцией; одного нажатия «использовать» недостаточно для удаления сообщения.

## Подходы

1. Расширить существующую очередь и добавить адаптер Midi-QOL. Единый владелец выбора, таймаута, сообщений и результата; существующая механика применения остаётся у своего владельца. Рекомендуется; предложение основано на подтверждённом требовании пропускать все реакции через наш сервис.
2. Только наблюдать окна Midi-QOL и добавлять чат. Меньше вмешательства, но оставляет независимый выбор вне нашего сервиса и не выполняет требование.
3. Полностью переписать применение реакций Midi-QOL внутри модуля. Дублирует фильтры, расход ресурсов и механику КД; не подходит для сохранения контрактов.

## Владельцы и поток данных

- `scripts/combat/reaction-queue-service.js`: каноническая очередь, маршрутизация владельцу, результаты, дедупликация; сюда добавляется жизненный цикл сообщения.
- Адаптер в `scripts/integrations/`: перевод стандартных запросов Midi-QOL в очередь и возврат совместимого результата в ожидающий workflow. Регистрация только из существующего composition root / combat hooks, идемпотентно.
- Midi-QOL и существующие providers: проверка доступности и применение выбранной способности через исходный workflow, включая эффекты и оплату. Очередь не списывает ресурс повторно после списания MIDI.
- Сервис координирует сообщения на одном авторитетном клиенте, используя текущую модель active GM и проверенный socket sender. UI не изменяет world settings и не выполняет привилегированные операции напрямую.

Последовательность: триггер → обнаружение и проверка кандидата → общая очередь → сообщение → выбор владельца (для NPC/отсутствующего владельца — GM) → повторная проверка → применение через существующий provider/MIDI → подтверждённый результат → удаление или замена сообщения → продолжение исходного workflow.

## Сохраняемые контракты

- Существующие API, providers, socket authorization, порядок инициативы в бою и однократное перемешивание вне боя.
- Текущий лимит выбора 10 секунд; поздний ответ не применяет реакцию. Лимит выбора не обрывает уже подтверждённое применение посередине транзакции.
- Все authored formulas, quantity rules, budgets, spell slots, item uses, reaction ledger, правила отката и настройки доступности реакций сохраняются. Отключённые реакционные возможности не включаются принудительно.
- MIDI получает ожидаемый результат, включая изменение AC и идентификаторы применённой способности; исходная атака/заклинание ждёт реакцию и корректно продолжается.
- Реакция и её ресурсы расходуются ровно один раз; существующие module providers не дублируются в native MIDI-списке.
- Нереакционные вызовы `promptDecision` не получают реакционных сообщений.
- Нет новых polling, мировых сканирований, независимых очередей или изменений файлов зависимости Midi-QOL.

## Намеренные изменения

- Стандартные MIDI-реакции, включая optional AC reaction path, подчиняются общей очереди и её 10-секундному выбору вместо отдельного MIDI-таймаута.
- Новые сообщения общего чата показывают ожидание выбора и отказ. Для одного запроса не создаются дубли этих сообщений из-за повторных socket/hook событий.
- Обновление версии `module.json` и согласованный versioned forwarder обязательны.

## Ошибки и завершение

Нет доступного кандидата — нет сообщения. Ошибка чата не должна ломать применение реакции или блокировать workflow. Отказ, закрытие, таймаут, неуспешная оплата или применение завершают ожидание и не оставляют «выбирает реакцию» навсегда. Дедупликация привязана к триггеру и кандидату, а не только имени Actor. После таймаута окно закрывается, поздние ответы отклоняются.

Сообщения содержат module-owned идентификаторы триггера/кандидата и состояние для безопасного обновления именно своей записи. Сообщение об отказе остаётся в истории чата. Нового таймера в чате, звука и грамматических вариантов нет: используются ровно согласованные строки. Поведение очереди при нескольких целях сохраняется; native MIDI-запросы подключаются к той же очереди, без отдельной параллельной очереди.

При исчезновении GM позднее применение запрещено; ожидание на клиенте должно завершиться по таймауту. При восстановлении координатора оставшиеся module-owned сообщения ожидания с истёкшим сроком переводятся в «не применил реакцию», без повторного применения и списания. Если авторитетного клиента нет, немедленное обновление общего чата невозможно; это ограничение не скрывается.

Проверка Gemini выявила продуктовый выбор: общий чат раскрывает имя даже скрытого NPC. В текущем предложении сохранено буквальное требование общего сообщения для всех Actor; это явно вынесено на согласование вместе со спецификацией. Маскирование имён по видимости потребует отдельного согласованного правила.

## Обязательная проверка

До изменения поведения закрепить focused-регрессии: create/update/delete сообщения; подтверждённое применение вместо клика; отказ/close/timeout; поздний ответ; ошибки оплаты/применения; дубликаты; NPC/GM и player owner; отсутствие сообщений у нереакционных prompts; ошибки ChatMessage; native MIDI activity и optional AC результат; отсутствие двойной оплаты и повторных окон; продолжение исходного workflow.

Обновить README и паспорт функций. Перед commit выполнить `node --test tests/*.test.mjs`, `git diff --check`, синтаксическую проверку tracked JS/MJS и парсинг tracked JSON. Проверить в живом Foundry GM/player/NPC, таймаут и MIDI workflow; если окружение недоступно, явно указать непроверенные сценарии. Commit и push только в `lich_branch`.

## Подтверждённые ограничения и следующий этап

Установлен Midi-QOL 13.0.61; manifest модуля рассчитан на Foundry 13. `midi-qol.ReactionFilter` сам по себе недостаточен: отмена возвращает служебный результат вместо результата применённой реакции. Точный перехват и возврат результата необходимо доказать по установленному исходнику и regression harness до выбора реализации адаптера; недокументированный API должен быть явно обозначен и изолирован. Версия работающего Foundry/dnd5e пока не проверена.

После согласования спецификации — отдельный письменный implementation plan с конкретной точкой адаптации MIDI и проверками, затем реализация по согласованному плану.
