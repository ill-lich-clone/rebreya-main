# Последовательный сервис продолжительного отдыха — дизайн

**Дата:** 2026-07-23

**Статус:** утверждено для реализации

## Цель

Заменить независимые обработчики `dnd5e.restCompleted` единым расширяемым
сервисом продолжительного отдыха. Все механики Rebreya, срабатывающие после
продолжительного отдыха, должны выполняться последовательно: следующее окно
открывается только после закрытия или завершения предыдущего.

Сервис является P0-фундаментом. Механика Модифицирования относится к P1 и
подключается к готовой цепочке отдельным зарегистрированным шагом, без нового
Foundry-хука.

## Исходная проблема

Сейчас модуль регистрирует семь независимых обработчиков
`dnd5e.restCompleted`. Один из них объединяет две разные обязанности
Ремесленника, поэтому фактически обработчиков механик восемь. Большинство
callback-ов запускают асинхронную работу без ожидания соседних callback-ов.
В результате:

- несколько окон могут открываться одновременно;
- порядок изменений состояния не определён;
- закрытие и ошибки обрабатываются каждой механикой по-разному;
- добавление новой механики увеличивает число глобальных хуков;
- диагностика одного отдыха разбросана по разным сервисам.

Native dnd5e вызывает событие через синхронный
`Hooks.callAll("dnd5e.restCompleted", actor, result, config)`. Системный метод
отдыха не может ожидать асинхронные хуки, поэтому модуль организует ожидание
внутри собственной очереди после получения события.

## Границы P0

P0 включает:

- `LongRestPipelineService`;
- один диспетчер завершения отдыха;
- публичный реестр шагов;
- последовательное выполнение и единое поведение при закрытии и ошибках;
- общий прогресс интерактивных окон;
- миграцию всех существующих механик продолжительного отдыха;
- тесты очереди, хука и мигрированных механик.

P0 не включает:

- интерфейс и правила Модифицирования;
- общий мастер с несколькими механиками в одном окне;
- глобальный откат уже завершённого системного отдыха;
- новые игровые правила для существующих классов и рас;
- перенос предрестовых правил транса в пострестовую цепочку.

## Архитектура

### LongRestPipelineService

`LongRestPipelineService` является нейтральным к классам и игровым правилам.
Он хранит реестр провайдеров, строит план конкретного отдыха и выполняет шаги
через `await`.

Концептуальный публичный контракт:

```js
game.rebreyaMain.registerLongRestStep({
  id: "paladin.prepared-spells",
  label: "Заклинания паладина",
  order: 220,
  interactive: true,

  isEligible: ({ actor, result, config }) => true,

  run: async ({
    actor,
    result,
    config,
    runId,
    progress,
    signal
  }) => {
    return { status: "completed" };
  }
});
```

Правила регистрации:

- `id` обязателен и уникален;
- `label` является строкой либо функцией, возвращающей название шага;
- `order` является конечным числом;
- `interactive` является boolean либо чистой функцией от контекста;
- `isEligible` не изменяет документы и только решает, входит ли шаг в план;
- `run` возвращает `completed` или `skipped`;
- повторный `id`, отсутствующий callback или некорректные поля вызывают
  синхронную ошибку регистрации;
- сортировка стабильна: сначала `order`, затем `id`.

Публичный API модуля предоставляет как минимум:

```js
registerLongRestStep(definition)
runLongRestPipeline(actor, result, config)
```

Прямой запуск нужен тестам и будущим внутренним интеграциям. Обычный игровой
путь использует единственный Foundry-хук.

### Контекст исполнения

Каждый `run` получает:

- `actor`, `result` и `config` исходного события;
- уникальный для локального запуска `runId`;
- `signal` для безопасной отмены при выгрузке мира;
- `progress` с номером интерактивного шага и форматтерами интерфейса;
- ограниченный сборщик диагностического результата.

Контекст не должен сохраняться во флагах Actor, Item или Active Effect.

### Очереди и дедупликация

Для каждого Actor существует независимая promise-очередь:

- два отдыха одного персонажа выполняются последовательно;
- отдых другого персонажа не блокируется;
- очередь удаляется из памяти в `finally`;
- повторная передача того же объекта `result` не создаёт вторую цепочку;
- два разных результата отдыха не склеиваются по времени или Actor UUID.

Для дедупликации одного события используется идентичность объекта результата,
а не временное окно. Это не позволяет случайно потерять второй настоящий
отдых.

### Построение плана

Перед выполнением сервис:

1. создаёт неизменяемый базовый контекст запуска;
2. вызывает `isEligible` всех зарегистрированных шагов;
3. отбрасывает неприменимые шаги;
4. сортирует оставшиеся шаги;
5. вычисляет `total` только по интерактивным шагам;
6. запускает план последовательно.

Непосредственно перед `run` применимость проверяется повторно. Если предыдущий
шаг сделал механику неприменимой, текущий шаг получает `skipped` без окна.
Первоначальный `total` не пересчитывается во время цепочки, чтобы номера уже
показанных окон не менялись.

## Порядок шагов

Диапазоны приоритетов:

- `100–199` — фоновые восстановления и очистка состояния;
- `200–299` — интерактивные решения игрока;
- `900–999` — итоговые сверки будущих механик.

Фоновые операции выполняются раньше окон, чтобы пользователь принимал решения
на полностью восстановленном персонаже.

Текущие большие обработчики разделяются по одной обязанности на шаг:

Фоновые шаги:

1. восстановление рун и долгосрочных ресурсов Рунного рыцаря;
2. очистка состояния Исполнителя;
3. ремонт Воина и восстановление Второго дыхания;
4. восстановление очков и ограничений Чародея;
5. расовое восстановление дополнительной ячейки.

Интерактивные шаги:

1. смена расового владения навыком;
2. выбор воинской мультиатаки;
3. подготовка заклинаний Паладина;
4. подготовка гаджетов Ремесленника;
5. настройка Конструкта.

P1 регистрирует замену имплантов в интерактивном диапазоне. Итоговая пересборка
общего эффекта `Импланты` остаётся частью транзакции Модифицирования, а не
ответственностью общего P0-сервиса.

## Интерактивный прогресс

Фоновые шаги не входят в пользовательский счётчик. Для интерактивного шага
`progress` содержит:

```js
{
  current: 2,
  total: 5,
  title(label, substep),
  header(label, substep)
}
```

Окна получают единый заголовок и верхний блок:

```text
Шаг 2/5 · Воинская мультиатака
```

Если один логический шаг открывает несколько последовательных окон, номер
шага сохраняется, а внутренний номер указывается отдельно:

```text
Шаг 5/5 · Сборка Конструкта · 1/2
Шаг 5/5 · Сборка Конструкта · 2/2
```

Форматтеры должны работать с классическим `Dialog`, `DialogV2` и обычным HTML.
Системный Compendium Browser, который нельзя безопасно переименовать через
публичный API dnd5e, остаётся ожидаемой частью текущего шага; цепочка всё равно
ждёт его результата.

## Закрытие, отмена и ошибки

Закрытие окна означает пропуск только текущего шага:

- шаг возвращает `skipped`;
- его игровые изменения не применяются;
- очередь немедленно переходит к следующему шагу.

Для интерактивных шагов действует правило «сначала решение, затем изменение».
Механика не должна частично менять документы до подтверждения выбора.

Исключение провайдера:

- перехватывается сервисом;
- превращает шаг в `failed`;
- логируется вместе с `runId`, `stepId` и Actor UUID;
- не прерывает остальные шаги;
- не вызывает глобальный откат предыдущих шагов.

После цепочки уведомление показывается только при наличии ошибок. Успешный
отдых и намеренные пропуски не создают лишних уведомлений.

## Транзакционные границы

Системный отдых dnd5e уже применён к моменту события, поэтому общей транзакции
для всей цепочки нет. Каждый игровой провайдер отвечает за атомарность своего
шага:

- предыдущие успешные шаги не откатываются;
- закрытый шаг не мутирует состояние;
- ошибка шага не должна оставлять заведомо неполную замену набора;
- существующие rollback-механизмы гаджетов сохраняются;
- P1 применяет замену имплантов и пересборку общего эффекта атомарно внутри
  своего шага.

## Foundry-хуки

В модуле остаётся один `dnd5e.restCompleted`-диспетчер:

- продолжительный отдых ставится в `LongRestPipelineService`;
- короткий отдых передаётся существующему восстановлению рун без запуска
  цепочки P0;
- неизвестный тип отдыха безопасно игнорируется.

`dnd5e.preLongRest` остаётся отдельным синхронным хуком, потому что он меняет
длительность транса или часового режима до выполнения отдыха и не является
пострестовым шагом.

Существующие прямые `restCompleted`-регистрации удаляются как из
`scripts/combat/hooks.js`, так и из интеграции Ремесленника.

## Многопользовательская модель

Цепочка запускается на клиенте, который завершил отдых и получил локальный
`dnd5e.restCompleted`. Это сохраняет текущую модель владения и не переносит
игровые окна владельца на клиента GM.

P0 не создаёт второй socket-координатор. Отдельные провайдеры продолжают
использовать существующие авторитетные socket-команды там, где изменение мира
требует GM. В будущем такая маршрутизация может быть добавлена в провайдер без
изменения контракта цепочки.

## Память и диагностика

Сервис не создаёт постоянных Actor flags, Items или Active Effects. В памяти
находятся только:

- небольшой реестр провайдеров;
- активные promise-очереди Actor;
- слабая дедупликация объектов результата;
- последние 32 результата запусков.

Завершённый результат содержит только:

- `runId`;
- Actor UUID;
- общий статус;
- для каждого шага: `id`, `status` и длительность;
- безопасное краткое описание ошибки для `failed`.

Содержимое форм, Actor snapshots и документы Foundry в историю не попадают.
История ограничена кольцевым буфером и не растёт в течение кампании.

## Совместимость миграции

Существующие публичные `handleRestCompleted` сохраняются там, где они
используются тестами или внешним кодом, но обычный Foundry-путь больше не
регистрирует их напрямую. Для смешанных обработчиков выделяются узкие методы
фонового восстановления и интерактивного выбора.

Каждый сервис регистрирует собственные шаги через общий API по модели сервисов
реакций. Центральный диспетчер не содержит проверок названий классов, рас,
предметов или имплантов.

## Проверки

Новые unit-тесты сервиса должны подтвердить:

- валидацию и запрет повторного `id`;
- стабильную сортировку `order`, затем `id`;
- фильтрацию через `isEligible`;
- повторную проверку применимости перед запуском;
- последовательное ожидание шагов;
- `completed`, `skipped` и `failed`;
- продолжение после закрытия окна;
- продолжение после исключения;
- правильный `current/total`;
- отсутствие фоновых шагов в `total`;
- последовательность двух отдыхов одного Actor;
- параллельность отдыхов разных Actor;
- дедупликацию одного объекта результата;
- очистку активной очереди в `finally`;
- ограничение истории 32 запусками.

Интеграционные и регрессионные тесты должны подтвердить:

- ровно один `dnd5e.restCompleted` в модуле;
- маршрутизацию продолжительного отдыха в цепочку;
- сохранение короткого восстановления рун;
- сохранение отдельного `preLongRest`;
- миграцию всех фоновых и интерактивных обязанностей;
- добавление прогресса в существующие окна;
- отсутствие игровых изменений при закрытии интерактивного шага;
- сохранение существующей атомарности гаджетов;
- отсутствие регрессий в тестах рас, Воина, Паладина, Чародея, Рунного рыцаря,
  Исполнителя и Ремесленника.

Перед реализационным коммитом обязательны:

- сфокусированные тесты P0;
- синтаксическая проверка изменённых модулей;
- `git diff --check`;
- полный запуск `node --test tests/*.test.mjs`.

## Критерии готовности P0

P0 готов, когда:

- модуль имеет один диспетчер завершения отдыха;
- все существующие долгосрочные механики зарегистрированы провайдерами;
- окна одного отдыха никогда не перекрываются;
- закрытие окна пропускает только текущий шаг;
- каждый интерактивный экран показывает `Шаг N/X`;
- новые механики могут подключаться публичной регистрацией;
- P1 может добавить Модифицирование без нового Foundry-хука;
- полный набор тестов проходит.
