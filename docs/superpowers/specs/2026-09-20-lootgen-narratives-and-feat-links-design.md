# Дизайн: нарративные варианты Lootgen и ссылки в описаниях черт

Дата: 2026-09-20
Статус: согласовано 2026-09-20

## 1. Наблюдаемый результат

1. Предметы из листа `Нарративное заполнение` получают при создании через инструменты модуля случайный нарративный вариант. Меняется только описание экземпляра предмета; базовое имя и механические данные остаются прежними.
2. Выбранный вариант сохраняется вместе с экземпляром и не переопределяется при повторной материализации, переносе на карту, выдаче персонажу, восстановлении состояния или повторе идемпотентной операции.
3. В чарник попадает уже изменённый Item, а не заново собранный «голый» предмет из `sourceType/sourceId`.
4. Нарративные экземпляры всегда существуют по одному и не объединяются ни друг с другом, ни с обычным экземпляром того же справочного предмета.
5. В описаниях черт упоминания других черт и терминов превращаются в обычные Foundry-ссылки `@UUID[...]` на реальные Item-документы.
6. Исходные табличные данные сохраняются в репозитории, а runtime не зависит от доступности Google Sheets.

## 2. Источники и границы

### Источники данных

- Google Spreadsheet `Ребрея: Оружие, огнестрел и снаряжение`, id `1G-UCW00vsjON05fr0CgyK03YaF82oYJemlqNKdv1JBk`.
- Лист `Нарративное заполнение`, столбцы:
  - `Оригинальный предмет`;
  - `Название`;
  - `Нарративное описание`;
  - `Ранг`.
- Лист `Глоссарий 0.1` для табличных терминов.
- Репозиторный файл `Глоссарий.txt` для состояний и терминов, отсутствующих на листе, включая `Окровавленный` и `Сбитый с ног / Лежащий ничком`.
- Существующие каталоги `data/gear.json`, `world.rebreya-feats` и `world.rebreya-actions` остаются каноническими владельцами снаряжения, черт и действий соответственно.

На момент проектирования все 160 уникальных значений `Оригинальный предмет` однозначно сопоставляются с `data/gear.json`, включая исправленную `Энциклопедия (20 томов)`.

### Входит в задачу

- сохранение точного снимка двух используемых листов;
- нормализованный runtime-каталог нарративных вариантов;
- выбор и сквозное сохранение варианта во всех путях Lootgen и инструментах модуля, создающих или переносящих эти предметы на карту;
- запрет стака нарративных экземпляров;
- Item-компендиум терминов;
- безопасная расстановка ссылок в описаниях черт;
- focused Node-тесты, обновление паспорта функций и версии модуля.

### Не входит в задачу

- живое чтение Google Sheets во время работы Foundry;
- изменение механик предметов, их базового имени, цены, ранга или таблиц выпадения;
- всплывающие подсказки и отдельный UI терминов;
- автоматическая правка произвольных world Item, созданных не через инструменты модуля;
- живые тесты Foundry, browser bridge или ручной прогон клиента в рамках этой задачи.

## 3. Сохранение таблицы и производные данные

Импорт создаёт два вида артефактов.

### 3.1. Lossless-снимок источника

В `data/source/` сохраняется UTF-8 JSON-снимок каждого используемого листа. Он содержит:

- spreadsheet id и URL;
- точное имя листа;
- заголовки в исходном порядке;
- все непустые строки и значения без нормализации;
- дату импорта;
- число строк.

Для `Нарративное заполнение` снимок должен включать все 3996 строк данных и четыре исходных столбца. Это и есть сохраняемая в репозитории таблица: снимок не обрезается до используемых runtime-полей и позволяет проверить производный каталог без обращения к Google Sheets. Сохраняется используемый лист, а не весь workbook из 28 листов.

### 3.2. Runtime-каталог

Отдельный UTF-8 JSON в `data/` содержит только нормализованные записи, необходимые модулю:

```json
{
  "schemaVersion": 1,
  "variants": [
    {
      "variantId": "stable-id",
      "gearId": "энциклопедия-20-томов",
      "sourceName": "Энциклопедия (20 томов)",
      "title": "Название варианта",
      "description": "Нарративное описание",
      "rank": 3
    }
  ]
}
```

`variantId` детерминированно выводится из стабильной идентичности строки и не зависит от её позиции после сортировки. Импорт завершается ошибкой при:

- пустом обязательном поле;
- неизвестном или неоднозначном `Оригинальный предмет`;
- дублирующемся `variantId`;
- недопустимом ранге;
- расхождении количества строк lossless-снимка и нормализуемых строк без явно разрешённой причины.

Runtime загружает только локальный JSON. Повторный импорт является отдельной обслуживающей командой/скриптом, а не частью запуска Foundry.

## 4. Выбор нарративного варианта

### 4.1. Владелец поведения

Новый чистый domain/data-сервис строит индекс `gearId -> variants[]`, проверяет каталог и предоставляет операции:

- получить варианты базового предмета;
- выбрать один вариант через переданный RNG;
- применить уже выбранный вариант к Item data;
- определить, является ли экземпляр нарративным и потому нестакаемым.

Случайность остаётся у существующего генератора: сервис не обращается к глобальному `Math.random`, если вызывающий код уже инъецирует `random`. Это сохраняет воспроизводимость focused-тестов.

### 4.2. Момент выбора

Нарративный вариант выбирается ровно один раз, когда Lootgen или другой инструмент модуля впервые формирует конкретную строку/экземпляр предмета. Далее по pipeline передаётся `narrativeVariantId`.

Выбор не повторяется:

- при построении Item data;
- при переносе на Scene/карту;
- при помещении в контейнер или извлечении из него;
- при выдаче в чарник;
- при восстановлении persisted state;
- при retry идемпотентной команды;
- при materialization upgraded/composite graph.

Это исключает ситуацию, когда в сообщении или на карте показан один текст, а персонаж получает другой.

### 4.3. Идентичность генерации

Для нарративной строки идентичность включает `sourceType`, `sourceId` и `narrativeVariantId`. Вариант участвует во всех ключах кандидата/агрегации/контейнерного хранения, где сейчас используется только `sourceType/sourceId`.

Само случайное выпадение остаётся равновероятным в рамках существующего выбора Lootgen. Если выбран базовый предмет с нарративным каталогом, один из его вариантов выбирается случайно из доступных для него строк. Ранг и прочие фильтры продолжают работать по существующим правилам предмета и каталога.

## 5. Изменение Item и сквозной data flow

### 5.1. Представление в Item

Применение варианта:

- сохраняет исходное `name`;
- заменяет `system.description.value` на безопасно сформированный HTML из `Название` и `Нарративное описание`;
- не меняет механические поля;
- записывает в `flags.rebreya-main` как минимум `narrativeVariantId`, `narrativeSourceId`/`gearId` и признак нестакаемости.

`Название` используется как заголовок внутри описания, а не как новое имя Item. Текст экранируется/рендерится существующим безопасным способом; сырая строка не вставляется как доверенный HTML.

### 5.2. Канонический поток

```text
локальный каталог
  -> случайный выбор варианта один раз
  -> Lootgen row / storage row / generated state с narrativeVariantId
  -> buildLootgenItemData применяет вариант
  -> persisted itemData
  -> Scene/карта, контейнер, чат и чарник используют тот же itemData
```

Критический инвариант: после того как `itemData` подготовлен, выдача персонажу не должна терять его и пересобирать предмет только из `sourceType/sourceId`.

### 5.3. Покрываемые пути

Изменение должно пройти через все существующие пути одного владельца поведения:

- обычная строка Lootgen;
- upgraded/composite item, включая базовый корневой предмет;
- предмет внутри контейнера и nested storage row;
- сохранённое generated state и его восстановление;
- перенос/создание на Scene через инструменты модуля;
- выдача из UI/чата/контейнера персонажу;
- идемпотентный повтор команды.

Для вложенных предметов optional `narrativeVariantId` сохраняется рядом с `sourceType/sourceId` в storage row и передаётся в общий builder. Формат descriptor v2 не меняется, если для расчёта цены/состава вариант не нужен.

## 6. Запрет стака

Нарративный Item всегда имеет количество `1` и никогда не является merge-кандидатом.

Правило действует на трёх уровнях:

1. генератор не агрегирует выбранные нарративные экземпляры;
2. container/storage pipeline не схлопывает их по базовому `gearId`;
3. inventory merge возвращает `false`, если хотя бы один Item имеет narrative flag.

Следствие: даже два экземпляра одного и того же нарративного варианта не стакаются. Обычные предметы без narrative flag сохраняют прежнее поведение.

## 7. Item-термины и ссылки из черт

### 7.1. Компендиум терминов

Создаётся и синхронизируется отдельный Item-компендиум `world.rebreya-glossary`. Документы имеют тип `feat` и используются как справочные карточки без механической автоматизации.

Предлагаемая структура папок:

- `Состояния` — `Окровавленный`, `Сбитый с ног / Лежащий ничком` и другие релевантные состояния из `Глоссарий.txt`;
- `Свойства оружия` — термины из `Глоссарий 0.1`, если для них ещё нет канонического Item в другом справочнике;
- дополнительные папки по группам только там, где это следует из источника и помогает устранить конфликт имён.

Не создаются дубликаты документов, уже принадлежащих другим каноническим каталогам:

- черты разрешаются через `world.rebreya-feats`;
- действия и реакции — через `world.rebreya-actions`;
- новый `world.rebreya-glossary` владеет только терминами и состояниями.

Статические данные состояний, уже используемые интеграцией листа dnd5e, выносятся в общий data-модуль либо адаптируются из одного источника, чтобы текст состояния не имел двух независимых владельцев.

### 7.2. Стабильные документы и порядок синхронизации

Для новых Item заранее вычисляются детерминированные Foundry `_id`. Существующие документы сохраняют свои `_id`. Перед рендерингом описаний строится индекс разрешённых целей по фактическим UUID.

Порядок boot/sync:

1. actions;
2. glossary;
3. feats.

Таким образом, во время синхронизации черт все цели уже существуют или имеют заранее известный стабильный UUID.

### 7.3. Linkifier

Linkifier работает по текстовым узлам HTML-описания черты и вставляет обычные Foundry-ссылки вида `@UUID[Compendium....Item....]{Отображаемый текст}`.

Ограничения:

- не изменять HTML-теги и атрибуты;
- не заходить внутрь существующих `<a>`;
- не изменять уже существующие `@UUID[...]`;
- не создавать ссылку черты на саму себя;
- сначала сопоставлять самые длинные имена;
- учитывать границы слов;
- неоднозначные совпадения не линковать автоматически;
- русские формы состояний разрешать только через явную таблицу псевдонимов/склонений;
- сохранять исходный отображаемый текст фразы.

Ссылки добавляются только в описания черт. Описания снаряжения и термины не проходят рекурсивный linkifier в рамках этой задачи.

## 8. Совместимость и миграция

- Существующие предметы без narrative flag остаются без изменений.
- Старое persisted generated state без `narrativeVariantId` читается как обычное состояние.
- Новый optional field не требует миграции descriptor v2.
- Повторная синхронизация компендиумов обновляет документы по стабильной идентичности, не создавая дублей.
- Удаление строки из источника не должно молча удалять world-документы или ломать ранее выданный Item: сохранённое описание и flag остаются на экземпляре. Политика удаления компендиумных терминов должна быть явной, по существующим правилам sync-сервиса.

## 9. Ошибки и диагностика

- Некорректный импорт завершается до изменения runtime-каталога.
- Если runtime-каталог содержит неизвестный `gearId`, загрузка/проверка сообщает конкретную запись.
- Если сохранённый `narrativeVariantId` отсутствует в новом каталоге, уже подготовленный `itemData` продолжает выдаваться как есть; пересборка из голого source Item не выполняется. Для старой строки без itemData используется контролируемый fallback на базовый предмет с диагностикой.
- Неразрешённое или неоднозначное упоминание в описании черты остаётся обычным текстом и учитывается в отчёте синхронизации.
- Ошибка одной ссылки не должна повреждать HTML всей черты.

## 10. Проверки

### Focused-тесты нарративов

- lossless-снимок содержит ожидаемые заголовки и 3996 строк;
- 160 исходных имён однозначно разрешаются в `gear.json`;
- выбор варианта детерминируется инъецированным RNG и статистически не фиксирован на первой строке;
- разные варианты имеют разные identity keys;
- описание меняется, имя и механика сохраняются;
- plain, upgraded/composite, container/nested и restored state сохраняют один `narrativeVariantId`;
- перенос на Scene и выдача персонажу используют подготовленный `itemData`;
- нарративные Items quantity 1 и не merge-ятся даже при одинаковом variant id;
- обычные Items продолжают агрегироваться как раньше;
- retry не выбирает новый вариант и не создаёт дубль.

### Focused-тесты ссылок

- создаются/обновляются glossary Item с детерминированными id;
- `Окровавленный` и `Сбитый с ног` разрешаются в существующие Item-термины;
- упоминание другой черты становится корректным `@UUID`;
- self-link, существующий anchor, UUID token, атрибут HTML и неоднозначное имя не изменяются;
- longest-match и явные русские формы выбирают правильную цель;
- повторная синхронизация идемпотентна и не дублирует ссылки/документы.

### Финальная проверка реализации

Без живого Foundry/bridge:

```powershell
node --test tests/*.test.mjs
git diff --check

$files = git ls-files '*.js' '*.mjs'
foreach ($file in $files) { node --check $file }

```

## 11. Предполагаемые владельцы и точки изменения

- `scripts/data/lootgen-source-catalog.js` — включение нарративной идентичности в кандидат;
- `scripts/data/lootgen-generator.js` — случайный выбор и запрет агрегации;
- `scripts/data/lootgen-container-generation.js` — сохранение варианта во вложенных строках;
- `scripts/application/lootgen-generated-state.js` — сквозная материализация plain/composite/container;
- `scripts/data/inventory-service.js` — применение описания и запрет merge;
- новый data-модуль нарративного каталога — единственный владелец lookup/apply;
- `scripts/data/feats-compendium.js` — индекс целей и linkifier при sync;
- новый glossary compendium service/data module — Item-термины;
- `scripts/main.js` — только композиция и порядок sync;
- `tests/` — focused-тесты владельцев;
- `docs/function-passport.md` — новые/изменённые методы, data flow и профильные тесты;
- `README.md` — только если меняется публичный API или пользовательская команда;
- `module.json` и versioned forwarder — обязательное повышение версии при реализации клиентских изменений.

Большие существующие файлы не получают второго владельца поведения: новые правила подключаются через текущие builders, services и composition root.

## 12. Критерии готовности реализации

- таблица сохранена в репозитории и из неё воспроизводимо строится проверенный runtime-каталог;
- любой поддерживаемый путь инструментов модуля создаёт один случайный вариант и доставляет тот же изменённый Item до карты/контейнера/чарника;
- нарративные предметы не стакаются;
- glossary Items существуют, а ссылки в чертах ведут на реальные Item-документы без повреждения HTML;
- обратная совместимость подтверждена focused-тестами;
- паспорт функций и версия модуля обновлены;
- все офлайн-проверки проходят; живой Foundry и bridge не использовались.
