# Универсальные runtime-компоненты автоматизации заклинаний

## Статус

Утверждённый дизайн первого этапа.

Целевой стек:

- Foundry VTT 13;
- dnd5e 5.2.5;
- Midi-QOL 13.0.61;
- DAE 13.0.27.

## Цель

Заложить расширяемые точки входа для боевой автоматизации заклинаний и прекратить
рост отдельных монолитных сервисов для каждого нового заклинания.

Первый этап должен:

1. создать общий registry деклараций автоматизации;
2. создать общий hook-bridge между Foundry/Midi и специализированными runtime;
3. реализовать `SpellInstanceRuntime` на реальном сценарии
   «Мельфовы маленькие метеоры»;
4. реализовать независимый `SummonLifecycleRuntime` для будущих нативных
   Foundry-призывов;
5. зафиксировать точки регистрации для перехвата магии и боевых зон;
6. не мигрировать и не изменять текущую реализацию ремесленника;
7. не переписывать существующее Контрзаклинание на первом этапе.

## Граница автоматизации

Runtime предназначен для детерминированной боевой механики:

- перехват, завершение и временное подавление магических эффектов;
- нативные Foundry-призывы;
- заклинания с сохраняемым состоянием и повторными активациями;
- обычные боевые зоны, реагирующие на движение и ходы.

Заклинания, требующие свободного решения мастера, остаются заявками. В первый
этап не входят `Wish`, `Magic Jar`, `Glyph of Warding`, `Contingency`,
`Prismatic Wall`, `Gate`, `Teleport`, `Demiplane`, `Astral Projection` и
другие межсценовые или открыто сформулированные эффекты.

## Рассмотренные подходы

### Выбранный: отдельный новый runtime рядом с ремесленником

Новый summon engine обслуживает только activities с новым явным automation-флагом.
Существующий `CraftsmanConstructorService` продолжает самостоятельно слушать
свои hooks и хранить прежние flags.

Преимущества:

- нулевой риск скрытой миграции уже созданных конструктов;
- существующее поведение ремесленника остаётся проверяемым прежними тестами;
- будущие призывы получают один общий контракт;
- ремесленника можно перенести позже отдельной задачей.

Недостаток: до будущей миграции в модуле временно существуют две реализации
маршрутизации призывов.

### Отклонённый: совместимый адаптер ремесленника сразу

Общий движок мог бы делегировать старые activities в
`CraftsmanConstructorService`. Это быстрее устраняет две системы, но затрагивает
порядок настройки synthetic Actor, удаления нового токена при ошибке, вывода
старого конструкта, ремонта и сохранения пользовательского снаряжения.

### Отклонённый: полное извлечение логики ремесленника

Немедленный перенос его жизненного цикла в общий движок уменьшил бы дублирование,
но создаёт максимальный риск регрессий и не нужен для первого потребителя
`SpellInstanceRuntime`.

## Общая архитектура

### `SpellAutomationRegistry`

Registry хранит декларации по составному ключу:

```text
runtime + recipe + version
```

Он предоставляет операции:

```js
register(definition)
resolve(activity)
has(activity)
```

Registry не подписывается на hooks, не сканирует мир и не исполняет игровую
логику. Повторная регистрация одного ключа с другой декларацией является ошибкой
инициализации.

Обычная activity без automation-флага всегда пропускается. Activity с явным
флагом, но неизвестным runtime, recipe или version блокируется до расходования
ресурсов и показывает одно диагностическое сообщение: явно запрошенная, но
неподдерживаемая автоматизация не должна молча разыгрываться наполовину.

### `SpellAutomationHookBridge`

Hook-bridge регистрируется один раз и переводит Foundry/Midi hooks в ограниченный
набор внутренних событий:

- до использования activity;
- после завершения Midi workflow;
- после `dnd5e.postSummon`;
- создание, изменение и удаление ActiveEffect;
- вход, выход и пересечение Region;
- начало и завершение хода или боя.

Каждый обработчик сначала читает automation-флаг конкретной activity или
связанного документа. Если подходящей декларации нет, он немедленно возвращает
управление без обхода actors, scenes, items или effects.

Hook-bridge не выполняет правила конкретного заклинания. Он создаёт
`AutomationContext` и передаёт событие выбранному runtime.

### Специализированные runtime

Первый архитектурный слой содержит четыре независимых компонента:

- `SpellInstanceRuntime` — сохраняемое состояние и повторные activities;
- `SummonLifecycleRuntime` — нативный Foundry/Midi-призыв;
- `SpellInterceptionRuntime` — будущие Counterspell, Dispel Magic и
  Antimagic Field;
- `SpellAreaRuntime` — будущие Spirit Guardians, Moonbeam, Spike Growth и
  аналогичные зоны.

`SpellInstanceRuntime` и `SummonLifecycleRuntime` получают рабочее поведение на
первом этапе. Interception и Area получают только стабильные интерфейсы
регистрации и маршрутизации, без реализации конкретных правил.

## Декларация activity

Автоматизируемая activity получает явный флаг:

```js
flags["rebreya-main"].automation = {
  runtime: "spell-instance",
  recipe: "melfs-minute-meteors",
  role: "cast",
  version: 1
}
```

Обязательные поля:

- `runtime` — идентификатор специализированного runtime;
- `recipe` — стабильный семантический идентификатор рецепта;
- `role` — роль activity внутри рецепта;
- `version` — версия контракта декларации.

Runtime не определяет заклинание по локализованному имени, Item ID или позиции
activity в коллекции.

Внутренние дочерние вызовы дополнительно получают transient usage flags:

```js
flags["rebreya-main"].automationInvocation = {
  operationId,
  parentInstanceId,
  childInvocation: true,
  actionEconomyBypass: true
}
```

Эти flags не сохраняются в Item и существуют только в контексте текущего
workflow. На первом этапе дочерний usage config также сохраняет существующий
совместимый флаг:

```js
flags["rebreya-main"].spellAutomationChild = true
```

Благодаря этому текущий `SpellAutomationService` пропускает дочерний взрыв без
переписывания Counterspell state machine.

## `AutomationContext`

Все runtime получают единый объект контекста:

```text
operationId
runtime
recipe
role
actor
token
item
activity
usageConfig
workflow
rootWorkflowId
parentInstanceId
castLevel
targets
combatSnapshot
childInvocation
```

`combatSnapshot` фиксирует combat UUID, раунд, ход и текущего combatant в момент
начала операции. Контекст не хранит скрытое глобальное состояние и может быть
собран повторно после перезагрузки клиента из документов Foundry.

## `SpellInstanceRuntime`

### Назначение

Runtime управляет одним экземпляром успешно наложенного заклинания:

- создаёт состояние после завершённого родительского каста;
- связывает его с нативным ActiveEffect;
- выполняет последующие дочерние activities;
- сериализует конкурентные изменения;
- прекращает доступ к activities после завершения эффекта.

### Модель `SpellInstance`

Источником истины является flag нативного ActiveEffect:

```js
flags["rebreya-main"].spellInstance = {
  schema: 1,
  instanceId,
  recipeId,
  ownerActorUuid,
  sourceItemUuid,
  rootActivityUuid,
  rootWorkflowId,
  castLevel,
  createdAt,
  revision,
  state
}
```

`state` принадлежит рецепту. Runtime не интерпретирует его поля напрямую, кроме
общей проверки сериализуемости.

ActiveEffect является якорем времени жизни. Удаление эффекта немедленно делает
экземпляр недоступным. Отдельный параллельный эффект концентрации не создаётся.

### Согласованность

Все изменения экземпляра выполняются под блокировкой `instanceId`.

Каждая мутация:

1. повторно читает ActiveEffect;
2. проверяет ожидаемую `revision`;
3. вычисляет новое состояние;
4. увеличивает `revision`;
5. сохраняет результат одной документной операцией.

Повтор события с тем же `operationId` возвращает уже сохранённый результат.
Двойной клик или повторный Midi hook не должны дважды расходовать ресурс.

## `SummonLifecycleRuntime`

### Назначение

Runtime дополняет нативную dnd5e `SummonActivity`. Он не создаёт собственный
формат Actor или Token и не подменяет размещение Foundry.

### Контракт provider

```js
{
  recipe,
  version,
  validate(context),
  afterSpawn(context, tokens),
  onCleanup(context, tokens)
}
```

- `validate` выполняется до нативного использования activity;
- Foundry самостоятельно выбирает профили и размещает токены;
- `afterSpawn` получает только токены конкретной операции;
- `onCleanup` является необязательным callback после штатного завершения связи.

### Поток операции

1. pre-use создаёт `operationId` для зарегистрированной summon activity.
2. `operationId` передаётся через usage/summon options.
3. Foundry выполняет нативное размещение.
4. `dnd5e.postSummon` возвращает созданные токены.
5. Runtime записывает общий `summonLink`.
6. Provider выполняет дополнительную конфигурацию.
7. При ошибке удаляются только токены текущего `operationId`.

Общий flag связи:

```js
flags["rebreya-main"].summonLink = {
  schema: 1,
  operationId,
  instanceId,
  summonerActorUuid,
  sourceItemUuid,
  recipeId,
  controllingEffectUuid
}
```

Midi-QOL остаётся владельцем штатной привязки токенов к концентрации и
автоматического удаления через `flags.dnd5e.dependentOn`.

### Изоляция ремесленника

На первом этапе:

- `craftsmanConstructor` и `craftsmanConstruct` flags не изменяются;
- activities ремесленника не получают новый automation-флаг;
- `CraftsmanConstructorService` не регистрируется в новом registry;
- его `dnd5e.postSummon`, updateToken, updateActor и остальные hooks сохраняются;
- новый runtime не читает и не записывает состояние конструкта;
- существующие тесты ремесленника остаются неизменными.

Будущая миграция ремесленника является отдельной задачей.

## Точки входа будущих runtime

### `SpellInterceptionRuntime`

Первый этап фиксирует регистрацию рецептов и методы:

```text
handleSpellAttempt(context)
handleDispelRequest(context)
handleSuppressionBoundary(context)
```

Предполагаемые будущие потребители:

- Counterspell отменяет ещё не завершившийся каст;
- Dispel Magic завершает выбранный действующий эффект;
- Antimagic Field временно подавляет, но не удаляет пересекающий область эффект.

Существующее Контрзаклинание остаётся в `SpellAutomationService` и не мигрирует.

### `SpellAreaRuntime`

Первый этап фиксирует регистрацию рецептов и методы:

```text
handleEnter(context)
handleExit(context)
handleMoveSegment(context)
handleTurnStart(context)
handleTurnEnd(context)
```

Конкретные Region behaviors и заклинания на первом этапе не реализуются.

## Первый рецепт: «Мельфовы маленькие метеоры»

### Подтверждённые правила

- заклинание третьего уровня;
- концентрация до 10 минут;
- успешный каст создаёт 6 метеоров;
- каждый уровень ячейки выше третьего добавляет 2 метеора;
- при касте можно сразу выпустить 0, 1 или 2 метеора;
- на последующих ходах bonus action выпускает 1 или 2 метеора;
- каждый метеор выбирает видимую точку в пределах 120 футов;
- обе точки могут совпадать;
- каждый метеор создаёт отдельный взрыв радиусом 5 футов;
- каждое существо в области делает отдельный Dexterity save;
- урон одного взрыва — `2d6` огнём, половина при успехе;
- заклинание заканчивается после расходования последнего метеора.

Начальный запас:

```text
6 + 2 × (castLevel - 3)
```

### Activities предмета

Управляемый spell Item содержит три activities.

#### `Cast`

- тип: `utility`;
- активация: одно действие;
- дальность: на себя;
- длительность: концентрация до 10 минут;
- расходует одну ячейку выбранного уровня;
- не создаёт шаблон и не наносит урон самостоятельно;
- роль автоматизации: `cast`.

#### `Release Meteors`

- тип: `utility`;
- активация: одно bonus action;
- не расходует ячейку;
- открывает выбор одного или двух метеоров;
- запускает последовательность дочерних взрывов;
- роль автоматизации: `release`.

#### `Meteor Burst`

- тип: `save`;
- скрытая дочерняя activity;
- дальность размещения: 120 футов;
- шаблон: круг радиусом 5 футов;
- спасбросок: Dexterity от spell save DC актёра;
- урон: `2d6` огнём, половина при успехе;
- мгновенная длительность;
- не расходует ячейку;
- роль автоматизации: `burst`.

### Состояние рецепта

```js
state: {
  totalMeteors,
  remainingMeteors
}
```

`totalMeteors` фиксируется уровнем родительского каста.
`remainingMeteors` изменяется только через транзакцию экземпляра.

### Родительский каст

После успешного завершения `Cast` runtime:

1. убеждается, что workflow не отменён и не контрзаклинан;
2. получает UUID созданного concentration ActiveEffect из результатов workflow;
3. создаёт на нём `SpellInstance`;
4. предлагает выпустить 0, 1 или 2 метеора;
5. последовательно запускает выбранные `Meteor Burst`;
6. не расходует дополнительное действие или bonus action.

Если Counterspell отменил родительский каст, экземпляр и запас не создаются.

Если Midi не сообщает UUID эффекта, допускается fallback-поиск только среди
effects текущего Actor по точному Item origin и времени/идентификатору текущего
workflow. Поиск по имени эффекта запрещён. Несколько подходящих effects являются
ошибкой, а не поводом выбрать первый.

### Последующий залп

До запуска `Release Meteors` runtime:

1. находит активный экземпляр рецепта на Actor;
2. блокирует activity при отсутствии эффекта или метеоров;
3. предлагает 1 либо 2, но не больше оставшегося запаса;
4. при отмене диалога возвращает `false` до расходования bonus action;
5. запускает дочерние взрывы последовательно.

Одна активация `Release Meteors` расходует ровно одно bonus action независимо
от количества выбранных метеоров.

### Дочерний взрыв

Для каждого метеора:

1. запускается полноценная save-activity через Midi-QOL;
2. пользователь размещает отдельный 5-футовый шаблон;
3. отмена размещения не расходует этот метеор;
4. после подтверждения точки runtime атомарно резервирует один метеор и помечает
   workflow как committed;
5. существа в шаблоне совершают отдельные saves;
6. Midi применяет половинный урон, сопротивления и иммунитеты;
7. временный шаблон очищается после завершения workflow;
8. успешное завершение превращает резервирование в окончательный расход;
9. ошибка до первого применённого Midi-результата снимает резервирование;
10. после любого применённого save или damage результат не откатывается, а
    метеор остаётся потраченным.

Два метеора никогда не запускаются через `Promise.all`: второй начинается
только после завершения размещения и commit первого. Совпадающие точки всё равно
создают два независимых save/damage workflow.

Дочерний взрыв:

- не считается новым кастом;
- не расходует ячейку;
- не вызывает новое окно Counterspell;
- не повторяет оплату метамагии;
- не открывает рекурсивный диалог `Release Meteors`;
- сохраняет контекст родительского spell Item для модификаторов урона.

### Завершение

При `remainingMeteors === 0` runtime удаляет связанный ActiveEffect, поскольку
заклинание заканчивается после последнего метеора.

Удаление эффекта из-за потери или добровольного прекращения концентрации также
делает последующие залпы недоступными. После перезагрузки клиента экземпляр
восстанавливается чтением flag существующего ActiveEffect; отдельный world scan
не выполняется.

## Ошибки и rollback

- Ошибка до запуска родительской activity блокирует использование без расхода
  слота или действия.
- Ошибка создания `SpellInstance` после успешного каста не удаляет штатный
  concentration effect. Автоматический начальный залп не запускается, а игрок и
  мастер получают одно сообщение об ошибке.
- Отмена размещения точки не расходует соответствующий метеор.
- Ошибка до commit дочернего workflow возвращает управление без расхода.
- После частичного применения Midi-урона автоматический rollback не выполняется:
  метеор остаётся потраченным, а сообщение содержит `operationId`.
- Ошибка первого метеора останавливает последовательность до второго.
- Если первый метеор уже committed, bonus action последующего залпа считается
  использованным даже при отмене или ошибке второго.
- Ошибка summon-provider удаляет только токены его `operationId`.
- Runtime никогда не ремонтирует чужие документы и не делает фоновые повторы.

Документную мутацию выполняет владелец документа. При недостаточных правах
используется существующий active-GM/socket путь и
`WorldMutationCoordinator.runIdempotent`.

Если Midi-QOL отсутствует или его API несовместим, модуль продолжает загружаться,
но activities с новым явным automation-флагом блокируют автоматизированное
использование одним предупреждением. Частичный запас, шаблоны или summon links
не создаются.

## Производительность

Обязательные свойства:

- нет сканирования мира на `ready`;
- нет документных записей при загрузке мира;
- нет периодических таймеров;
- hooks регистрируются один раз;
- первая проверка hook ограничена чтением automation-флага;
- registry выполняет прямой поиск по составному ключу;
- ActiveEffect ищется только у Actor текущей activity;
- пустые Interception и Area runtime не выполняют игровую работу.

### Критерий загрузки мира

Сравниваются минимум 20 тёплых запусков одного мира до и после изменений по
одному DOM-ready критерию.

Допустимый регресс медианы:

- не более 50 мс;
- и не более 5%.

Оба ограничения должны выполняться одновременно.

Повторяющиеся `updateItem`, `updateActiveEffect` или другие документные записи в
тихом окне загрузки являются дефектом независимо от времени.

## Тестирование

### Registry и hook-bridge

- регистрация и разрешение деклараций по `runtime + recipe + version`;
- конфликтующая повторная регистрация отклоняется;
- обычная activity немедленно пропускается;
- дочерний invocation не запускает родительскую автоматику;
- повтор одного `operationId` идемпотентен;
- hooks регистрируются один раз.

### `SpellInstanceRuntime`

- экземпляр создаётся только после успешного workflow;
- состояние сохраняется на нативном ActiveEffect;
- конкурентные мутации не теряют и не дублируют ресурс;
- неверная `revision` повторяет чтение или безопасно останавливает операцию;
- удаление эффекта блокирует последующие uses;
- перезагрузка клиента не требует repair-записи.

### Метеоры Мельфа

- запас равен 6 на третьем уровне и растёт на 2 за уровень;
- начальный выбор допускает 0, 1 и 2;
- последующий выбор допускает 1 и 2;
- начальный залп не расходует bonus action;
- последующий залп расходует одно bonus action;
- каждый метеор создаёт отдельный шаблон и Dexterity-save workflow;
- Midi применяет `2d6` fire damage и половину при успехе;
- одинаковые точки не объединяют saves или damage;
- отмена первого шаблона ничего не расходует;
- отмена второго сохраняет расход и результат первого;
- последний метеор завершает ActiveEffect;
- потеря концентрации блокирует залп;
- контрзаклинанный родительский каст не создаёт экземпляр;
- child invocation не вызывает Counterspell и не расходует ячейку;
- ошибка после частичного применения не пытается откатить Midi damage.

### `SummonLifecycleRuntime`

- обрабатываются только activities с новым summon-флагом;
- pre-use и postSummon связываются одним `operationId`;
- provider получает только токены своей операции;
- `summonLink` содержит UUID источника и управляющего эффекта;
- ошибка provider удаляет только новые связанные токены;
- обычный нативный призыв без декларации пропускается.

### Совместимость ремесленника

- оба существующих файла тестов ремесленника проходят без изменения ожиданий;
- новый runtime игнорирует `craftsmanConstructor` activity;
- прежние flags версии 1 не изменяются;
- существующий hook ремесленника продолжает получать `dnd5e.postSummon`;
- тесты подтверждают отсутствие новых записей на старых конструктах.

### Живая Foundry

Используется отдельный тестовый Actor; игровые персонажи игроков не изменяются.

Проверяются:

1. каст на третьем и повышенном уровнях;
2. начальный выбор 0, 1 и 2;
3. два разных шаблона;
4. два шаблона в одной точке;
5. успешные и проваленные saves;
6. сопротивление и иммунитет к огню;
7. отмена первого и второго размещения;
8. последующий bonus-action залп;
9. расход последнего метеора;
10. потеря концентрации;
11. Counterspell родительского каста;
12. перезагрузка с активным экземпляром;
13. тестовый summon-provider на отдельной summon activity;
14. загрузка мира с включёнными и отключёнными новыми runtime.

## Совместимость и миграция

Первый этап не содержит миграции документов. Новые managed spell Items получают
automation flags через существующую управляемую синхронизацию сборника.

Старые:

- предметы;
- actors;
- токены;
- конструкты ремесленника;
- Counterspell flags

не переписываются на старте мира.

## Вне первого этапа

- миграция ремесленника в `SummonLifecycleRuntime`;
- перенос Counterspell в `SpellInterceptionRuntime`;
- реализация Dispel Magic;
- реализация Antimagic Field;
- реализация конкретных Region-заклинаний;
- межсценовые переходы и произвольные заявки;
- визуальные метеоры на токене;
- анимации Sequencer;
- общий интерпретатор естественного языка правил;
- автоматический rollback уже применённого Midi damage.
- полное восстановление module-owned `SpellInstance` через Midi Undo; первый этап
  гарантирует только описанный pre-result refund и идемпотентность операций.
