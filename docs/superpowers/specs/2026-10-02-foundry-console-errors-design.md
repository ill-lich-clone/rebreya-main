# Исправление ошибок из пользовательского лога

Статус: спецификация для согласования; продуктовый код не изменён.

## Наблюдаемый результат

Настройки Foundry открываются с одной работающей кнопкой дирижабля; обычные обновления Actor не вызывают исключения очистки трансформаций; переходы боя без предыдущего Actor не вызывают исключения effectmacro. Существующие игровые правила и данные сохраняются.

## Подтверждённые причины

Среда проверки: Foundry 13.351, dnd5e 5.2.5, GM CODEX, 2026-10-02.

- Все четыре Item с `object is not iterable` из лога имеют тип `rebreya-main.gadget`: Сфера Механуса у М-010-7, Заряженный ботинок, Форсажный инжектор и Силовая перчатка у Харлифа. В новом сеансе у каждого native ActivityCollection с iterator/filter. Во всех world Actors не найдено Item с activities без filter. Их advancement подготовлен, конфигурация инициативы читается, HP конечны. Исправление ранней регистрации гаджетов уже существует в commit `7f770ec4`; focused tests: 4 passed, 0 failed. Точную версию клиента исходного лога установить нельзя. Повторная правка гаджетов не требуется по текущим данным.
- `D:/FoundryVTT/Data/modules/sm-airship/scripts/module.js:307`: renderSettings вызывает `html.find` на HTMLElement Foundry 13.
- `D:/FoundryVTT/Data/modules/transform-cleanup/transform-cleanup.mjs:85`: onUpdateActor обращается к changed.flags.dnd5e без проверки наличия этих объектов. Обычное изменение имени и обновление midi flags воспроизводят оба исключения из лога.
- `D:/FoundryVTT/Data/modules/effectmacro/module.mjs:381`: getExecutor обращается к actor.testUserPermission, хотя updateCombat на строках 503–504 передаёт отсутствующего предыдущего Actor. В начале боя это допустимый случай.

Три дефекта сторонних модулей воспроизведены из установленного исходника в изолированном Node VM без изменений мира.

## Точечные изменения и владельцы

1. В существующем renderSettings sm-airship нормализовать DOM/jQuery input и сохранить вставку кнопки перед settings-documentation либо в конец контейнера. Сохранить canOpenApp, обработчик открытия и предотвращение дубликатов.
2. В существующем onUpdateActor transform-cleanup проверять наличие dnd5e flags перед оператором in. Только active GM по прежнему удаляет Actor при наличии `-=isPolymorphed`; другие изменения ничего не удаляют. Это сохранение прежнего поведения удаления, не новый маршрут мутации.
3. В effectmacro вернуть null из getExecutor для отсутствующего Actor и пропустить _executeAppliedEffects для такого Actor. Сохранить выбор активного владельца/GM, фильтр appliedEffects и порядок исполнения существующих эффектов.

Локальные установленные файлы этих трёх модулей находятся вне Git-репозитория rebreya-main. До изменения сохранить точные резервные копии и manifest в отдельной папке вне клиентской раздачи. Повысить версии изменённых модулей и проверить их entrypoints. Обновление стороннего модуля может заменить локальную правку; сохранить проверяемый patch и manifest изменённых файлов. Не внедрять эти исправления через глобальный compatibility hook rebreya-main.

## Сохраняемые контракты

Не менять settings, public API, namespace flags, authored activities/formulas, Item IDs/types, ресурсы и uses.spent, quantity rules, budget spending, HP, текущий бой, эффекты или права пользователей. Не выполнять миграцию мира, броски, урон или удаление реальных Actor для проверки.

## Проверка и границы

Перед исправлениями закрепить regression tests на реальном исходнике: DOM/jQuery, двойной render и запрет доступа; отсутствующие flags, чужие flags и реальное снятие polymorph с mocked deletion; отсутствующий Actor, owner/GM selection и выполнение валидных эффектов. Показать red до правки и green после.

Проверить синтаксис изменённых файлов, manifest JSON и целевые тесты. В текущем Foundry-сеансе проверить обновлённый renderSettings и существующие публичные entrypoints без persisted world writes. Полная проверка runtime rebreya-main нужна только если его runtime-файлы окажутся изменены.

ResizeObserver и сообщения midi о reactions не имеют подтверждённой самостоятельной причины. HP NaN, инициативу и byType повторно оценить после загрузки клиента: сейчас эти симптомы не воспроизводятся, HP вручную не исправлять. Сбой sheet activities сейчас не воспроизводится. Не считать весь пользовательский лог исправленным до повторной проверки после применённых изменений.

## Review gate

Пользователь согласует эту спецификацию. Затем создаётся письменный implementation plan с отдельным review gate согласно AGENTS.md; реализация — executing-plans в текущем чате. Это точечные исправления существующих потоков; письменные документы обязательны по пользовательскому AGENTS.md даже для bounded-задачи.
