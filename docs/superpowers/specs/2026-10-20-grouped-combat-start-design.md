# Начало сражения и общий ход одинаковых существ

Дата: 2026-10-20. Статус: утверждена пользователем 2026-10-21.

Пользователь согласовал концепцию: штатное отображение групп dnd5e, настоящий общий ход под управлением Ребреи, отдельное начало и конец хода каждого существа. Эта спецификация уточняет контракт до составления плана и изменения runtime-кода.

## Наблюдаемый результат

В существующей world-папке макросов «Ребрея» появляется макрос «Начать сражение». GM выделяет существ текущей сцены и запускает макрос. Модуль добавляет подходящие токены, определяет группы, бросает недостающую инициативу и начинает бой. В трекере dnd5e одинаковые NPC показаны штатной свёрнутой группой. Одно обычное нажатие перехода к следующему ходу завершает текущую группу и начинает следующую.

У всех участников группы начало хода наступает при входе в группу, конец — при выходе. Для группы из трёх существ недопустимо обработать начало/конец второго и третьего только при переходе к следующей группе. Каждое существо сохраняет отдельные HP, эффекты, ресурсы, действия и реакции.

## Выбор участников и инициатива

- Источник — только выделенные Token текущей сцены; пустой подходящий выбор показывает русское уведомление без создания пустого Combat.
- Допускаются существа dnd5e типов `character` и `npc`. Нет Actor, хранилище по каноническому `isStorageActor`, объект карты по module flags, а также явно обозначенный системой NPC-объект исключаются. Имена токенов не используются для определения хранилища или объекта.
- Старт доступен GM. Полномочия проверяются повторно на исполняющем active GM; переданные клиентом признаки ownership не являются доказательством прав.
- Персонажи и linked-токены получают индивидуальные ходы. Группируются только unlinked NPC с одинаковым исходным `Token.baseActor`, disposition и совпадающими эффективными правилами инициативы. Одно имя, одинаковое численное значение инициативы или общий вид существа недостаточны.
- Текущие HP и обычные эффекты не разделяют одинаковых NPC. Эффект, меняющий формулу, модификатор или advantage/disadvantage инициативы, может разделить группу. Если эквивалентность правил инициативы нельзя подтвердить, существа получают отдельные группы.
- Для новой однородной группы выполняется один штатный бросок инициативы. Его результат получают все участники. Авторские формулы, модификаторы, advantage/disadvantage, выбранный штатный режим видимости броска и правила сообщений сохраняются; фиксированная замена на `1d20 + dex` запрещена.
- При равных значениях порядок групп детерминирован; участники каждой группы непрерывны в native turn order. Случайное совпадение инициативы разных групп не объединяет их.

## Действующий бой и повторный запуск

- Используется активный бой текущей сцены. Если подходящего активного боя нет, создаётся scene-linked Combat; бой другой сцены не изменяется и не переключается автоматически.
- Повторный запуск не создаёт повторных Combatant для токена, не сбрасывает раунд, активную группу и уже брошенную инициативу. Переброс уже установленной инициативы остаётся отдельным штатным действием пользователя.
- Если существующий обычный бой уже начат, текущий раунд сохраняет native ходы. Макрос подготавливает группы и сообщает, что общий режим включится со следующего раунда: уже выполненные начала/концы текущего раунда не переигрываются. Для не начатого боя группировка применяется перед стартом.
- Новое существо с недостающей инициативой бросает её самостоятельно либо получает уже установленную инициативу подходящей группы. Если у кандидатов уже разные установленные инициативы, макрос сохраняет их и разделяет на разные логические группы по установленной инициативе, даже при одинаковом исходном Actor.
- Подкрепление в уже активную открытую группу получает начало хода только нового участника и затем общий конец группы. Начало остальных и события «каждый ход» не повторяются. Если ход соответствующей группы в этом раунде уже завершён, новый участник ждёт следующего её обычного начала. Добавление и переход сериализованы; новичок не получает конец до своего первого начала.
- Удаление/отметка defeated одного участника не удаляет остальных. Пропуск defeated сохраняет настройку Foundry `skipDefeated`; 0 HP сами по себе не исключают персонажа и его спасброски от смерти.

## Общие фазы и эффекты

Порядок одного перехода: завершить эффекты конца текущей группы → завершить раунд, если он сменился → начать новый раунд → выполнить эффекты начала следующей группы → разрешить дальнейший переход. Внутри каждой фазы участники обрабатываются последовательно в стабильном порядке; «одновременно» означает одну игровую границу, а не конкурентные записи HP.

1. Для каждого участника начало и конец обрабатываются ровно один раз на соответствующей фазе раунда. Смена представителя, раскрытие строки, камера и ручное выделение токена не являются новой фазой.
2. DAE/Times Up сохраняют `turnStart`, `turnEnd`, `turnStartSource`, `turnEndSource`, `startEveryTurn`, `endEveryTurn`, `startEndEveryTurn` и варианты `Any`; disabled/suppressed и source-origin трактуются по правилам провайдера.
3. Сроки effects в rounds/turns и authored `duration.startRound/startTurn` сохраняются. Adapter сопоставляет native позицию с логической фазой, не переопределяет авторскую длительность и не переводит эффекты молча в seconds. Эффект, созданный после уже прошедшего начала группы, не получает дополнительный start в этом же раунде.
4. MIDI-QOL `OverTime` и `ActivityOverTime`, урон, лечение, saves, снятие эффектов и концентрация проходят штатный workflow соответствующего провайдера. Затихающий урон Ребреи сохраняет существующий маршрут `OverTime → RollComplete → изменение конкретного счётчика`; прямой дополнительный HP-тик запрещён.
5. Нативные восстановления ресурсов dnd5e, Effect Macro и автоматизации Ребреи (включая реакции, классовые ресурсы, длительности и cooldown) получают нужные фазы каждого существа. Восстановления от броска инициативы относятся ко всем участникам общего броска. События «каждый ход»/«каждый раунд» исполняются один раз на логический ход/раунд, а не дополнительно на каждого технического участника. Штатная очистка movement history применяется к каждому участнику на соответствующей фазе.
6. Один и тот же провайдер не обрабатывает одновременно native переход и его grouped-проекцию. Массовый повторный `Hooks.callAll` для каждого участника не используется как замена интеграции.
7. Переход назад — навигация: он не отменяет уже нанесённый урон и не воспроизводит уже выполненные фазы при возвращении вперёд. Ручной переход через несколько групп проводит реальные пересечённые невыполненные фазы по порядку. Persistent receipt различает шаги по Combat, раунду, стабильному group ID, Combatant ID, фазе, провайдеру и конкретному эффекту/шагу; уже завершённый шаг отличается от ещё не посещённого без повторного исполнения. Эти правила применяются к управляемым боям Ребреи; обычные бои сохраняют существующее поведение.
8. На время незавершённого workflow повторный переход присоединяется к текущей операции либо отклоняется как устаревший, а не запускает параллельную фазу.
9. Ошибка провайдера останавливает следующий переход и показывает участника/фазу. Завершённые шаги не повторяются. После reload неоднозначно завершившийся внешний workflow требует проверки GM; автоматическое повторение с риском двойного урона запрещено.

## Отображение и камера

- Используется штатная группировка `CombatTracker5e`, без отдельного трекера или окна управления боем. Core Combatant каждого существа сохраняется. Группы с одинаковым native display key, но разными эффективными правилами инициативы отображаются раздельно узким adapter к существующему grouping extension point.
- Активная свёрнутая строка обозначает общую группу. Её участники доступны для раскрытия; технический порядковый счётчик dnd5e дополняется обозначением «общий ход», чтобы не показывать ложное требование отдельно заканчивать каждого.
- После успешного начала хода камера плавно перемещается к существу; для группы — к первому доступному непобеждённому участнику в стабильном порядке, затем к первому доступному участнику. Масштаб, выделение и targets не меняются.
- GM видит доступные ему токены. У игрока нет панорамирования к скрытому/невидимому для него токену или чужой сцене; координаты не отправляются ему отдельным широковещательным сообщением. Переход к другому видимому участнику группы не раскрывает скрытого представителя.
- Новая client-настройка автокамеры включена по умолчанию; отключение действует только для этого клиента. Автокамера относится к управляемым боям Ребреи, включая первый ход; чужие бои сохраняют настройки и поведение.

## Владельцы и границы реализации

- `scripts/main.js` остаётся единственным composition root и публикует тонкий `startCombatFromSelection()` через `game.rebreyaMain` и `game.modules.get("rebreya-main").api`; переходы направляются к тому же application owner существующими кнопками трекера. `GrappleMacroService.syncManagedDocuments()` расширяется новым managed sourceId; существующая папка и макросы переиспользуются, unmanaged документы не перезаписываются.
- Application owner общего боя отвечает за выбор, группы, start/advance, ревизии, фазовые receipts и очередь одного Combat. Pure combat rules строят группы и переходы; сохранение выполняется через Foundry Document/repository boundary и существующий mutation coordinator.
- Состояние управляемого боя находится в versioned module flag Combat: группы и их участники, текущая логическая позиция, ревизия, границы присоединения и receipts выполненных шагов. Исходные Actor, имена и авторские ActiveEffect не заменяются общим Actor.
- GM/player ingress использует валидируемые typed commands. Active GM повторно разрешает Combat/Token и проверяет scene, ожидаемую ревизию и отправителя. Старт и изменение состава требуют GM; завершение индивидуального хода разрешено владельцу действующего существа по штатной политике, общего NPC-хода — GM. На клиентах нет самостоятельной привилегированной записи world-state.
- Штатные Next/Previous/End Turn и public API направляются к одному application owner. Для управляемых боёв используется проверенная protected lifecycle boundary `Combat._manageTurnEvents`, чтобы native private обход пропущенных индексов не запускал промежуточные циклы. Приватные `#triggerTurnEvents` не изменяются. Вне module flag исходный lifecycle вызывается без изменения.
- Compatibility adapter централизует фазовую обработку DAE/Times Up, MIDI-QOL, Effect Macro, dnd5e и существующих Rebreya owners. Он переиспользует API провайдеров; адаптация внутренних hook callbacks изолирована, привязана к проверенному контракту и не редактирует исходники сторонних модулей. В установленном MIDI-QOL `ActivityOverTime` не экспортирован: для него требуется отдельно проверенная изолированная проекция зарегистрированного callback, без запуска остальных провайдеров и сторонних HP-мутаций. Подмена несуществующим public API недопустима. Неидентифицированный необходимый callback/несовместимый контракт отклоняет включение общего хода до мутаций боя.
- Перед стартом выполняется capability preflight активных провайдеров. Установка модуля на диске не считается доказательством его активности. Универсальная совместимость с произвольными сторонними turn-модулями не заявляется.

## Подтверждённая база и намеренные изменения

Локальные исходники: Foundry 13.351, dnd5e 5.2.5, DAE 13.0.27, Times Up 13.1.9, MIDI-QOL 13.0.61; `rebreya-main` 1.4.396. Живой мир в этой сессии ещё не проверен, его активные модули и версии необходимо подтвердить при runtime QA.

Намеренно добавляются: managed макрос, общий бросок для однородной новой NPC-группы, логический общий ход, включение режима в уже начатом обычном бою со следующего раунда, начало нового участника при присоединении к открытой группе, client-настройка камеры и соответствующие module flags/API/typed commands. Существующие настройки, формулы, ресурсы, предметы, экономические правила и неуправляемые бои не меняются.

В release обязательны повышение `module.json.version`, новый тонкий `scripts/main-<version>.js`, синхронный `esmodules`, корректные ESM cache keys, обновление API-раздела README и профильного раздела `docs/function-passport.md`.

## Обязательные регрессии до runtime-изменений

| Проверка | Требуемый результат |
| --- | --- |
| Выбор: персонаж, NPC, хранилище, объект, token без Actor | В Combat только подходящие существа; пустой выбор без мутаций |
| Одинаковые NPC, разные baseActor, стороны, linked-токены и initiative rules | Группы определяются контрактом; имена и совпадения чисел не объединяют лишних |
| Native authored formula, advantage/disadvantage и уже установленная инициатива | Ничего не теряется и не перебрасывается; один штатный бросок новой группы |
| Три NPC и следующий персонаж | Все три start до действий группы; все три end при выходе; персонаж начинает после них |
| DAE durations/repeats, source effects на чужой группе, disabled/suppressed | Верный участник, фаза и одно срабатывание; сохранены authored duration и origin |
| MIDI OverTime/ActivityOverTime, save, temp HP/resistance, затихающий урон | Штатные workflows последовательно завершаются; нет дополнительных тиков |
| Изолированный внутренний ActivityOverTime callback | Каждый участник обработан в нужной фазе; native updateCombat и другие провайдеры не дают дублей |
| dnd5e recovery, Effect Macro, реакции и классовые automation | Per-creature фазы сохранены; global period `turn` исполняется один раз на общую фазу, `turnStart` — для каждого начинающего; initiative recovery и movement history сохранены |
| Двойной клик, два GM, задержка workflow, stale command | Одна авторитетная операция; нет повторной фазы и перескока двух групп |
| Повторный macro, подкрепление, разные старые initiatives, удаление, defeated и 0 HP PC | Нет дублей, сброса боя, скрытого переброса или лишней фазы |
| Включение в начатом обычном бою; разные старые initiatives с чужим токеном между ними | Текущий native раунд завершается без повторных тиков; следующий grouped раунд сохраняет инициативу и отдельные непрерывные группы |
| Rewind, прыжок через группы, reorder, reload во время ошибки | Подтверждённые фазы не повторяются; неоднозначная операция видима GM |
| Reload между несколькими damage/save workflows и записью receipts | Завершённые шаги не повторяются; незавершённый неоднозначный шаг требует проверки GM |
| GM и player камеры; hidden group member; другая сцена; настройка отключена | Фокус без утечки координат, смены сцены/масштаба/targets |
| Повтор ready/reload, обычный Combat, старые managed макросы/API | Нет дублированных hooks; старые контракты и обычный бой сохранены |

Focused suites выбираются по владельцам группировки, фазовой интеграции и managed macro; существующие `tests/grapple-macro-service.test.mjs`, `tests/effectmacro-compat.test.mjs`, `tests/decaying-damage.test.mjs` и профильные combat tests остаются регрессиями. До commit runtime-кода выполняются `node --test tests/*.test.mjs`, `node --check` tracked JS/MJS, parse tracked JSON и `git diff --check` согласно AGENTS.md. В живом Foundry проверяется полный цикл группы с эффектом на каждом из трёх NPC и source-эффектом на другом участнике. Без этого пункт об эффектах не считается выполненным.
