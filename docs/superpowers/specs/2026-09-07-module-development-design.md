## Общие инварианты реализации

1. scripts/main.js остаётся единственным composition root; публичные дополнения публикуются через прежние game.rebreyaMain и module.api.
2. UI собирает намерение и показывает результат. World-state пишет domain/application owner через repository/coordinator. Никаких world settings writes из окна.
3. Привилегированное действие игрока: exact typed payload → authenticated sender → authorize → active GM → fresh state → mutation → receipt → scoped refresh.
4. Нельзя передавать от игрока доверенный ItemData, цену, результат броска или senderId. Допустимы идентификаторы и проверяемые решения; authority восстанавливает документы и данные.
5. Retry сохраняет operation ID и fingerprint. Потеря acknowledgement не означает отсутствие записи. Неоднозначный результат не исполняется заново; старый GM прекращает writes.
6. Перенос сохраняет количество, индивидуальную идентичность, flags, effects и связи дочерних Items. Source списывается после подтверждённого target; recovery покрывает разрыв между фазами.
7. Каталог идентифицируется по stable IDs. Runtime не разбирает русское название или prose для исполнения правил.
8. Не вводить второго владельца рук, папок, контейнеров, проклятий, действий атаки, системного отдыха или выдачи лута.
9. Новые/изменённые/удалённые методы вносятся в соответствующий раздел docs/function-passport.md в том же commit. Будущие методы из этих спецификаций пока туда не вносятся: паспорт описывает текущий код.
10. Изменение public API требует обновления соответствующего раздела README.md.
11. Любое изменение клиентских файлов повышает module.json version, меняет esmodules и создаёт scripts/main-<version>.js с единственным импортом main.js. Старые runtime-ссылки проверяются. Только для настоящих docs-only commits версия не повышается.
12. UTF-8, сохранение кириллицы; scoped CSS, ApplicationV2, отсутствие новых frontend frameworks и обязательных сторонних зависимостей.
13. Существующие данные читаются без разрушительной миграции при render; миграции только у authority, идемпотентны и отдельно проверяются.
14. Формулы в спецификациях — предлагаемые контракты нового поведения. Имена новых файлов/методов явно отмечены как проектируемые.

## Согласованные уточнения и оставшиеся решения

- Проклятья уже готовы; автоматизировать остальные типы только там, где бонусы и простые эффекты. Сложные помечать «Усовершенствования нет в реализации», не планировать для них новый движок.

## Общая проверка и Git

Перед правками: git status --short --branch; git branch --show-current; git fetch origin; git rev-list --left-right --count HEAD...origin/main; git log --oneline HEAD..origin/main; сравнить HEAD с origin/lich_branch. Если remote использует master — проверить его аналогично. Чужие незакоммиченные изменения, опережение remote lich_branch или конфликт актуальной основной ветки требуют остановки и сообщения пользователю.

Работать только в lich_branch. Сначала focused-тест владельца, затем минимальная реализация. Перед commit: содержательный diff, diff --stat, diff --check; stage только файлов задачи. Осмысленный commit и git push -u origin lich_branch. Не использовать force push или прямой commit/push в main/master.

Полная проверка один раз перед завершением каждого этапа:
```powershell
node --test tests/*.test.mjs
git diff --check
$files = git ls-files '*.js' '*.mjs'
foreach ($file in $files) { node --check $file }
$json = git ls-files '*.json'
foreach ($file in $json) { Get-Content -Raw -Encoding UTF8 $file | ConvertFrom-Json | Out-Null }
```

Отчёт: точные команды, passed/failed, реальные ошибки, commit, версии фактически проверенного runtime. UI/rolls/сокеты дополнительно проверяются в выделенном Foundry-мире на GM и player: live interactions, reload, повторное открытие, отсутствие дублей hooks, состояние после reconnect и новые console errors. Не выдавать Node-тесты за live QA.
