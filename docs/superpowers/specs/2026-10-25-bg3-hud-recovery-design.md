# BG3 HUD: восстановление после реконнекта и телепортации

Статус: согласована пользователем 2026-10-25; пользователь разрешил самостоятельно составить и выполнить план без дополнительных согласований.

## Наблюдаемый результат

У игрока включённый BG3 HUD восстанавливается для его персонажа после реконнекта, перерисовки canvas и переноса между сценами. Он также восстанавливается после пересоздания токена через DAE в той же сцене. Позднее событие от старой сцены не закрывает новую панель и не стирает её раскладку. У ГМа HUD не создаётся и не рисуется, как в установленной версии.

Исправляются все ошибки из диагностики: сравнение токенов без сцены, отсутствие восстановления lifecycle, закрытие при множественном выделении после загрузки, null/map при обновлении эффектов, неверный индикатор нескольких реакций/бонусных действий и устаревшие import mocks тестов.

## Подход и владельцы

Правки в существующих владельцах `bg3-inspired-hotbar`: `BG3Hotbar`, `HotbarManager`, `ActiveContainer`, `FilterContainer`, существующий lifecycle и тесты. Сохранить обратимый patch установленного модуля, точные резервные копии и SHA-256 manifest в принятом формате `tools/local-module-patches/` репозитория rebreya-main. Новые зависимости, второй HUD и отдельный набор конкурирующих hooks не нужны.

Дополнительно сохранить работоспособность двух существующих compatibility patches rebreya-main: их dynamic imports должны получать те же версии ESM-классов BG3, что и сам HUD. Сейчас bare imports и imports с `?v=3.4.5` дают разные экземпляры классов. Runtime-логика остаётся у BG3.

## Обязательное поведение и сохранение контрактов

1. **ГМ.** Сохранить ранний выход до конструирования `BG3Hotbar` и регистрации его player UI. Настройки по-прежнему зарегистрированы у всех клиентов; их callbacks безопасны без панели. Recovery hooks не обходят GM guard.
2. **Выключенная панель.** При `uiEnabled=false` автоматическое восстановление не открывает HUD. Не переписывать это setting ради восстановления.
3. **Контекст токена.** Учитывать сцену и токен вместе; существующий `currentTokenId` сохранить как контракт. Обработчик удаления получает настоящий исходный TokenDocument и учитывает `options.replacements`. Совпадение ID в другой сцене не означает удаление текущего токена.
4. **Удаление и раскладка.** При удалении/переносе старого токена не удалять flags актёра или нового токена. Существующий явный reset при ручном переключении linked → unlinked остаётся отдельным прежним действием; recovery его не вызывает. Настоящее удаление без подходящего оставшегося персонажа закрывает HUD без записи в данные.
5. **Восстановление.** Использовать существующие события canvas/token и существующий серверный transport; не добавлять polling. Сначала удерживать действующий текущий токен, затем выбирать доступный токен прежнего актёра/назначенного персонажа, затем единственный выделенный либо единственный подходящий собственный токен. Кандидат обязан существовать на текущей сцене и быть доступен игроку; не выбирать чужой или скрытый токен.
6. **Несколько выделенных.** Не закрывать HUD лишь из-за количества выделенных токенов. Удерживать прежнего подходящего персонажа; при отсутствии прежнего выбирать назначенного персонажа, затем первый подходящий выделенный токен в стабильном порядке canvas. HUD показывает одного актёра и не меняет выделение на canvas. При отсутствии доступного токена безопасно закрывается. Обычное ручное снятие всего выделения по-прежнему подчиняется существующей настройке блокировки `deselect`; fallback восстановления применяется к startup/reconnect/canvas/замене токена, а не отменяет это ручное действие.
7. **Асинхронный порядок.** Отложенный control/delete/effect callback и завершение старого render не должны перезаписать более новый контекст. Tear-down отменяет устаревшие запланированные операции; повторные переходы не умножают hooks и не накапливают ссылки на уничтоженные компоненты.
8. **Эффекты.** Без актуального актёра список эффектов равен `[]`; render, удаление и обновление эффекта безопасны во время teardown. При действующем актёре сохранить существующее отображение и действия эффектов. Ошибку действующего render не скрывать пустым catch.
9. **Midi-QOL.** При включённом `synchroBRMidiQoL` состояние bonus/reaction брать из установленного публичного API/счётчиков MIDI. При 1 потраченной реакции из 2 индикатор остаётся доступным; при 2 из 2 помечается потраченным, после сброса восстанавливается. При отсутствии MIDI использовать прежние effect IDs как fallback. При отключённой синхронизации сохранить ручные controls. Advantage/disadvantage и `advOnce` сохранить без изменения расхода ресурсов или workflow.
10. **Данные и настройки.** Не менять setting keys/scopes/defaults, flags namespace и схему, порядок/размеры/содержимое ячеек, сохранённые UUID, фильтры, подготовку заклинаний и остальные прежние ограничения. Не запускать autopopulation персонажа при recovery. Восстановление не пишет actor flags, world settings или игровые ресурсы.
11. **Кэш и версии.** BG3 `3.4.5 → 3.4.6`: новый versioned forwarder, manifest entrypoint и единый `?v=3.4.6` относительных JS imports. Для runtime compatibility imports rebreya-main повысить его установленную версию `1.5.4 → 1.5.5`, синхронно обновить forwarder и manifest. Прежние локальные исправления сохранить. Baseline rebreya-main обновлён после согласования: другие завершённые изменения уже повысили версию до 1.5.4; объём и поведение этой задачи не меняются.

## Намеренные изменения поведения

- Несколько выделенных токенов больше сами по себе не скрывают HUD; он сохраняет контекст одного персонажа по правилам выше.
- После переноса, пересоздания токена или восстановления подключения HUD автоматически привязывается к подходящему токену в текущей сцене.
- Старое удаление больше не очищает чужие/новые данные; индикаторы MIDI учитывают весь доступный лимит.
- Null-актёр означает пустой список эффектов вместо исключения; ссылки на старые компоненты очищаются при пересборке.

Остальные настройки, управление и раскладка сохраняются. Не менять код Midi-QOL, DAE и Foundry core: исправляется обработка их существующих контрактов в BG3.

## Регрессионные проверки до правок runtime

- Реальный lifecycle BG3 у GM: ноль созданий HUD, ноль его render/recovery registrations, настройки зарегистрированы и callbacks безопасны.
- Player ready/reconnect: 0/1/несколько токенов, назначенный персонаж, повторный canvasReady, uiEnabled=false, отсутствие прав/скрытый токен; ручной deselect при включённой/выключенной блокировке сохраняет прежнее поведение.
- Перенос A → B с одинаковым ID и replacement UUID: позднее удаление A не закрывает B и не вызывает unsetFlag/setFlag у B; сохранённая раскладка идентична исходной.
- Перенос с новым ID, DAE create-before-delete в той же сцене, повторный A → B → C и запоздавшие async completions: остаётся актуальный контекст и одна панель.
- Настоящее удаление, teardown и эффект без актёра: безопасное завершение; обновления действующего эффекта продолжают работать.
- MIDI: 0/1/2 из 2 для bonus/reaction, reset, отсутствующий MIDI/API, отключённая синхронизация; прежние advantage/disadvantage/advOnce проверки остаются.
- Исправленный resolver versioned imports сохраняет все прежние runtime-policy assertions; compatibility imports rebreya попадают в canonical BG3 ESM URL.
- До/после сравнить setting metadata, сохранённые fixtures раскладки и отсутствие неожиданных Document writes; проверить canonical imports, синтаксис и JSON.

Профильные тесты исполняют настоящий установленный/изолированно скопированный исходник с doubles только внешних API. Перед commit выполнить обязательную полную suite rebreya-main, синтаксис tracked JS/MJS, JSON и `git diff --check`. Проверить обратное и повторное применение patch к точным backup-копиям. Live GM/player reconnect, эффекты и межсценовый регион проверить через доступную существующую сессию; если подключения нет, явно указать отсутствие live-проверки и не перезапускать чужую игру.

## Условия исполнения и завершения

Работа только в `lich_branch`; исходное состояние чистое, remote синхронизирован. До изменений sibling BG3 зафиксировать backup/hashes; перед применением сверить отсутствие параллельных изменений. Spec и следующий implementation plan входят в task report. Новые/изменённые методы и tests зарегистрировать в `docs/function-passport.md`; сохранить команды, результаты RED/GREEN, версии и инструкции отката. Commit и push выполняются после проверок по AGENTS.md.
