# Папки партийного инвентаря — дизайн

**Статус:** утверждено пользователем 2026-08-23

**Этап:** спецификация перед отдельным планом реализации

## 1. Наблюдаемый результат

Партийный инвентарь остаётся одним списком embedded Item группового Actor, но получает общее для группы дерево организационных папок в стиле каталогов Foundry VTT.

GM и каждый участник текущей группы могут создавать, переименовывать, перемещать и удалять папки, а также переносить между ними целые Item-стэки. Папки раскрываются в основном окне либо открываются как живое поддерево в отдельном popout-окне. Общая структура синхронизируется между пользователями, а раскрытие папок сохраняется отдельно для каждого пользователя.

Папки не являются dnd5e-контейнерами, не имеют веса или вместимости и не изменяют игровые свойства Item.

## 2. Цели

- Организовать большой партийный инвентарь в дерево глубиной до пяти папок.
- Сохранить один канонический владелец поведения и существующую модель embedded Item.
- Разрешить безопасные player-мутации через active GM и typed socket commands.
- Поддержать drag-and-drop внутри основного окна, между ним и popout-окнами, а также возврат в корень.
- Искать одновременно по папкам и предметам без дорогостоящего перечитывания состояния на каждую клавишу.
- Не смещать колонки количества, веса, цены и действий при визуальной вложенности.
- Безопасно открыть существующий мир без отдельной массовой миграции.

## 3. Не входит в первую версию

- Разделение одного Item-стэка между несколькими папками.
- Ручной порядок среди соседей: используется алфавитная сортировка.
- Цвета и пользовательские иконки папок.
- Вес, вместимость, правила dnd5e-контейнеров или изменение свойств Item.
- Автоматическое повторное открытие popout-окон после перезапуска Foundry.
- Нативные Folder Documents Foundry для embedded Item группового Actor.
- Изменение каталожных данных или пользовательского публичного API модуля.

## 4. Текущий владелец и границы изменения

Канонический владелец партийного инвентаря остаётся прежним:

- поведение и общее состояние — `scripts/data/inventory-service.js`;
- group resolution и проверка принадлежности — существующий `GroupContextService`;
- active-GM dispatch и exact-key validation — существующий `SocketCommandBus`, регистрация в `scripts/main.js`;
- сериализация мутаций — существующий `WorldMutationCoordinator`;
- scoped refresh — только `refreshInventoryViews({ actorIds })`;
- UI — `scripts/ui/inventory-app.js`, `templates/inventory-app.hbs`, `styles/main.css`;
- reconciliation embedded Item — существующий `scripts/integrations/inventory-sync.js`, только если ему потребуется очищать устаревшие привязки.

Допускается небольшой чистый модуль `scripts/data/inventory-folder-tree.js` для нормализации, проверки глубины и построения дерева. Он не хранит состояние и не становится вторым владельцем поведения.

Новый глобальный hook, второй resolver, отдельное приложение-владелец или параллельный refresh-канал не создаются. UI не записывает общий Actor state напрямую.

## 5. Рассмотренные варианты хранения

### 5.1. Выбранный: всё организационное состояние во флаге группового Actor

Дерево папок и соответствие Item папкам хранятся одной структурой во флаге Actor. Перенос Item меняет только эту структуру и не обновляет сам Item Document.

Преимущества:

- одна атомарная запись общего состояния;
- игровые данные Item остаются неизменными;
- простая проверка циклов и глубины;
- отсутствие записи автоматически означает корень;
- проще нормализовать удалённые Item и повреждённые ссылки.

### 5.2. Отклонённый: дерево на Actor, `folderId` на каждом Item

Этот вариант требует нескольких document writes, сложнее восстанавливается после частичной ошибки и изменяет документы Item при каждой реорганизации.

### 5.3. Отклонённый: нативные Folder Documents Foundry

Нативные папки каталогов не являются владельцами embedded Item одного Actor. Их зеркалирование создаст второй жизненный цикл и источник истины.

## 6. Общая схема состояния

Общий флаг группового Actor:

```js
flags["rebreya-main"].inventoryFolders = {
  version: 1,
  folders: [
    {
      id: "stable-folder-id",
      name: "Оружие",
      parentId: null
    }
  ],
  itemFolderIds: {
    "embedded-item-id": "stable-folder-id"
  }
}
```

Правила схемы:

- `id` стабилен при переименовании и перемещении; одинаковые названия разрешены.
- `parentId: null` означает корневой уровень.
- Отсутствующий ключ Item в `itemFolderIds` означает корень.
- У одного `itemId` может быть только одно значение `folderId`.
- Ручное поле `sort` не хранится.
- Корневая папка имеет глубину 1; допустимая максимальная глубина — 5.
- Счётчик папки показывает рекурсивное число Item Documents/стэков (`N поз.`), а не сумму quantity.

Личное состояние пользователя:

```js
flags["rebreya-main"].inventoryFolderUi = {
  version: 1,
  groups: {
    "group-actor-id": {
      expandedFolderIds: ["stable-folder-id"]
    }
  }
}
```

Оно синхронизируется между устройствами через User Document. Popout-окна в этот флаг не входят и после входа автоматически не открываются. UI изменяет личный флаг через метод существующего module API/сервиса, а не прямой записью общего Actor state.

## 7. Нормализация и восстановление

Отсутствующий флаг нормализуется в пустую структуру версии 1; поэтому отдельная массовая миграция существующих миров не нужна и все текущие Item остаются в корне.

Нормализатор должен быть чистым и детерминированным:

- обрезать пробелы вокруг имени;
- отбрасывать записи без валидного стабильного ID или непустого имени;
- при повторном ID сохранять первую валидную запись;
- заменять отсутствующего родителя и самоссылку на `null`;
- для цикла поднимать участвующие в цикле папки в корень;
- если ветка превышает пять уровней, поднимать первую нарушающую глубину папку в корень, сохраняя её допустимое поддерево;
- удалять `itemFolderIds` для отсутствующих embedded Item;
- трактовать неизвестный `folderId` у существующего Item как корень;
- удалять из пользовательского `expandedFolderIds` ID отсутствующих папок.

Read path строит безопасную нормализованную проекцию и никогда не зацикливается. Следующая успешная общая мутация сохраняет уже нормализованное состояние одной записью Actor. Нормализация не изменяет игровые поля Item.

## 8. Команды и авторизация

Предпочтительны отдельные typed-команды с точными payload:

- `inventory.folder.create`;
- `inventory.folder.rename`;
- `inventory.folder.move`;
- `inventory.folder.delete`;
- `inventory.item.folder.move`.

Каждый payload содержит ID целевого группового Actor и только необходимые поля операции. Create также получает заранее сгенерированный стабильный `folderId`; повтор команды с тем же ID и теми же данными становится естественно идемпотентным. Конфликт существующего ID с другими данными отклоняется.

Остальные операции идемпотентны по результату: повторное переименование или перемещение в уже установленное состояние успешно ничего не меняет; повтор удаления не удаляет содержимое. Socket envelope сохраняет штатный `requestId`, а операции одного Actor проходят через `WorldMutationCoordinator` с ключом этого Actor.

Active GM перед записью заново разрешает target Actor и проверяет:

- отправитель является GM либо текущим участником именно этой группы;
- Actor является каноническим инвентарём разрешённой группы;
- папки и Item существуют в актуальном snapshot;
- новое имя после trim непустое и не длиннее 80 символов;
- новый родитель существует либо равен `null`;
- папка не перемещается в себя или потомка;
- глубина самой глубокой части переносимого поддерева остаётся не больше 5;
- Item не получает больше одной принадлежности.

Проверка проводится после ожидания очереди мутации, а не по устаревшему UI snapshot. Допустимая устаревшая команда применяется к текущему состоянию; недопустимая возвращает понятную ошибку и вызывает перечитывание snapshot инициатором.

## 9. Семантика операций

### 9.1. Создание

- Кнопка главного инвентаря создаёт папку в корне.
- Кнопка popout создаёт папку непосредственно внутри его корневой папки.
- Контекстное меню папки содержит «Создать вложенную папку».
- Диалог trim-ит имя и не принимает пустое значение или строку длиннее 80 символов.

### 9.2. Переименование

Изменяется только `name`. ID, дети, Item membership и открытые popout остаются прежними. Заголовки открытых popout обновляются через scoped refresh.

### 9.3. Перемещение папки

Папка переносится вместе со всем поддеревом. Перед записью проверяются цикл и итоговая глубина самого глубокого потомка. Поскольку сортировка автоматическая, drag-and-drop задаёт только нового родителя, но не ручную позицию.

### 9.4. Перемещение Item

Перемещается весь embedded Item Document вместе со своим quantity. Разделения стэка нет. `folderId: null` удаляет запись membership и возвращает Item в корень.

### 9.5. Удаление папки

Удаление никогда не удаляет Item или дочерние папки:

- Item удаляемой папки получают её `parentId` либо корень;
- прямые дочерние папки получают тот же новый parent;
- более глубокое поддерево остаётся связанным с прямыми детьми;
- открытый popout удалённой папки закрывается с уведомлением о переносе содержимого выше.

Перед операцией UI показывает подтверждение с явным пояснением этого поведения.

## 10. Поступление и объединение предметов

Существующие правила `itemsCanMergeInInventory()` и различение durability signature остаются каноническими.

- Новый отдельный Item без folder target создаётся в корне.
- Внешний Item, брошенный на строку папки, передаёт эту папку как target.
- Операция поступления, инициированная из popout, по умолчанию передаёт его root folder как target.
- Если Item объединяется с существующим стэком, обновляется существующий Item и сохраняется его текущая папка; запрошенный target не переносит стэк неявно.
- Если создаётся новый Item, membership записывается только после доказанного успешного создания Item.
- Ошибка записи membership после создания проходит через существующий recovery/receipt-путь либо безопасно оставляет созданный Item в корне; дублировать Item при retry нельзя.

Внутренние optional-поля folder target можно добавить в существующие import/storage grant routes, но нельзя создавать второй маршрут выдачи или ослаблять exact-key validation и authoritative re-resolve.

## 11. Построение дерева и сортировка

Snapshot инвентаря содержит нормализованные папки и `folderId` каждой Item-строки. UI строит из одного snapshot дерево, не перечитывая Actor для каждого уровня.

На каждом уровне:

1. папки сортируются по локализованному алфавиту;
2. затем Item сортируются по выбранному алфавитному режиму;
3. папки и Item не смешиваются в единый алфавитный список.

В первой версии выбор другого sort mode может менять порядок Item, но папки всё равно идут раньше Item и сортируются по названию. Принадлежность и раскрытие не влияют на общие количество позиций, вес и стоимость.

## 12. Поиск и производительность

Главное окно ищет по всему дереву; popout — только внутри своего поддерева.

- Папка сопоставляется по имени.
- Item сохраняет существующие поля поиска: название, тип, материал и уже поддержанные нормализованные признаки.
- Для каждого совпавшего элемента выводится цепочка родителей.
- Родители совпадений временно раскрываются только в вычисленном render context.
- Временное раскрытие поиска не записывается в User flag.
- Совпавшая папка показывается с родителями; её несовпавшие потомки не становятся результатами автоматически.
- Type filter применяется к Item; папки остаются видимыми, только если совпали сами либо ведут к видимому Item.

Инвентарный snapshot и нормализованный поисковый индекс кэшируются на уровне открытого приложения. Input search использует существующий debounce и выполняет только чистую фильтрацию/перерисовку. На каждую клавишу запрещены Actor/User writes, socket requests, повторная catalog resolution и полное получение snapshot из сервиса.

## 13. UI основного окна

Toolbar сохраняет поиск, фильтр и сортировку. Поле поиска становится немного уже; справа от сортировки появляется одна компактная icon-only кнопка папки с tooltip и доступным `aria-label` «Создать папку».

Строка папки:

- занимает полную ширину списка, но заметно ниже Item-строки;
- содержит chevron раскрытия, единую иконку папки, название, рекурсивный счётчик `N поз.` и меню;
- не имитирует колонки quantity/weight/price;
- получает Foundry-подобные hover, selected/drop-target состояния в цветах модуля;
- не получает настройку цвета в первой версии.

Меню папки:

- «Создать вложенную папку»;
- «Переименовать»;
- «Открыть отдельно»;
- «Удалить».

Вложенность задаётся отступом только внутри ведущей области иконки/названия. Grid-колонки количества, веса, цены и меню Item остаются одинаковыми на всех уровнях. Отступ растёт на небольшой фиксированный шаг до глубины 5 и не рассчитывается процентом от всей строки.

## 14. Раскрытие и личное состояние

Chevron раскрывает или сворачивает папку только у текущего пользователя. Изменение сначала применяется оптимистично в памяти приложения, затем объединённо записывается через module API во флаг текущего User.

- Другие пользователи не получают этот UI-state.
- Reload Foundry и вход с другого устройства восстанавливают состояние.
- Закрытие popout не удаляет папку и не меняет раскрытие дерева.
- Созданную или перемещённую папку можно раскрыть независимо в каждом окне.
- Удалённые ID очищаются при следующей нормализации личного состояния.

## 15. Drag-and-drop

Внутренний drag payload различает folder и Item, содержит target Actor ID и стабильный document/folder ID. Payload не является источником прав: active GM всё перечитывает и авторизует.

- Drop на папку означает помещение внутрь и подсвечивает всю строку папки.
- Drop на свободную область списка либо явную корневую область означает возврат в root текущего группового инвентаря.
- Drop между главным окном и любым его popout использует тот же payload и команды.
- Папку нельзя переносить между разными групповыми Actor.
- Внешний Item можно импортировать в папку через существующий import route с folder target.
- Недопустимая цель визуально не принимается; серверная ошибка дополнительно показывается уведомлением.
- Drop не задаёт позицию между соседями, потому что после него действует автоматическая сортировка.

## 16. Popout папки

Popout является вторым представлением того же Actor, а не копией данных. Предпочтительно переиспользовать `InventoryApp` с параметрами `groupActorId` и `rootFolderId`, отдельным стабильным application key и урезанным до поддерева context.

Popout предоставляет:

- заголовок из актуального имени корневой папки;
- локальный поиск только по поддереву;
- существующий фильтр и сортировку;
- создание дочерней папки;
- те же context actions и drag-and-drop;
- синхронное обновление после scoped refresh.

Переименование или перемещение корневой папки не закрывает popout благодаря стабильному ID. Удаление папки закрывает только соответствующие окна с уведомлением. Автоматическое повторное открытие popout после reload не выполняется.

## 17. Refresh, конкурентность и ошибки

Поток общей мутации:

1. UI/API формирует минимальный exact payload.
2. `SocketCommandBus` аутентифицирует transport sender, выполняет validate и authorize.
3. Active GM ставит операцию в actor-scoped очередь `WorldMutationCoordinator`.
4. Внутри очереди `InventoryService` заново читает Actor, Item и folder state.
5. Сервис нормализует состояние, проверяет инварианты и делает одну запись Actor flag.
6. Composition root вызывает `refreshInventoryViews({ actorIds: [groupActorId] })`.
7. Только основное окно и popout этого Actor перечитывают snapshot.

Document hooks не должны запускать второй конкурирующий цикл обновления для той же flag-записи. Если существующий inventory-sync hook видит обновление Actor flag, он должен либо игнорировать организационный flag, либо коалесцировать его через существующий refresh coordinator.

Ожидаемые пользовательские ошибки локализуются и объясняют действие: пустое имя, шестой уровень, цикл, удалённая цель, отсутствующий Item, потеря членства в группе. Ошибка не закрывает главное окно; инициатор перечитывает актуальный snapshot.

## 18. Ожидаемые файлы реализации

Точный план уточнит места после focused-инспекции, но ожидаемая область ограничена:

- `scripts/data/inventory-folder-tree.js` — чистая нормализация и дерево;
- `scripts/data/inventory-service.js` — канонические snapshot/mutations и интеграция membership со стэками;
- `scripts/main.js` — typed command registration, module API и scoped refresh;
- `scripts/ui/inventory-app.js` — context, popout, personal state и drag-and-drop;
- `templates/inventory-app.hbs` — toolbar, folder rows и nested rendering;
- `styles/main.css` — компактная строка папки, отступ и drop states;
- при доказанной необходимости `scripts/integrations/inventory-sync.js` — только очистка устаревших Item membership;
- профильные focused-тесты;
- раздел 7 `docs/function-passport.md` для всех новых или изменённых методов и команд.

`README.md` не меняется, пока публичный пользовательский API остаётся прежним.

## 19. Тестовая стратегия

### 19.1. Чистое дерево

Новый focused-тест, например `tests/inventory-folder-tree.test.mjs`:

- пустая/повреждённая схема;
- одинаковые имена и разные ID;
- missing parent, self-parent, cycle и duplicate ID;
- глубина 1–5 и отклонение 6;
- проверка глубины всего переносимого поддерева;
- рекурсивный Item count;
- сортировка folders-first/items-second;
- delete/reparent и root membership.

### 19.2. Владелец состояния и recovery

Расширить `tests/group-inventory-migration.test.mjs` и `tests/inventory-mutation-recovery.test.mjs`:

- отсутствие флага оставляет Item в корне;
- одна Actor flag write на мутацию;
- actor-scoped serialization;
- новый Item получает target folder только после create;
- существующий merge candidate сохраняет прежнюю папку;
- broken/damaged варианты не сливаются;
- retry не создаёт вторую папку или Item;
- удалённые Item membership очищаются безопасно.

### 19.3. Команды и безопасность

Новый focused-тест либо расширение socket/security suites:

- exact-key validation всех пяти команд;
- GM и участник целевой группы разрешены;
- участник другой группы и неизвестный sender запрещены;
- target Actor повторно разрешается на active GM;
- stale move повторно проверяет цикл и глубину;
- конфликт folder ID отклоняется;
- refresh ограничен изменённым Actor.

### 19.4. UI context

Расширить `tests/inventory-app-context.test.mjs`:

- folders-first/items-second на каждом уровне;
- глубина и fixed-column context;
- рекурсивные счётчики;
- collapse/expand отдельно по User state;
- поиск показывает родителей и не изменяет сохранённое раскрытие;
- popout ограничивает search/filter поддеревом;
- rename обновляет title;
- delete закрывает только затронутый popout;
- internal drag payload и root/folder targets;
- search input не вызывает повторный `getInventorySnapshot`, socket request или persistence на каждую клавишу.

### 19.5. Ручная проверка Foundry

- GM и два игрока одновременно видят create/rename/move/delete.
- У игроков различается раскрытие, и оно восстанавливается после reload.
- Main ↔ popout drag-and-drop работает в обе стороны.
- Drop на свободную область возвращает Item/папку в root.
- Нельзя создать цикл или шестой уровень.
- Удаление сохраняет содержимое и закрывает удалённый popout.
- Колонки Item не двигаются при глубине 1–5.
- Общие вес, стоимость и количество не зависят от collapse/filter.
- Быстрый ввод в search не вызывает видимых лагов.

## 20. Критерии готовности реализации

- Все утверждённые операции доступны GM и каждому участнику своей группы.
- Каждый Item находится в корне либо ровно в одной папке.
- Максимальная глубина равна пяти; циклы невозможны.
- Общая структура синхронизируется, личное раскрытие изолировано по User.
- Popout является живым поддеревом и поддерживает те же переносы.
- Удаление папки никогда не удаляет содержимое.
- Существующий стэк при merge сохраняет папку; durability variants остаются раздельными.
- Поиск работает по кэшированному snapshot и не возвращает прежний input lag.
- Нет второго resolver/hook/state owner и нет прямой общей world-state mutation из UI.
- Каталоги, игровые поля Item и публичный API не изменены без необходимости.
- Раздел 7 `docs/function-passport.md` отражает все новые и изменённые методы, команды, data flow и focused-тесты.
- Focused-тесты и полная проверка из `AGENTS.md` проходят перед commit.
