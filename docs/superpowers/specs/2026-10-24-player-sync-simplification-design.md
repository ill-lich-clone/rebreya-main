# Синхронизация действий игроков: причины и проект упрощения

Статус: предложение для согласования, не утверждённая реализация.
Исследован commit `b9ec4cc2`, ветка `lich_branch`, модуль 1.5.2.
Локальная установленная Foundry: 13.351. Живой сеанс GM/player недоступен;
выводы ниже основаны на исходниках и воспроизводимых Node-пробах.

## Требуемый результат

Игрок видит завершённое действие без ожидания чужого персонажа или окна.
Повторный клик во время ожидания присоединяется к исходному действию и не
создаёт новую операцию. Изменение собственного предмета, не перемещающее
ценности между владельцами, использует штатные Document API Foundry там,
где прав владельца достаточно. GM-команды остаются для операций, которым
действительно нужны права GM или согласованное изменение нескольких владельцев.

Проблема относится ко всем действиям игроков. Кукла используется как
воспроизводимый пример; общие transport/scheduling/refresh исправления
должны распространяться на всех их callers.

## Подтверждённые механизмы

1. **Лишние сохранения при простой экипировке.**
   `HeroDollService.#submitAssignment()` всегда вызывает публичный GM-маршрут
   (`scripts/data/hero-doll-service.js:364`, `scripts/main.js:2343`).
   `executeAssignItemToSlot()` запускает `ItemInstanceWorkflow`, включая
   случай одного собственного предмета без split/transfer.
   Workflow сохраняет start + три checkpoint + finish
   (`scripts/application/item-instance-workflow.js:161–184`).
   Проба на `makeInstanceDocumentsFixture({quantity:1})` с настоящим сервисом:
   equip = 5 setting writes + 2 document writes; clear = те же 5 + 2;
   количество остаётся 1. Это число записей, не измерение сетевой задержки.

2. **Общий журнал снова связывает независимые операции.**
   `DurableMutationJournal.find/listPending/start/checkpoint/finish` используют
   один ключ `durable-mutation-journal`; даже чтение ждёт незавершённую запись
   (`scripts/application/durable-mutation-journal.js:103–218`).
   Изменение одной записи клонирует и сохраняет весь state (:262–291).
   Inventory подключает его к world setting (:1982–1985 в inventory-service.js).
   Проба: задержанная запись A блокирует `find` несвязанной операции B.
   Фазы разных операций могут чередоваться: утверждение, что B обязательно
   ждёт все пять фаз A подряд, неверно. Простое удаление lock здесь повредит
   read-modify-write одного общего setting и не является исправлением.

3. **Повторный клик разрушает защиту от повторов.**
   Bus отвергает уже pending request как `duplicate-request`
   (`scripts/infrastructure/foundry/socket-command-bus.js:263–268`).
   Hero service удаляет pending intent при этой ошибке (:376; аналогично :467).
   Проба с реальными HeroDollService, PrivilegedMutationGateway и SocketCommandBus:
   первый клик остаётся pending; второй даёт duplicate-request и очищает map;
   третий отправляет второй запрос с новым operationId.
   Подтверждено создание независимого запроса; фактическое дублирование предметов
   в живом мире этой пробой не доказано.

4. **Один Actor имеет разные ключи конкуренции.**
   `actorKey` напрямую вызывает `aggregateKey` (`scripts/main.js:458`),
   который лишь обрезает пробелы (`socket-command-scheduling.js:26`).
   Кукла передаёт `Actor.hero` (:2436), inventory take — `hero` (:2832).
   Проба coordinator: `actor:Actor.hero` и `actor:hero` стартуют одновременно.
   Это доказанный разрыв внешней сериализации; некоторые внутренние очереди
   могут дополнительно защищать конкретные маршруты. Потеря данных не доказана.

5. **Перерисовка разных окон связана общим ожиданием.**
   `UiRefreshCoordinator.#drain()` ждёт весь предыдущий Promise.allSettled
   перед запуском следующего batch (:24–31).
   Проба: зависший render торговца задерживает пришедший позже refresh инвентаря.
   Дополнительно `runInventoryMutation` удерживает общий счётчик refresh
   (:7707 и далее в main.js); живое влияние этого счётчика надо замерить отдельно.

6. **Тайм-аут не отменяет серверную работу.**
   Bus удаляет локальный pending и отклоняет promise (:531–550), но queued/running
   работа GM продолжает жить. Gateway повторяет тот же ID один раз и затем
   возвращает ambiguous-outcome (:295–315). Это не доказательство потери пакетов;
   пользовательский интерфейс обязан различать «отказано» и «исход пока неизвестен».
   Проба с двумя bus и fake timers: после accepted истекают 60000 ms,
   клиент получает operation-timeout; снятие блокировки затем запускает
   executor один раз. Это воспроизводимый поздний запуск, не живой замер 60 s.

## Что не подтвердилось

- Memory dedup coordinator — Map lookup с bounded completed cache 256; сам по
  себе он не создаёт сетевых ожиданий. Удалять его ради скорости незачем.
- Внешний scheduler уже допускает независимые keyed операции параллельно.
- Установленная Foundry 13.351 действительно передаёт authenticated sender
  вторым аргументом custom socket callback (проверено в установленном
  `resources/app/dist/server/sockets.mjs`). Проверка sender не отвергается
  на основании предположения, что такого аргумента у платформы нет.
- Реальная доля причин задержек, поведение Cloudflare и взаимодействие с
  остальными модулями не измерены; нельзя приписывать им или этому коду «99%».

## Подходы

**Рекомендуемый: упрощать по праву владения и размеру операции.** Сначала
устранить подтверждённые дефекты общих механизмов, затем вывести простые
owner-операции из GM/recovery пути. Сохранить текущие сервисы и публичные API.

**Альтернатива: заменить весь custom transport штатными User.query.** Это
не устраняет пять journal writes, внутренние очереди и связанную перерисовку.
Большая миграция протокола сейчас не обоснована измерениями.

**Альтернатива: отключить очереди и журнал целиком.** Смешивает простую
экипировку с покупкой/переносом и допускает потерю изменений общего setting.
Не подходит под требование сохранить предметы, деньги и правила.

Выбор рекомендуемого подхода пока является предложением Codex.

## Границы первой реализации

1. В существующем bus один и тот же pending intent возвращает общий результат.
   Совпадают sender, command, request ID и содержимое payload. Другой payload
   под тем же ID по-прежнему отклоняется. Сигнатуры API сохраняются; это
   намеренное изменение контракта повторного идентичного вызова.
2. Канонизировать Actor identity в существующем scheduling owner и проверить
   все регистрации, где используются Actor ID/UUID; source/target footprint
   операций должен совпадать с реально затрагиваемыми документами. Не
   объединять очереди независимых Actor и не менять synthetic Actor identity
   на world Actor identity без проверки соответствующего контракта.
3. В существующем UiRefreshCoordinator запускать независимые app keys
   независимо. Один app не рендерится одновременно сам с собой; поступивший
   во время render запрос обеспечивает последующий refresh свежего состояния.
   Caller ждёт собственные задачи; ошибки одного окна не блокируют другое.
4. В HeroDollService добавить штатный owner route для assign/clear уже
   существующего singleton внутри одного Actor. Сервис проверяет владение,
   допустимость слота и текущее состояние; UI по-прежнему вызывает сервис.
   Ни custom GM request, ни durable world journal для этого случая не нужны.
   Использовать минимальные Document patches; для конкурентных изменений
   сохраняется обычная модель владения Foundry, без обещания глобальной
   транзакции между клиентами. В пределах клиента порядок изменений одного
   Actor сохраняется. Если второй document write падает, операция явно
   сообщает ошибку, перечитывает состояние и восстанавливает затронутые поля
   только при отсутствии последующих изменений; не скрывает частичный исход.
5. Split, transfer между Actor, изменение количества, normalize legacy stack,
   применение комплектов с несколькими предметами и общие world settings
   остаются на существующем авторитетном маршруте в этой реализации.
   Это явная граница: ускорение простого assign/clear не выдаётся за полную
   миграцию всех функций. Для остальных owned actions составить компактную
   классификацию по реальным callers, без массового изменения на предположениях.
6. Избавление от общего durable setting для оставшихся многошаговых операций
   требует отдельного решения о хранении и миграции существующих receipts.
   В первой реализации его не удалять, не делать fire-and-forget и не
   превращать незавершённые manual-review записи в успешно завершённые.
7. Для ожидающих GM-операций различать pending, подтверждённый отказ и
   неизвестный исход. Тайм-аут не должен предлагать повтор с новым ID.
   Использовать существующий stable intent/replay маршрут; не добавлять
   отмену уже начатой многошаговой мутации или бесконечный автоматический retry.

### Уточнения после независимого builder check

- **Owner route и одновременная GM-операция:** никакой новой распределённой
  блокировки. Как в штатном листе Foundry, владелец меняет только допустимые
  поля собственного документа; остатки, валюты и удаление Item в этом пути
  не затрагиваются. Использовать точечные slot patches вместо перезаписи
  всего heroDoll. Если предмет исчез/изменил количество или размещение до
  завершения, перечитать состояние, сообщить конфликт и не сообщать успех.
  Это не обещание атомарной транзакции с параллельным transfer; такая гарантия
  сознательно не входит в owner route. Проверить этот сценарий отдельно.
- **Занятый другим Item слот:** в первой реализации остаётся GM workflow.
  Не создавать новый rollback engine для swap. Fast path ограничен singleton
  в пустой слот, изменением размещения того же singleton и его снятием;
  дополнительные изменения чужих Item выводят операцию в прежний путь.
- **Synthetic Actor:** для текущих world-Actor команд bare ID трактуется
  исключительно как world Actor ID и канонизируется с Actor UUID. Существующий
  Scene/Token UUID сохраняется целиком. Caller, который действительно работает
  с synthetic Actor, обязан передавать уже известный полный UUID; не искать
  его синхронно по bare ID и не объединять разные Token Actor.
- **Идентичность клика:** bus объединяет только тот же intent ID с тем же
  payload. Семантически похожие покупки/переносы с разными ID объединять
  нельзя. UI/services сохраняют один ID пока действие pending или outcome
  неизвестен; проверить реальные callers, генерирующие ID заново. После
  подтверждённого завершения следующий осознанный клик — новая операция.
- **Правила:** переиспользовать существующую same-Actor валидацию допустимости
  слота/предмета и владения из HeroDollService. Server-side Document permissions
  продолжают действовать. Не выдумывать новые запреты на curses/attunement;
  найденные существующие правила/hook отмены необходимо сохранить и проверить.
  Случаи, требующие GM-only данных или мутаций, остаются на GM-маршруте.

## Сохраняемые контракты и намеренные изменения

Сохраняются item ID singleton, количество и дробная точность, stack splitting,
содержимое контейнеров, установленные улучшения, индивидуальное состояние,
held/equipped semantics, совместимость слотов и комплектов, ghost slots,
правила доступа к группе, authored formulas, настройки, цены, бюджеты,
списание валют/ресурсов, receipts и recovery для незавершённых операций.
Не менять публичные имена API, stored flag schemas и socket command names.

Намеренно меняются: идентичный повтор ждёт исходную операцию; Actor ID/UUID
получают один конфликтный ключ; окна обновляются независимо; простая owner
экипировка работает без присутствия активного GM и без пяти world writes.
UI не сообщает успех раньше подтверждения реальной записи документов.

## Проверки до продуктовых изменений

- Regression на тройной клик: один intent/emit/эффект, общий результат;
  конфликтующий payload не присоединяется. Отдельно ошибка и повтор после неё.
- ID и UUID одного Actor конфликтуют; разные Actor выполняются параллельно;
  проверки footprint source/target и отсутствие self-deadlock.
- Задержанный/ошибочный render A не задерживает B; один app получает свежий
  следующий render без параллельного render самого себя.
- Player owner assign/clear singleton: 0 custom requests, 0 world-setting
  writes, сохранён ID/quantity/held state и корректный итог slots/equipped.
  Player non-owner отклонён. Без GM owner route работает; transfer требует GM.
- Неподходящие слоты, повторное назначение, slot replacement, ошибки между
  записями, конкурентное изменение, reload persistence и существующие split,
  presets/ghost, recovery и торговые правила остаются покрыты.
- Тесты не ослаблять ради новой реализации: сначала закрепить требования
  failing regressions, затем минимальное исправление.

Уже выполнено: 159 passed / 0 failed в семи текущих focused suites:
`world-mutation-infrastructure`, `privileged-mutation-gateway`,
`durable-mutation-journal`, `item-instance-workflow`, `hero-doll-instances`,
`hero-doll-presets`, `ui-refresh-coordinator` (все `tests/*.test.mjs`).
Команда: `node --test --test-reporter=tap tests/world-mutation-infrastructure.test.mjs tests/privileged-mutation-gateway.test.mjs tests/durable-mutation-journal.test.mjs tests/item-instance-workflow.test.mjs tests/hero-doll-instances.test.mjs tests/hero-doll-presets.test.mjs tests/ui-refresh-coordinator.test.mjs`.
Шесть диагностических сценариев выше проверены отдельными Node-пробами;
это не регрессионные тесты исправления и не живой GM/player тест.

После реализации: required full suite, JS syntax, JSON parsing, diff check;
новая версия module.json и согласованный versioned forwarder; проверить
клиентские import/cache URLs изменённых модулей; обновить профильный паспорт.
В отдельном тестовом мире проверить GM + два игрока, отсутствие GM, повторные
клики, одновременные действия разных Actor, задержку ответа и reconnect.
Снять существующую socket telemetry и document/setting write counts, затем
сравнить задержки; не обещать миллисекунды без измерений.

runtime не меняется. План ещё не создан и утверждённым не считается.
