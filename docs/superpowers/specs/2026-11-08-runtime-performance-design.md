# Производительность реакций, боя, контейнеров и экономики

При перемещении нескольких токенов, переключении группового хода, переносе контейнера и пересчёте экономики модуль выполняет меньше повторных обходов. Игроки видят те же доступные реакции, порядок ходов, содержимое контейнеров и результаты экономики. Торговцы за пределами задачи.

## Подход

Аудит предложил индексировать связи у существующих владельцев данных и переиспользовать результаты внутри одной операции. Индекс реакций хранит обратную связь на время жизни сцены, поскольку уже владеет индексами сцены. Бой и операции с предметами строят индексы из актуальных документов на время расчёта. Долгоживущие кэши для боя и предметов потребовали бы отдельной инвалидации на изменения Foundry и сторонних автоматизаций.

## Индекс реакций

`ReactionCapabilityIndex` поддерживает соответствие UUID токена и актёра при построении сцены, переиндексации, смене актёра токена и удалении. Обновление одного токена удаляет его старую запись напрямую, с затратами, пропорциональными числу его записей реакций. Вызовы провайдеров на `updateToken` сохраняются, поскольку публичный провайдер может читать координаты. Регрессионный тест проверяет, что обновление токена обходится без обхода всех актёров и сохраняет результаты провайдеров при переносе токена между актёрами, удалении и смене сцены.

## Групповой бой

В расчёте `skipDefeated` трекер и GM обрабатывают участников и членство групп одним проходом на синхронный расчёт. Проверка бойца перед асинхронным шагом фазы получает его по ID из актуальной коллекции Foundry. Адаптер тестов поддерживает массивы участников. Планирование фазы использует множества ID и один расчёт позиции хода для всех эффектов, которым она нужна. Сохраняются порядок групп, выбор при всех побеждённых, проверка полномочий игрока, условия истечения эффектов, порядок автоматизаций и контрольные записи перехода. Тесты фиксируют число чтений списка на большом бою и удаление бойца между шагами.

## Контейнеры

При захвате, удалении и откате переноса контейнера индекс предметов строится один раз на снимок инвентаря. Связи по ID, нативному родителю и флагам установленного компонента читаются из этого индекса, включая проверку осиротевших привязок. Сохраняются порядок обхода, идентичности экземпляров, количества, payload снимков и порядок удаления потомков.

При проверке циклов используется один обход графа родителей с переиспользованием результата для уже посещённых цепочек. Выбор сумки для отсоединения сохраняет приоритет `updatedItemId` и прежний порядок кандидатов. Одно синхронное создание нескольких предметов одного актёра ставит одну проверку вместо нескольких. Для выбора сохраняется ID первого события, как при первой проверке прежней очереди. Отдельное изменение родителя сохраняет собственную проверку. Тесты считают обходы на большом инвентаре, проверяют порядок выбора в цикле и проверяют снимок и удаление контейнера с установленными компонентами.

## Экономика

`EconomyRepository` возвращает уже собранную базовую модель, если сервис глобальных событий отсутствует или сообщает, что подсистема выключена. Активные события применяются текущим расчётом, а охват города использует готовый `cityById` модели. Для входных данных со списком городов сохраняется путь поиска по списку. Сохраняются маршруты, цены, формулы, состояние событий, ревизия модели и сброс её зависимых кэшей. Тесты проверяют одну сборку при выключенных событиях, прежний результат при активных событиях и охват через оба вида входных данных.

## Проверка и выпуск

Перед правками каждый тест производительности должен упасть по ожидаемому счётчику операций. Тесты проверяют число обходов, чтобы результат не зависел от скорости машины. После правок проходят профильные и полные проверки репозитория. Изменённые методы отражаются в паспорте функций, версия и entrypoint повышаются в `lich_branch`.
